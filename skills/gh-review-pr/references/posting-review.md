# Posting A Maintainer Review

Part of **gh-review-pr**. Read after the technical review and finding inventory are complete, immediately before constructing or posting the GitHub review. It contains the live-state rechecks, atomic payload rules, verdict selection, anchor validation, and post-write verification.

1. Before posting, re-list existing PR reviews with `gh api repos/{owner}/{repo}/pulls/{number}/reviews --paginate`.
2. If a review authored by you is `PENDING`, delete it with `gh api repos/{owner}/{repo}/pulls/{number}/reviews/{review_id} --method DELETE`.
3. Recompute the head SHA. If it differs from the SHA reviewed, stop and review the new head instead. Embed the sentinel `<!-- gh-review-pr:sha=<HEAD_SHA> -->` at the end of the review body. Recheck the reviews listed in step 1 for one authored by you (compare `user.login` to `gh api user --jq .login`) whose body already contains that exact sentinel; if one exists, do not post again — report that you already submitted a review for this head SHA (cite its state and id) and stop, unless the repeat-review exception in [review-state-edge-cases.md](review-state-edge-cases.md) applies (the user invoked this skill directly on that head, or explicitly asked to redo and post it). In that case, post a new review anyway: open the body by stating it supersedes the prior review of the same head, and keep the same sentinel since the head is unchanged.
   - Before constructing the final body, confirm every top-level review-body finding has a unique `<!-- gh-review-pr:finding=... -->` marker. Do not leave body-only findings as unmarked prose or bullets; follow-up address and verification workflows depend on stable anchors.
4. Before assembling the payload, validate every inline `path`/`line`/`side` against the exact hunks GitHub exposes through `gh pr diff` or the paginated pull-files endpoint's `.patch` fields. A non-null patch proves only that *some* hunks render: an unchanged current line between two hunks is outside the diff and makes the atomic POST fail with `Line could not be resolved`. Move an out-of-hunk anchor to the nearest changed line and name the real location in its body. When no hunk renders for a large, binary, or generated file, put that finding in the review body instead. Then prefer one atomic review POST so a failed step does not leave a pending review: write a JSON body with `commit_id` set to the reviewed head SHA, `event`, `body`, and `comments` (`[]` for a body-only review), then call `gh api repos/{owner}/{repo}/pulls/{number}/reviews --method POST --input <json_file>`. Build that JSON by serializing an object with a real serializer (for example a short Python `json.dump` snippet), never by hand-authoring the JSON text: the `body` is Markdown full of double quotes, backticks, `<!-- ... -->` markers, and newlines, and a single unescaped `"` inside it makes the POST fail with `Problems parsing JSON` (HTTP 400). Have the serializer write the file, then `--input` it.
5. Weigh one more cost before anchoring inline: when the base branch enables `required_conversation_resolution` and the workflow posting this review is forbidden from resolving threads (the automated review/address/verify loop is), every inline comment becomes a merge gate that only a human can clear. In that combination prefer marker-bearing review-body findings, which carry the same content and the same stable anchors for the follow-up workflows without leaving the PR `BLOCKED` after the findings are addressed. Say in the body why the findings are not inline, so the choice reads as deliberate. Anchor inline as usual when protection does not require resolution, or when the user will resolve threads themselves.
6. Submit `REQUEST_CHANGES` if there are blocking issues, `COMMENT` if the PR is draft, `APPROVE` if there are no blocking issues and the PR is merge-ready, otherwise `COMMENT`.
7. If you are the PR author, GitHub rejects `APPROVE` and `REQUEST_CHANGES`; submit `COMMENT` and include the same findings. Say another maintainer is required only when live GitHub state reports an approval gate. Report the account's inability to give a formal approval to the user rather than writing it into the review body — see the posted-body voice rule in the shared conventions; put it in the body only when a reader must act on it, and then name who and what.
8. If GitHub rejects the atomic POST with `Line could not be resolved`, re-read reviews and inline comments to confirm that no artifact was created, compare every proposed anchor with the exposed patch hunks, correct the invalid anchor or move that finding into the marked review body, rerun the live state/head/review preconditions, and retry once. This exception is only for that definite validation rejection; if the outcome is ambiguous, follow the shared conventions' [GitHub mutation-readback rule](../../gh-workflow-conventions/references/github-writes.md) instead. Report the exact error and stop for any other definite rejection or for a second failure.
9. After posting, verify submitted review state through `gh api repos/{owner}/{repo}/pulls/{number}/reviews --paginate`; `gh pr view --json latestReviews` can omit COMMENTED reviews, especially author COMMENT reviews. For inline comments, query GraphQL `reviewThreads`, match the posted comment ids, and inspect `path`, `line`, `originalLine`, and `isOutdated`. Do not infer an invalid anchor solely because the REST review-comments response returns `line: null` or `side: null`; it can do so for a valid current comment, while `isOutdated: false` and a resolved current GraphQL line confirm the anchor. After posting an `APPROVE`, also re-read `reviewDecision`, `mergeStateStatus`, and branch protection if the PR still appears blocked. Do not claim the approval satisfied branch protection solely because the review API returned `APPROVED`; if GitHub still reports `REVIEW_REQUIRED`, state that another eligible maintainer/account may be needed, especially when the reviewer also authored or pushed the latest changes. When the posted review contains inline comments and branch protection enables `required_conversation_resolution`, expect `mergeStateStatus` to flip to `BLOCKED` because of the just-created unresolved threads (see shared conventions); report thread resolution as the remaining merge gate, not an approval requirement. For the same reason, do not assert a pre-post merge state such as `CLEAN` as current inside a review body that adds inline comments — posting the review itself invalidates it. Re-read the PR `state` (not only `mergeStateStatus`) immediately before posting: a maintainer can merge concurrently while you review, and a review can land seconds after the merge. `mergeStateStatus: UNKNOWN` on an otherwise-ready PR is a hint that a merge (or recompute) just happened — check `state` for `MERGED`. If it merged during your review, keep the review but frame it as retrospective, and drop any "before merge" recommendation since that gate is already gone.
10. If the user asks to revise a review's verdict at the same head SHA (for example converting previously `Nonblocking`/`Question` findings into blocking, or otherwise changing `APPROVE`/`REQUEST_CHANGES`/`COMMENT`) without new commits to react to, do not try to edit or delete the earlier submitted review — a submitted (non-`PENDING`) review is immutable and dismissal only marks it `DISMISSED` without changing its content. Submit a new review with the updated `event` and the same `<!-- gh-review-pr:sha=... -->` sentinel, and open the body by linking to and stating it supersedes the prior review. GitHub computes `reviewDecision` from each reviewer's most recently submitted review, so the new one takes effect without needing to dismiss the old one.
