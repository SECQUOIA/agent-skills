# Review State And Setup Edge Cases

Part of **gh-review-pr**. Read only when setup encounters a scoped edit, repeat or prior review, changed head, author/draft/terminal PR, retrospective audit, findings limited by prior feedback, empty merge-base diff, or apparent line-ending churn.

## Scoped Source Edits

- If the same request also explicitly authorizes a scoped source edit, make only that edit on the verified PR head, append and push its commit under the shared conventions' [change-hygiene.md](../../gh-workflow-conventions/references/change-hygiene.md), then re-resolve and fetch the new head before selecting the reviewed SHA. Do not extend that authorization to defects discovered during review; those remain findings.

## Review History And Terminal State

- Exception: a *direct user invocation* of this skill against an already-reviewed head is itself the request for a new review — run the full review and post it, opening the body by stating it supersedes the prior review at the same head and keeping that head's sentinel. Do not stop to ask, and do not treat the earlier review's conclusions as settled: users deliberately run one head past several agents for an independent opinion, and a second pass overturning a "no actionable findings" verdict with blocking findings is the outcome that justifies the practice. Reach the prior review's text only after forming your own conclusions, so it cannot anchor them. Still ask first when the user constrained the output ("report back only", "don't post", "preview it") or when the request is ambiguous about a *verdict change* rather than a re-run. This exception is for a user typing the invocation; when an orchestrating workflow re-enters this skill in a loop, keep the duplicate-review stop in Setup step 4 of the core skill — those workflows rely on it to reuse the existing review instead of stacking duplicates.
- If the head SHA has advanced past a prior sentinel of yours (a re-review after new commits), review the new head rather than starting from scratch: diff your previously-reviewed SHA against the new head (`git diff <prior-sha> <new-head>`) to isolate the new commits and check whether they address your earlier findings, while still re-verifying the full changed-file set and re-running the relevant tests at the new head. An expensive validation from the prior head (a solver matrix, a long benchmark, a full notebook execution) may be carried forward instead of re-run when the delta to everything it exercises is proven semantically inert — for example a docstring-stripped AST comparison of the touched sources across the two heads; state the carry-forward and its proof in the posted review, and re-run whenever the comparison shows real behavior moved. Post a fresh review that reports which prior findings were resolved and carries the new head's sentinel. Re-read the PR description against those new commits as well: authors update code, docs, and CI but routinely leave the body's verification counts, platform/scope claims, and follow-up list describing an earlier head. Compare each claim in the body against what the head's own artifacts now say, and report a contradiction as a finding in its own right — the description is what readers see after merge, so a stale "only X is supported" line outlives the commit that made it wrong.
- When a PR has iterated through earlier review rounds — especially rounds where a reviewer asked to revert wording or "restore the previous text" — do not assume correctness fixes from earlier rounds are still present at the current head. Re-verify each earlier correctness change against the head you are actually reviewing: a broad revert can silently drop a correctness fix that shared lines with the reverted prose. This matters most when the head advanced (new SHA, added commits, or a base merge) since the prior review. Read what each earlier thread was actually resolved *with*, not just that it says "Addressed in `<sha>`": a thread closed by documenting a limitation — a docstring caveat, a note in the PR body — left the limitation in place, so judge that resolution on its merits rather than treating the thread as settled. It is legitimate to re-raise it with new evidence the earlier round did not have.
- A prior review of *yours* at the same head that carries no sentinel (posted by hand, or before this workflow existed) is not a duplicate-post gate — run the review and post normally. Its findings are still open, though, so re-verify each one against that head and carry the unaddressed ones into the new body with concrete drafted fixes, rather than silently dropping them or re-raising them as if new. Say that nothing was pushed since, so the author reads them as still-open items and not as a second opinion. First check whether such a review is really a review at all: GitHub records each inline thread *reply* as an empty-body COMMENTED review, so a batch of replies (for example an address pass answering threads, recognizable by `gh-arc:` markers in the reply bodies) shows up as several no-sentinel reviews of yours at the head. Those are transport containers, not prior findings — evaluate the replies as claimed fixes on their original threads instead of carrying the wrappers forward as open reviews.
- When the user asks for only findings other reviewers have not already raised, read every existing review body *and* every inline comment including replies, since a reply thread often records that an item was already fixed. Re-verify each prior finding against the current head rather than trusting its original text: one that is already resolved there must be neither re-raised nor silently dropped. Open the posted body by naming the prior findings you deliberately left out and their current status, so the omission reads as deliberate coverage rather than as a gap.
- If the current user is the PR author, still complete the normal maintainer review checks, then plan to post COMMENT; GitHub rejects author APPROVE and REQUEST_CHANGES. Do not infer that another maintainer approval is required from authorship alone; state it as required only when live GitHub state reports a review gate such as `REVIEW_REQUIRED` or branch protection requiring approval. Authorship is not the only conflict, and the other one has no mechanical guard: once you have pushed a commit to a PR that someone *else* authored — a scoped fix the same request authorized is the usual route — GitHub accepts your APPROVE normally, so nothing stops the account that wrote the newest commit from also clearing the gate on it. Name the commit and its size in the review body, and say so to the user before posting so they can choose whether you or another maintainer approves. Compare `user.login` on your own commits against the PR author rather than assuming the two roles stay separate across a long review loop.
- If the PR is draft, plan to post COMMENT unless there are blocking findings. Note what remains before it can be formally approved or merged.
- Read the PR `state` here, not just `mergeStateStatus`. If it is already `MERGED` or `CLOSED`, stop and report that — a review is retrospective at that point; do not run the full pipeline or post "before merge" advice as if the merge were still pending.
- If the user explicitly follows that stop by asking for a retrospective audit, keep it read-only: inspect the exact merged diff and linked context, record your own findings before reading prior reviews, then compare the two. Classify pre-existing or adjacent concerns separately; do not attribute them to the PR, post a formal verdict, or present already-moot advice as a merge gate.

## Merge-Base And Line-Ending Edge Cases

- An empty local merge-base diff while GitHub's file list still lists files is not the changed-file-set mismatch in Setup step 5 of the core skill: compare `git merge-base origin/<base> HEAD` with `HEAD`. When they are equal the head is already an ancestor of the base — the PR merged, or the base fast-forwarded past it — so re-read the PR `state` (expect `MERGED`) and stop under the merged-state rule above rather than re-fetching to "correct the base". This is easy to hit when a redo or re-review request lands after the PR merged between turns, since the earlier turn's `state: OPEN` no longer holds.
- When a hunk shows lines whose content looks unchanged, suspect end-of-line churn: a PR that writes LF lines into a CRLF file (or the reverse) rewrites untouched lines. Compare `git diff` with `git diff --ignore-cr-at-eol`, and count the file's CRLF versus LF-only lines at base and head. Report the EOL-normalized insertion/deletion counts as the real change, flag the churn `Nonblocking`, and suggest either a deliberate normalization commit plus `.gitattributes` or keeping the diff consistent with the file's existing endings.
