# Maintainability Review Rubric

Read this when judging whether the code a PR introduces or materially changes is well-structured, i.e. the "maintainability risks" part of the Review Standard. It is language- and repo-agnostic.

## Three binding rules

1. **The repo overrides.** A documented repository standard (`CONTRIBUTING`, style guide, linter config, established local pattern) always wins. Where the repo endorses something this rubric would flag, suppress the flag. Infer endorsement from the repo's *trajectory*, not from any single occurrence: one legacy call site is weak evidence against a recent maintainer-driven change that moved sibling code the other way (for example, a just-merged PR making internal keywords required), and suppressing a flag on the strength of the older pattern reproduces exactly what the maintainer is removing.
2. **Always a judgement call.** Every item below is a labelled heuristic ("possible Feature Envy"), never a hard violation. Map it to `Nonblocking` (or `Question`) severity by default; escalate to `Blocking` only when the smell also causes a correctness, security, or serious maintainability problem covered by the Review Standard.
3. **Skip what tooling enforces.** If a formatter, linter, or type checker already catches it, do not raise it in the review.

Apply the rubric only to what the PR introduces or materially changes, not to pre-existing code it merely touches.

## Smell baseline

Each entry reads *what it is* → *how to fix*. Match against the changed hunks.

- **Mysterious name** — a function, variable, or type whose name doesn't reveal what it does or holds. → rename it; if no honest name comes, the design is murky.
- **Duplicated code** — the same logic shape appears in more than one hunk or file in the change. → extract the shared shape and call it from both.
- **Long function / large change unit** — a unit doing too many things to hold in one's head. → decompose along the seams.
- **Feature envy** — a method that reaches into another object's data more than its own. → move the method onto the data it envies.
- **Data clumps** — the same few fields or parameters keep travelling together. → bundle them into one type and pass that.
- **Primitive obsession** — a primitive or string standing in for a domain concept that deserves its own type. → give the concept its own small type.
- **Repeated switches** — the same `switch`/`if`-cascade on the same type recurs across the change. → replace with polymorphism, or one shared map.
- **Shotgun surgery** — one logical change forces scattered edits across many files. → gather what changes together into one module.
- **Divergent change** — one file or module is edited for several unrelated reasons. → split so each module changes for one reason.
- **Speculative generality** — abstraction, parameters, or hooks added for needs the spec doesn't have, *including* a correct-but-broader construction that exceeds the change's stated scope/version assumptions or whose cost grows combinatorially where a bounded one would do. → delete it or defer to the version that needs it; inline back until a real need appears. (Escalate beyond the default when the over-broad surface would constrain future API/SemVer or ship a pathological cost.)
- **Redundant public interface** — two exported entry points (or keywords) doing roughly the same thing, or a superseded/experimental spelling kept "for compatibility" it does not yet owe (not present in any released version). → collapse to one; remove the superseded spelling while removing it is still free.
- **Divergent sibling vocabulary** — a second implementation of an abstraction the repo already has (another backend, adapter, driver, provider, exporter) names shared concepts differently from the sibling already in the tree (`onGPU` vs `device`, `bond_dim` vs `maxdim`, `num_sweeps` vs `iterations`), or configures itself in a different shape — one carrying its options as constructor fields where the established one forwards keywords. → use the existing sibling's name wherever a concept applies to both, and match its configuration shape, or rename both together in this change. Divergence here is not a local style choice: both spellings ship, callers switching implementations pay the difference forever, and it is effectively permanent once released. When the implementations genuinely need to differ, that is the signal to give the abstraction an explicit interface — an abstract supertype with a named contract the siblings implement — rather than letting two ad-hoc shapes accumulate.
- **Interior validation / eager collection** — argument checks, `collect`, or normalization performed inside inner or hot functions, repeating a contract that the public boundary or constructor should establish once. → validate and normalize at the boundary (or when building the return type) and let inner code assume the invariant. Defensive checks in the interior are cost and duplicated contract, not robustness.
- **Defaulted internal parameters** — keyword or optional-argument defaults on internal (unexported/private) functions, mirroring the ergonomics of the public API. → keep defaults only on the public entry points and make internal call sites pass every argument explicitly. Internal code needs no ergonomy: a default deep in the call stack is a silent decision that hides unintended-behavior bugs, while spelling the value out at the few internal call sites costs almost nothing.
- **Sentinel branching** — an absent-value sentinel (`nothing`/`None`/null, a magic value) threaded through the logic, forcing is-present branches at every use, where a neutral element of the operation (identity permutation, empty collection, zero offset, identity function) would let the general code path absorb the "absent" case with no branches. → represent "no-op" as the operation's identity element and delete the branches.
- **Implementation-detail documentation** — a docstring or user-facing doc that explains *how* the current implementation works, restates default language behavior, or lists what the code deliberately does *not* do. → keep docstrings to the what and why of the contract (signature, arguments, behavior, units); move how-notes to code comments or internal design docs, and simply omit non-actions. Text about internals goes stale silently and reads as contract to users.
- **Narrating or overclaiming comment** — a code comment that restates what the adjacent lines do ("the shift is added back to every reported energy"), or asserts a guarantee the author cannot defend ("never", "guaranteed", "only a cleanup"). → keep comments to the *why*, and scope every claim to what was verified, softening absolutes into the mechanism ("suppresses X" rather than "makes X impossible"). Cross-reference issues and PRs in source comments with full URLs rather than bare `#N`, which resolves only inside the forge UI.
- **Misplaced or over-coupled artifact** — a subordinate artifact (benchmark, example, demo, generated data, how-to prose) wired into a surface it should stay independent of: package tests tracking a benchmark, the package depending on its own examples, reference/how-to docs carrying benchmark results, or a module exporting names no caller uses. → give the concern its own home (a `benchmarks/`- or examples-style sub-project or environment that depends on the package as if it were external, with the package unaware of it) and export only what callers actually use. A test checks correctness and a benchmark measures speed — keep them from depending on each other.
- **Reinvented standard tooling** — a hand-rolled harness for a job the language ecosystem standardizes (benchmarking, property/fuzz testing, RNG/seed handling, argument parsing, data loading) or that the repo already exposes an API for. → use the standard package or the existing API. In particular, threading state a standard facility manages through every call site — for example passing RNG seeds by hand instead of seeding once at a boundary and letting the standard-library RNG flow — is bug-prone, not more controlled.
- **Overengineered test logic** — a test mixes randomized property checking with branches, search loops, or Boolean bookkeeping that selects its own boundary fixtures and obscures the invariant. → keep the randomized check branch-free and obvious; express cheap accepted/rejected boundaries as separate explicit unit cases, and rely on the test framework's RNG isolation unless randomness itself is the contract.
- **Silently permissive signature** — a public entry point with a catch-all parameter (`**kwargs`, `**_`, varargs, an untyped options bag/index signature) that absorbs and discards anything it does not recognize, so a caller's typo or an argument the previous implementation honored is dropped instead of rejected. Worst when the change narrows a wrapped or replaced API: the names the catch-all now swallows are real parameters callers may still pass, so the call silently produces a wrong request/result rather than an error. → drop the catch-all and let the language raise on unknown arguments, or reject explicitly, naming the unsupported one. Keep it only for genuine pass-through forwarding, where the arguments are handed onward untouched rather than dropped.
- **Message chains** — long `a.b().c().d()` navigation the caller shouldn't depend on. → hide the walk behind one method on the first object.
- **Middle man** — a class or function that mostly just delegates onward. → cut it; call the real target directly.
- **Refused bequest** — a subclass or implementer that ignores or overrides most of what it inherits. → drop the inheritance; use composition.
