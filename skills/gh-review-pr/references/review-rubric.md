# Maintainability judgment

Use for a structural concern introduced or materially changed by the PR. Repository policy and demonstrated direction take precedence; a legacy occurrence is weaker evidence than a deliberate recent migration. Skip formatter/linter findings already enforced. These are decision prompts, not a mandatory smell checklist or automatic demand for abstraction.

Raise a concern only with a concrete maintenance consequence. Default to Nonblocking or Question; use Blocking when design creates serious API debt, pathological cost, correctness risk, or violates an established architecture contract.

- Prefer a single coherent public contract. Check duplicated interfaces, unreleased aliases preserved without a compatibility obligation, sibling adapters with divergent shared vocabulary, or silently discarded catch-all arguments.
- Keep general APIs independent of backend details and subordinate examples, benchmarks, or generated content. Check whether new integration creates a real dependency cycle or prevents independent use; do not prohibit useful tests merely because benchmarks also exercise that behavior.
- Locate validation and derived values where their invariant is established. For thin forwarding wrappers, check whether the callee already enforces a required keyword before recommending repeated declarations or validation; retain explicit handling when the wrapper consumes it or owns a distinct contract. Repeated hot-path normalization, split-site adjustments, or defaulted internal options deserve attention when they hide actual decisions or measurable cost, not merely because a pattern exists.
- Avoid speculative abstraction and machinery for composable special cases. Existing ecosystem tools or a small repository-consistent operation may solve the same problem. Do not mandate a framework, class, or extraction solely to reduce repeated lines.
- Look for coupled edits, repeated switches, long multi-purpose functions, data clumps, inheritance without a coherent contract, and opaque naming when they make the changed behavior difficult to maintain. Name the concrete risk rather than reciting the smell.
- Keep docs/tests honest about their contracts. A test name is not coverage; read its assertion. Comments should explain a non-obvious reason or invariant rather than narrating code or overclaiming guarantees. User docs need observable behavior and units, not transient PR machinery. Quick starts should lead with a valid current usage; put migration details where existing users need them. Document the general operation at its public entry point and backend-specific behavior at the backend, consolidating duplicate prose. Avoid repeating signature mechanics unless they explain a consequential behavior.
- Prefer direct assertions and explicit boundary cases over tests that search for their own expected outcome. Preserve the framework's randomness/reproducibility contract instead of prescribing unnecessary RNG plumbing.

Recommend the smallest change that addresses the demonstrated concern. Check the compatibility and runtime cost of proposed alternatives. Existing approvals and a valid maintainer-prescribed follow-up can justify nonblocking deferral; do not trade a reviewed head for stylistic churn without a practical benefit.
