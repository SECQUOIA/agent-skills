# Testing and evidence in review

Read for test changes, disputed coverage, or behavioral claims based on validation. Use shared [test quality](../../gh-workflow-conventions/references/test-quality.md) for execution mechanics; read [mutation safety](../../gh-workflow-conventions/references/mutation-testing.md) only when a regression guard, disputed protection, or consequential uncertainty warrants a probe.

Choose checks for a claim and risk. Existing valid CI/local evidence can carry forward across irrelevant or inert changes; identify the source/head/environment and why the delta does not invalidate it. A new review round alone does not justify a full suite or mutation battery. Honor no-test instructions and state what static evidence cannot establish.

Coverage must preserve repository layer boundaries. A unit helper deliberately independent of backends need not import one to satisfy an end-to-end heuristic. Test the proper integration surface. Compare a claimed known solution with the soundness of returned results when both contracts matter; one does not prove the other.

For added tests, identify the distinct regression each guards against existing assertions. Prefer extending the established testset or fixture when it covers the same contract; avoid parallel suites that repeat successful solves for a narrow API change. Preserve new failure-path guards when consolidating redundant success cases. More assertions or another test file do not by themselves establish better protection.

For broadened types/domains, inspect the general dependency contract and representative boundaries. For classifiers or status normalization, test both error directions and ensure every predicate has the inputs it needs; rounded reported values can disagree with an authoritative dependency status. Check thresholds at production values, not only convenient test constants. Expected domain outcomes should follow the ecosystem's result/status convention; genuine contract violations need the appropriate error type.

For test-removal or replacement PRs, inventory removed tests and read their bodies before claiming coverage loss. Map consequential deleted guards to actual replacements. When warranted, disable the protected behavior in an isolated copy and verify the replacement fails for that defect; a stored output or an unexercised neighboring layer may not guard the edited source. Check a behavior-neutral change remains accepted when that is the cleanup's promise.

Investigate relevant skips, deselections, strict-mode suppressions, and unexpected migration warnings. For hardware-dependent tests, distinguish a useful optional check from coverage exercised by ordinary CI; a skipped branch proves neither support nor failure. Before prescribing a new hardware dependency or test lane, check its relevance to the PR and the repository's ability to run and maintain it. Do not generalize one repository's scope decision into a ban on hardware tests. A suppression can hide an unfixed artifact, but relabeling content that never satisfied the strict format may be correct. Check the final artifact or lane, not warning text alone.

Validate reported counts against the actual command/head/environment; internally inconsistent totals or a stale artifact are evidence questions. Optional dependency collection changes can explain different totals. Do not call a report false because your environment differs, or reconstruct every historical run unless that would resolve a consequential discrepancy. Probe the documented active environment before declaring an optional backend absent.
