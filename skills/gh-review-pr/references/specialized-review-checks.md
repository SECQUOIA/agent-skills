# Specialized Merge-Readiness Checks

Part of **gh-review-pr**. Read only for the changed artifacts and claims that match the categories below. Keep validation proportional to the PR and combine these checks with the core review standard.

- For notebook/output-refresh PRs, verify the PR body matches the current branch behavior, committed outputs, required credentials, and validation actually performed; stale PR metadata is review feedback even when code is correct. If full notebook execution fails outside changed hunks, distinguish a pre-existing or out-of-scope notebook failure from the PR's changed behavior and require a targeted reproduction for the changed cells before accepting the limitation.
- When a figure *is* the deliverable — a plotting/analysis PR, a paper-figure refresh, a parity or porting change claiming visual equivalence — neither the diff nor a green suite can see what the figure actually shows, so render it and interrogate the returned object instead of reading the plotting source: pull back legend label texts, tick labels, annotations, and each line's plotted arrays. Check the PR's own prose against that rendering rather than against the code, because a gated code path makes a false claim read as true in source — a README stating that some series' fit is omitted is confirmed by an exclusion branch that the caller never actually triggers (it sits behind a keyword the notebook does not pass), and only the rendered legend settles it. Watch specifically for an axis-transform change silently discarding out-of-domain points: switching an axis to log drops every zero or negative value, which is routinely the meaningful case — the exact-convergence events, a zero gap, a reference line at 0 — so count them (`(y <= 0).sum()` over each line's data) rather than eyeballing the image, since the loss is invisible in the diff and no test fails. For parity or porting PRs, compare the analogous source and target workflows end to end, including rendered notebook outputs and follow-on analysis cells; do not stop at checking that replacement APIs are present.
- For fixes to shared setup paths or repository-wide conventions in examples, notebooks, docs, or config files — especially claims that guidance is "canonical," "unique," or a single source of truth — search the whole repository for distinctive headings, phrases, and concepts across every artifact and language family, not only the named files or same-family siblings. Inspect each match for retained copies and stale or contradictory guidance. Flag a narrow fix or source-of-truth claim that leaves another active copy unless a regression test or explicit scope explains why it is correct.
- Test a clean merge result in a temporary worktree if the head lags the base or generated output depends on full-repo state; remove the worktree after. Treat this as required, not optional, whenever the PR deletes or renames a path — follow the merge-result verification bullet in the shared conventions' [references/worktrees-and-checkouts.md](../../gh-workflow-conventions/references/worktrees-and-checkouts.md), which covers probing conflicts with `git merge-tree --write-tree`, grepping the current base for consumers the diff cannot show, and why an import-time failure costs the whole test lane rather than one test.
- For PRs whose deliverable is *removing* tests — a test-suite cleanup, a de-duplication pass, a "replace snapshots with behavioral checks" refactor — the defect class is removed coverage, and it is invisible in the usual signals: the suite is green, CI is green, and the author's metrics (assertion ratios, line counts, test totals) are all reproducible. Reproducing those numbers is not the review. Diff the *test-name sets* between base and head (`git grep -h -oE "def test_[A-Za-z0-9_]+" <base> -- <tests>` versus the same at head, sorted, then `comm -23`; keep the character class case-insensitive, since a lowercase-only one truncates `test_knownRp_execution` to `test_known` on both sides and silently drops every camelCase removal from the inventory) and read the removed names for the ones that guard a safety, cost, credential, or fail-closed policy rather than pedagogy or prose. For each, find what at head still catches it and mutation-test that claim; a removed guard whose replacement you cannot name is the finding. Treat the name as a hypothesis about the body and open the deleted source before calling any coverage lost — the inventory method starts from names, so it feeds you exactly this error. A test named `test_higher_pressure_dries_faster` can assert only that both pressures completed drying, never the ordering its name promises, which makes an equivalent replacement look like a dropped monotonicity check; that finding reads as `Blocking` right up until the author quotes the deleted body back at you. Two traps recur. A replacement that asserts a *committed output* ("QPU execution is disabled" in a stored notebook/snapshot) does not cover a source edit that was never re-executed, because the artifact stays byte-identical — so mutate the source only, leaving outputs untouched. And a replacement one layer away (the build target refuses without opt-in) does not cover the layer the users actually run, so check whether CI or any documented command exercises that layer at all before accepting it. Prove both directions: the defect mutation red, and the behavior-neutral edit the PR promises to tolerate still green.
- For dependency or lockfile PRs, verify the exact resolved versions in the lockfile, import updated packages when practical, and run documented tests/notebooks that exercise the changed dependencies. For compat-only PRs, compare the changed bounds against the current base files and flag any silent narrowing of already-allowed compatible lines when issue or PR examples are stale. Report expected warnings without treating them as failures. When a PR renames or first-sets a published distribution name, advertises an install command, or merely curates published distribution metadata (project URLs, maintainers, classifiers) without touching the name, confirm the name is actually available or owned on the target index (PyPI/npm/crates; for PyPI, `https://pypi.org/pypi/<name>/json` returns 404 when unregistered and 200 when taken). An advertised `pip install <name>` (or equivalent) can silently install an unrelated project that already holds the namespace — and a PR that publishes an unreserved name in README, rendered docs, and an install guide opens exactly that window between merge and first release, so flag reserving it (a placeholder upload) or tracking it in an issue. A rename also needs a migration step whenever the *import* name stays the same: package managers do not treat the new distribution as superseding the old one, so an environment holding the old name ends up with two records owning the same files, and uninstalling the new one can leave the stale record reporting an installed package whose import fails. Reproduce that upgrade path in a throwaway environment (install the merge-base, then the head, then uninstall) instead of reasoning about it, and require the install docs to carry an explicit uninstall-first step.
- When a rename or any manifest edit lands alongside a committed lockfile, confirm the lockfile was regenerated to match — a frozen/locked install (`pip install --locked`-style, `pixi install --locked`, `cargo build --locked`, `npm ci`) fails when lock and manifest diverge, so run it rather than trusting the committed lock. That check, and green CI, still answer only whether the lock *matches the manifest*, not whether its resolved content is sound. In a lockfile that mixes ecosystems (conda plus PyPI, system plus language packages), check whether any package resolves **twice** into one prefix from both sides: it happens when the entry on one side carries no cross-ecosystem mapping (for example `purls: []` on a freshly built conda package), so the other resolver satisfies the same requirement with a second artifact that then overwrites the first in place. Two builds of a compiled library stacked in one environment still import and still pass every test, so nothing but the lock content reveals it. Re-solve the same manifest with a current tool and diff against the committed lock; entries the re-solve drops, or mappings it fills in, are the evidence. Report the lock/manifest result and the resolved-content result separately, since the first can be green while the second is wrong.
- For security-alert remediation PRs, read the alert/advisory metadata and verify whether a patched version exists. If no patched version exists, verify that the vulnerable package path is removed or no longer locked/installed, that docs explain any intentionally unsupported optional path, and that a regression check prevents quiet reintroduction.
- For generated sites/docs, build the output and run a local-link/resource sanity check that respects generated base paths; include syntax checks for shipped JS/assets when applicable. Inspect the built markup itself, not only links and the one structure you set out to audit: grep the generated HTML for source that leaked through as literal text — `&lt;` where a tag should be, or a `<pre>`/`<code>` wrapping content meant to render — across the regions the PR restructured. Markdown engines branch on what a block *starts* with, so changing the first line of a cell or file can silently turn the rest of it into an escaped or indented-code block while every heading assertion you were checking still passes. Source-level tests cannot see this at all; only the built artifact shows it.
  If local build dependencies are unavailable but GitHub checks already ran the authoritative generated-site build for the same head, use targeted static checks plus the GitHub check result instead of spending time repairing the local system environment, unless a suspected issue specifically requires local reproduction.
  For GitHub Pages PRs, verify the intended deployment owner and canonical Pages URL. If the PR body advertises a fork or preview URL, make sure it is labeled as a preview or updated to the post-merge repository URL so reviewers do not confuse a fork Pages site with the upstream deployment.
- For LaTeX/manuscript PRs, compile the document (for example `pdflatex` + `bibtex` + reruns) as the merge-readiness check, and treat undefined references/citations and any mismatch between an `\includegraphics` filename and its caption or surrounding text (an embedded figure that plots a different case than the caption claims) as review findings, not cosmetic. Cross-check numeric claims against the figures/tables actually included rather than the prose alone. When the PR regenerates data-derived inputs (tables, figures, generated sections), enumerate every file the document `\input`s or includes and inspect the narrative fragments *absent from the diff* whose data sources changed: hand-written prose beside regenerated tables is where the compiled document contradicts itself (a prose file quoting the previous generation's reference optimum next to a table showing the new one), and a clean build hides it because both halves compile. When prose states an indexed recurrence or derived relation but the implementation special-cases the first or last index, require the manuscript to state the relation's index domain and boundary convention or write it piecewise; a term such as `x_{n+1}` is undefined at the final index without one. A diagram the document *builds* — a `tikzpicture`, a `pgfplots` axis — has no image filename to cross-check and emits no warning when its nodes collide, so apply the figure-is-the-deliverable rule above to the page itself: rasterize it (`pdftoppm -png -r 150 -f <page> -l <page>`) and look. A node placed relative to a wide sibling can land on top of an unrelated box with both texts illegible while `latexmk` reports zero overfull boxes and the whole suite passes, and a PR body's "visually inspected" list routinely enumerates the tables and omits the one figure whose layout changed. The finished PDF's navigation and font layers are part of the deliverable and are equally invisible to source review and to a green build: dump the outline destinations (`pypdf`'s `get_destination_page_number`) and confirm every bookmark lands on the section it names, check that floats sit on the side of a heading the prose assumes (`pdftotext -f <page> -l <page>`), and treat a Type 3 plot font as a submission defect journals reject rather than only the text-extraction hazard the shared conventions' [test-environment.md](../../gh-workflow-conventions/references/test-environment.md) describes. Two anchor bugs produce the navigation case and neither fails anything: a counter reset without a matching `\theH...` namespace points a whole appendix's bookmarks at main-text pages, and an anchor is written when its environment *opens*, so a `\renewcommand` inside the body is already too late — scope it around the environment instead. Read the warnings off the final `.log` the build leaves behind rather than off `latexmk`'s stdout, which interleaves every pass: the undefined citations of run 1, all resolved once BibTeX has run, otherwise read as a list of findings that does not exist in the finished document. That log is also the only build-time trace of those anchor collisions (`destination with the same identifier ... has been already used`), and it wraps long identifiers across lines, so join continuations before extracting names — a truncated stem reads as a different, entirely plausible anchor. And a warning present at head is a finding only once the *base* builds without it, so compile the merge base too before calling an overfull box a regression — that comparison is what separates a cosmetic remark from a defect this PR introduced, and it is also what catches a PR body claiming a clean build. For build-environment package gaps such as a missing document-class package, follow the shared conventions' [test-environment.md](../../gh-workflow-conventions/references/test-environment.md).
- For PRs that generate an input file consumed by an external solver or tool (a GAMS `.gms`, an LP/MPS or other model file, a generated CLI/config), a test that only asserts the expected lines appear in the written text does not prove the tool accepts the file: it can be emitted yet fail to compile or solve (for example priority `.prior` assignments written for variables the writer later eliminates, which pass a unit suite but break GAMS compilation). When a local instance of the target tool is available, run the generated artifact through it end to end. The tool may be installed outside `PATH`, so probe it through the project's own driver (for example Pyomo `SolverFactory("gams").available()`, which finds a GAMS install under a package directory) before concluding it is unavailable, and note when a subsolver path could only be validated from the author's own run because a local sublicense (for example GAMS/Gurobi) was missing.
- For PRs that add or swap an optimization/solver backend behind an adapter (or any thin wrapper that reads specific fields off a third-party result object — an SDK response, an HTTP client, a solver `Results` object), verify the adapter against the pinned dependency's *actual* result object rather than trusting the field names: a small probe against the locked version (one real solve/call) confirms the captured status/termination mapping, objective, timing, and version accessors exist and return sane values, because a mistyped attribute or an unmapped status surfaces only when that untested branch runs. Separately confirm the failure contract: the adapter must not expose a partial, stale, or non-optimal result as a success — it should load/return values only after a success/optimal termination and reject missing, non-finite, or materially out-of-range extracted values — and the public result type and report output must stay backend-independent (no solver object leaking through the general API). Reproduce any published reference result the PR claims to preserve, and when the underlying problem is degenerate (alternate optima), check the tie-break is a documented deterministic rule rather than incidental solver ordering.
  Check the *request* direction the same way, which matters most when the repo ships its own reimplementation of a vendor client rather than depending on it (a bundled SDK subset, a hand-rolled REST bridge — often declaring the version it mirrors, e.g. a `__..._parity_version__` constant). Do not read the two implementations side by side: install that exact upstream version into a scratch environment and diff the *generated payload* for every supported call. Include a call that should match as a positive control, since a divergence is only decisive once the sibling path is byte-identical. The defect this catches is a field the vendor never sends being added for one device, endpoint, or job type — the vendor's own builder is the executable spec for which keys each one accepts. Nothing else in the review sees it: no offline test can, the PR's tests typically assert the new payload as correct, CI stays green, and it reaches the provider on every production call of that kind. When you cannot reach the live service to settle it (no credentials, a forbidden device), the vendor-parity diff *is* the evidence — say so, and treat an unexplained deviation from it as `Blocking` rather than deferring to the author's intent.
- For PRs whose deliverable is a table of reproducible results (a benchmark campaign, a solver comparison, a generated results document), the load-bearing question is whether the *method* reproduces, not only whether the code runs — and two environment differences routinely fake a finding, each of which publishes a wrong claim under your name. When a licensed component blocks a run, check whether it sits in a *configurable* slot before recording the lane as unvalidatable: a master or sub-solver named by a CLI flag or a config default can be swapped for one you are licensed for, which turns "I could not validate this" into both a reproduction and a concrete portability finding about the hardcoded default (a CPLEX master default failing with a solver error, where `--master-solver-name gurobi` then reproduced every published row, is the shape of it). And treat timing- or limit-derived outcomes as load-sensitive: a run that hits its time limit on a busy machine can finish well inside it when idle, so re-run before reporting that a published time or iteration count fails to reproduce. Reproduce enough rows to support the verdict — one reproduced row is not the table — and say which rows you covered, under which solver stack and machine state.
- For PRs that vendor or derive code from another repository and cite a pinned revision as the implementation source, verify the pin by diffing the shipped file against that exact revision (fetch it raw by SHA) rather than checking that the link resolves. A pin chosen as "current upstream main" routinely postdates an upstream refactor of the same file — the citation then names a revision whose implementation differs from the shipped one, and a regression test asserting the pin string cements the error. When the diff is substantive, walk the file's upstream history (`gh api 'repos/OWNER/REPO/commits?path=<file>'`) to find the revision that actually matches, and prescribe repinning to it with deliberate local deviations noted beside the citation. Verify cited upstream PR/issue identities separately: query `repos/OWNER/REPO/issues/<N>` and inspect whether `.pull_request` exists, then use `repos/OWNER/REPO/commits/<sha>/pulls` to bind the pin to the PR that carried it. A commit subject such as `Fix ... (#63)` can name a tracking issue while the implementation merged through another PR, so a correct SHA does not make an incorrect PR attribution harmless. Cross-check values inherited from the upstream docs the same way: a "best known" objective or size table copied from the source repo must not contradict the PR's own committed artifacts — a best-known value better than every proven-optimal bound in the committed results is internally inconsistent, and the repo's own regenerated artifacts win.
- For PRs that add or edit a repository policy or planning document (`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING`, `PLANNING`/`RELEASING`, a style guide, agent instructions), check the three things the diff cannot show. For an agent-instructions file specifically (`AGENTS.md`, `CLAUDE.md`, `.cursorrules`), settle whether the repository wants one *at all* before reviewing its content: maintainers commonly class it with `.vscode` or editor dotfiles as personal development tooling that does not belong in shared infrastructure, and decline to maintain another contributor's agent configuration. Search closed PRs and issues for a prior refusal before treating the file as welcome; where the repo has already turned one down, the finding is that it is being added again rather than how it is written, and the fix is to keep it in the contributor's own ignored local config. First, every artifact the policy references must exist and match the repo: run the documented commands, and compare named test markers, environment names, file paths, and relative links against the tree (a marker list against `pytest.ini`, a `.github/`-relative link resolving to `../AGENTS.md`), including — for a Markdown policy — its own table-of-contents anchors against its headings, since GitHub's slug drops backticks and punctuation. Second, review it for *omissions* — a policy's defects are mostly what it leaves out — by checking it against the failure modes this repo has actually paid for: its recent fix PRs, open issues, and prior review threads. Propose each missing rule as drafted replacement text, not as "consider documenting X". Apply the redundant-interface lens to the entry points too: do not ask for another adapter file when a tool already reads the canonical one natively (Codex reads `AGENTS.md`), but do ask the document to say so, since an unexplained gap invites someone to add the redundant file later.
  Third, a policy binds the humans who must follow it, so check that they can actually read it — a document only an agent can parse fails at its stated purpose. The mechanical version of this check: for every term the document uses in a *normative* position (a gate, a promotion rule, an entry/exit criterion), confirm it is defined in the document or in a repo file it links. An undefined gating term is a finding at the severity the gate warrants, not a style nit, because a gate nobody can define cannot be walked; the usual tell is a term used several times in several spellings ("smoke/validation suite", "smoke/numerical suite", "smoke-install job") that `git grep` finds nowhere else in the repo. Judge the vocabulary against the audience the repo actually has: project-management and release-engineering idiom ("lazy consensus", "WIP limit", "burn down", "commitment unit", "DOI'd") is not common knowledge on a research or domain-science team. Ask for a one-line definition on first use or a short glossary rather than rewriting the author's model, and cite the document's own good examples when it has them — a term already defined parenthetically, or a terminology table it added for something else — so the ask is a pattern to extend rather than a matter of taste.
- For PRs that split an always-loaded instruction file into conditionally loaded parts — a progressive-disclosure refactor of a skill, an `AGENTS.md`/`CLAUDE.md` policy split, a runbook or docs extraction — the defect is a rule that survives the move but stops being reachable where it is needed, and the checks a reviewer naturally runs all come back green: nothing was deleted, every relative link resolves, and each relocated rule has a trigger. Verify preservation mechanically instead of by reading — split the pre-change file into clauses, search each verbatim across the post-change file set, and account for every non-match as relocated, reworded, or deliberately dropped; on a several-hundred-clause split, reading both sides and calling it complete is how a silent drop ships. Then audit routing by *action* rather than by rule: walk the workflow's own sequence and ask at each step which reference that step needs and whether the file being read *at that moment* names it. Rule-indexed checking cannot find this, because a rule can be correctly triggered from a file the agent never opens at that step — the recurring shape is a procedure moved into a reference that never mentions the shared write-safety rules its own step depends on. Three defects recur and each looks like a clean diff: an unconditional duty that gains a trigger and becomes conditional; an instruction that stops before the routed exception qualifying it can be consulted; and a deictic ("above", "step 4", a renamed section) whose referent stayed behind. Apply the same test to the split's own new categories — one with no trigger in the always-loaded file is unreachable however well written.
- For CI/workflow changes, cheaply verify referenced external action/tool versions exist and check `GITHUB_TOKEN` permissions/event triggers for unnecessary write scope or secret exposure. Flag by name the canonical injection pattern: a workflow on `pull_request_target` (or `workflow_run`) that checks out the PR head ref and then executes contributor-influenced code — build steps, tests, install scripts, or even linters reading config from the checkout — since those triggers run in the base repository's context with secrets and a write-capable token that a plain `pull_request` trigger never gets. Require the privileged trigger to keep the checkout inert (metadata-only, or explicitly pinned to the base ref), split the work into an unprivileged run-and-upload workflow plus a privileged consume-artifact workflow, or gate execution behind an explicit trust label before treating the workflow as safe. When a workflow change renames jobs, runner labels, or status contexts, compare branch-protection required checks against the PR's current check names and flag stale required contexts as merge-readiness feedback.
- For Dependabot-configuration changes, compare configured update directories against checked-in package/project manifest directories, verify grouped update names/cadences are coherent, and flag omitted active project directories or non-existent configured directories unless the PR explains the exception.
- For citation-metadata files (`CITATION.cff`), validate with `cffconvert --validate` rather than only eyeballing the YAML, since the acceptance bar is usually schema validity; the tool is not always in the project environment, so install it into a scratch venv when absent. Structurally-valid YAML is not proof of a valid CFF. Separately judge whether the `authors:` roster matches what the PR/issue claims (for example a full team versus only the verified contact), and flag an under-filled roster as review feedback.
