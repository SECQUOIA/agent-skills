# GitHub Maintainer PR Review

## Overview

Use this workflow to perform and post a maintainer-quality PR review.

Follow the shared **gh-workflow-conventions** (read the sibling `gh-workflow-conventions/SKILL.md`): gh-only tooling and `--json` fallback, PR/repository resolution across remotes, terse invocation shorthand, untrusted-text handling, network/filesystem escalation and bounded watches, CI-after-push polling, active test environment, commit/push hygiene, and concise tone. This file covers only what is specific to posting a maintainer review.

## Setup

1. Resolve the PR (see shared conventions for URL/number/branch and multi-remote resolution).
2. Fetch the PR base branch and head with `git` so the local checkout is fresh.
3. Read PR metadata and diff through `gh pr view`, `gh pr diff`, and `gh api`.
4. Determine the head SHA and current GitHub user early. List existing reviews; if one by you already contains the exact sentinel `<!-- gh-review-pr:sha=<HEAD_SHA> -->`, stop before running expensive checks and report the existing review id/state.
   - Exception: if the user explicitly asks to redo the review despite an existing one for the current head SHA, run the full review again before deciding whether to post. If the request does not clearly say to post a second review to GitHub (for example "do the review again" without mentioning posting), ask whether they want the re-analysis reported back only or an actual duplicate GitHub post before posting — posting a review is a visible, hard-to-reverse action distinct from re-running the checks. Skip the confirmation only when the request already says to post/submit/resubmit again.
   - If the head SHA has advanced past a prior sentinel of yours (a re-review after new commits), review the new head rather than starting from scratch: diff your previously-reviewed SHA against the new head (`git diff <prior-sha> <new-head>`) to isolate the new commits and check whether they address your earlier findings, while still re-verifying the full changed-file set and re-running the relevant tests at the new head. An expensive validation from the prior head (a solver matrix, a long benchmark, a full notebook execution) may be carried forward instead of re-run when the delta to everything it exercises is proven semantically inert — for example a docstring-stripped AST comparison of the touched sources across the two heads; state the carry-forward and its proof in the posted review, and re-run whenever the comparison shows real behavior moved. Post a fresh review that reports which prior findings were resolved and carries the new head's sentinel. Re-read the PR description against those new commits as well: authors update code, docs, and CI but routinely leave the body's verification counts, platform/scope claims, and follow-up list describing an earlier head. Compare each claim in the body against what the head's own artifacts now say, and report a contradiction as a finding in its own right — the description is what readers see after merge, so a stale "only X is supported" line outlives the commit that made it wrong.
   - A prior review of *yours* at the same head that carries no sentinel (posted by hand, or before this workflow existed) is not a duplicate-post gate — run the review and post normally. Its findings are still open, though, so re-verify each one against that head and carry the unaddressed ones into the new body with concrete drafted fixes, rather than silently dropping them or re-raising them as if new. Say that nothing was pushed since, so the author reads them as still-open items and not as a second opinion. First check whether such a review is really a review at all: GitHub records each inline thread *reply* as an empty-body COMMENTED review, so a batch of replies (for example an address pass answering threads, recognizable by `gh-arc:` markers in the reply bodies) shows up as several no-sentinel reviews of yours at the head. Those are transport containers, not prior findings — evaluate the replies as claimed fixes on their original threads instead of carrying the wrappers forward as open reviews.
   - When the user asks for only findings other reviewers have not already raised, read every existing review body *and* every inline comment including replies, since a reply thread often records that an item was already fixed. Re-verify each prior finding against the current head rather than trusting its original text: one that is already resolved there must be neither re-raised nor silently dropped. Open the posted body by naming the prior findings you deliberately left out and their current status, so the omission reads as deliberate coverage rather than as a gap.
   - If the current user is the PR author, still complete the normal maintainer review checks, then plan to post COMMENT; GitHub rejects author APPROVE and REQUEST_CHANGES. Do not infer that another maintainer approval is required from authorship alone; state it as required only when live GitHub state reports a review gate such as `REVIEW_REQUIRED` or branch protection requiring approval.
   - If the PR is draft, plan to post COMMENT unless there are blocking findings. Note what remains before it can be formally approved or merged.
   - Read the PR `state` here, not just `mergeStateStatus`. If it is already `MERGED` or `CLOSED`, stop and report that — a review is retrospective at that point; do not run the full pipeline or post "before merge" advice as if the merge were still pending.
   - If the user explicitly follows that stop by asking for a retrospective audit, keep it read-only: inspect the exact merged diff and linked context, record your own findings before reading prior reviews, then compare the two. Classify pre-existing or adjacent concerns separately; do not attribute them to the PR, post a formal verdict, or present already-moot advice as a merge gate.
5. Diff against the merge-base. Verify that the changed-file set from your local diff (`git diff --name-only $(git merge-base origin/<base> HEAD) HEAD`) equals `gh pr diff --name-only`; treat line totals as advisory only, since context and whitespace can differ. On a file-set mismatch, re-fetch base and head and recompute once. If the sets still differ, do not post a review — stop and report the discrepancy (the files present on only one side) so the base can be corrected.
   - An empty local merge-base diff while `gh pr diff --name-only` still lists files is not the base-correction mismatch above: compare `git merge-base origin/<base> HEAD` with `HEAD`. When they are equal the head is already an ancestor of the base — the PR merged, or the base fast-forwarded past it — so re-read the PR `state` (expect `MERGED`) and stop per step 4's merged rule rather than re-fetching to "correct the base". This is easy to hit when a redo or re-review request lands after the PR merged between turns, since the earlier turn's `state: OPEN` no longer holds.
   - When a hunk shows lines whose content looks unchanged, suspect end-of-line churn: a PR that writes LF lines into a CRLF file (or the reverse) rewrites untouched lines. Compare `git diff` with `git diff --ignore-cr-at-eol`, and count the file's CRLF versus LF-only lines at base and head. Report the EOL-normalized insertion/deletion counts as the real change, flag the churn `Nonblocking`, and suggest either a deliberate normalization commit plus `.gitattributes` or keeping the diff consistent with the file's existing endings.
6. For first-time contributors or otherwise untrusted external contributors, complete a static safety pass before executing any contributor-controlled code. Inspect changed files and metadata for execution hooks, workflow changes, package-manager scripts, generated binaries, dynamic import/eval/exec, shell/subprocess use, filesystem or network access, environment/secret reads, and test hooks such as `pytest_plugins`, `conftest.py`, fixtures, and `autouse`. If the pass finds a credible injection or supply-chain risk, do not run the PR code; continue with static review only and state the risk clearly.
7. Review the PR head in a clean tree. If unrelated local artifacts make the shared checkout dirty, use a temporary worktree at the PR head for inspection and tests, then remove it before finishing. When running containerized validation against a temporary worktree, run the container as the host user or otherwise ensure generated files can be removed during cleanup. Flag only issues introduced or materially changed by this PR, not pre-existing code it merely touches.

## Review Standard

Inspect the diff, surrounding code, tests, docs, and repository conventions for:

- correctness bugs and regressions
- missing tests for changed behavior
- public API, CLI, UX, or documentation inconsistencies
- maintainability risks that matter to future maintainers
- security or data-safety issues
- design and scope: whether the change *should exist as written*, not only whether it works — minimal public surface (no second interface doing roughly what an existing one does; a superseded/experimental spelling not yet in any released version is debt to remove now, not compatibility to preserve), staying within the repo's stated version/scope assumptions (e.g. "v1" contracts), keeping layer boundaries clean (a general/interface-level function must not encode downstream/backend specifics in its code or docs), and avoiding constructions whose cost grows combinatorially when a bounded one exists.

Correct, tested, and green is necessary but not sufficient. A maintainer also asks "is this the right change for where the codebase is going?" — and blocks correct code on design or scope grounds when it adds interface debt, exceeds the stated version scope, leaks backend concerns into a general layer, pushes validation/normalization into inner or hot paths instead of doing it once at the public boundary or constructor, couples a subordinate artifact (benchmark, example, script, generated data) into a core surface — package tests, dependencies, or published/reference docs — that should stay independent of it, reinvents a standard ecosystem tool (or an API the repo already exposes) instead of using it, builds in a feature users can already compose from the public API (a loop around an entry point, a callback hook covers saving/monitoring/restarts — prefer the general hook over the baked-in special case), or invests in machinery that cuts against the package's stated core value proposition (for example a CPU-bound sub-solver in a package whose selling point is GPU execution). Surface these as first-class findings at the severity a maintainer would assign; do not downgrade them to `Nonblocking` merely because the code passes tests. When you catch yourself concluding "works, only nits," recheck the change against this design/scope lens before finalizing.

When judging maintainability, apply the code-smell baseline in [references/review-rubric.md](references/review-rubric.md); read that file for the smell list and the rules that keep it from producing noise (repo standards override, smells are judgement calls, skip anything tooling enforces).

Calibrate generic coverage and mutation heuristics against verified repository intent before turning them into findings. Maintainer guidance in the linked issue or prior review that assigns a file or layer a narrow role — for example, interface infrastructure that must remain independent of concrete backends — is a design boundary when it matches the repository's organization. Do not restore an integration path inside that unit merely because end-to-end coverage would be useful; check the appropriate integration-test surface instead, and report a genuine suite-level gap without prescribing a fix that violates the boundary.

For randomized tests, first distinguish property testing from unit testing. Keep a property test direct: sample inputs and assert the invariant without search-until-boundary loops, outcome bookkeeping, or branches that manufacture a deterministic accepted/rejected pair. Put cheap boundary examples in separate explicit unit tests. Use complex mutation probes as private review evidence when useful, but treat a surviving mutant as evidence of a missing defect class, not as a mandate to ship the probe's machinery. Before designing any mutation battery — whether to find a defect or to validate a guard you are about to prescribe — read the shared conventions' [references/test-quality.md](../gh-workflow-conventions/references/test-quality.md). Its mutation rules are load-bearing here, not background: they name the defect classes one probe per test misses, and the ways a source-level guard stays green while the policy it claims to protect is gone. Reaching them through the conventions' pointer only after the review is posted is too late. Respect the test framework's reproducibility contract; in Julia, `@testset` copies and restores the task's default RNG, so do not require an explicit per-helper RNG merely for reproducibility or testset rearrangement. Require explicit RNG control only when randomness itself is under test, the framework cannot reproduce failures, or repository convention calls for it.

Do not treat deterministic known-solution membership and sampled-result validity as substitutes. `known_solution in result` checks that one expected solution is represented; checking a sampled result against the valid set, feasibility predicate, and domain checks that returned values are sound. When both contracts matter and the problem is cheap and small, preserve both. Do not replace the sampled assertion with feasibility or domain checks on a hand-picked expected value.

Do not flag a test utility solely because it currently has no callers when verified maintainer intent preserves it for future test construction. Judge whether its behavior and usage are stable and documented instead. Keep docstrings to current behavior and how to call the utility; do not ask them to encode transient call counts, PR rationale, or future plans that can silently drift.

Verify behavioral claims by running commands, imports, tests, or entry points when practical; run at least the targeted changed-behavior test locally when cheap, and scale broader local validation to risk (active-environment and license-probe escalation are in the shared conventions). For PRs from untrusted authors, run contributor-controlled code only in an isolated environment; if isolation is unavailable, review statically and say why.

When a PR widens an input range (a new domain, dimension, type, or value set), check the *general* case against the underlying framework/dependency contract, not just the exercised happy path: confirm the library actually defines the operator/state/method for every value the change now admits (and that the tests cover the extremes, not one interior example). "The added test passes" answers a narrower question than "does this hold across the range it now claims to support."

When a change reports an expected domain outcome — an infeasible model, a non-converged solve, a failed fit — check how it is surfaced against the ecosystem's convention, not just that it is surfaced. Solver and fitting ecosystems report such outcomes as a status/termination field on the result with diagnostics as logs; raising an exception there breaks caller composition (every solve needs a try/catch) and diverges from what users of sibling tools expect. Reserve exceptions for contract violations, and when code does throw, require the semantically correct exception type — callers catch by type, so an overflow raised as an argument error (or vice versa) is a real defect, not a style nit.

When a PR adds a layer that *corrects* a dependency's own status, classification, or validity verdict — normalizing a solver termination, re-deriving a gap or tolerance, overriding an SDK's success flag, tightening a parser's accept decision — review it as a two-sided classifier. The PR was written to fix one error direction, so its tests and its description only exercise that direction; the review's job is the other one. Ask specifically where the new rule over-rejects: a result the dependency itself declared valid that the layer now downgrades. That case is easy to miss because it usually still looks green — the suite passes and the artifact is merely relabelled — while the mislabel ships into whatever the layer feeds (a published table, a report, a downstream branch). Re-deriving a quantity from *reported* values and comparing it against the dependency's *own* threshold with no slack is the recurring shape: reported bounds, timings, and estimates are rounded on the way out, so a solve that legitimately met a `1e-6` tolerance can recompute to `1.0019e-6` and be overturned. Prefer trusting an explicit raw status where the dependency provides one, and reserve the re-derived check as the fallback for results that carry no such status.

The tests are where this defect announces itself. When a test pins a threshold, tolerance, or version constant *just* past the value the shipped code uses — asserting at `1.1e-6` what production runs at `1e-6` — treat that gap as evidence the shipped value fails on the very case the test names, not as an incidental choice. Re-run the assertion at the production constant before accepting the test as coverage; if it goes red, the test documents the boundary rather than covering it, and the finding is in the code, not the test. Say so explicitly in the review, since the author's fix must change both.

When a PR turns on a strict mode — warnings-as-errors (`-W`, `-Werror`, `fail_on_warning`), `--strict-markers`, a new lint or type gate — inspect *how* each pre-existing diagnostic was cleared, not just that the build is now green. Suppressing rather than resolving keeps (or publishes) the very artifact the diagnostic identified: marking an empty document `:orphan:`, adding an unreferenced file to an index to satisfy an "not included" warning, a `# noqa`, a widened ignore list. Grade those at the severity the surviving artifact warrants. Before calling a relaxation a workaround, though, confirm the artifact could actually satisfy the stricter setting — a snippet relabelled from `json` to `text` because its "values" are prose placeholders was never valid JSON, so the relabel is the correct fix and reporting it would be wrong. Build the artifact and inspect the generated output, not only the source.

When a PR has iterated through earlier review rounds — especially rounds where a reviewer asked to revert wording or "restore the previous text" — do not assume correctness fixes from earlier rounds are still present at the current head. Re-verify each earlier correctness change against the head you are actually reviewing: a broad revert can silently drop a correctness fix that shared lines with the reverted prose. This matters most when the head advanced (new SHA, added commits, or a base merge) since the prior review. Read what each earlier thread was actually resolved *with*, not just that it says "Addressed in `<sha>`": a thread closed by documenting a limitation — a docstring caveat, a note in the PR body — left the limitation in place, so judge that resolution on its merits rather than treating the thread as settled. It is legitimate to re-raise it with new evidence the earlier round did not have.

After local validation, inspect changed areas for ignored disposable artifacts created by the check itself, such as Python `__pycache__/` directories from workflow tests. Clean safe test caches before posting the review, or report any generated residue that cannot be removed safely.

When a relevant test run reports skipped or deselected tests, inspect the skip reasons and pytest marker/filter config (for example with `-rs` and `--collect-only`). Compare default collection with a relevant marker override when useful (for example `--collect-only -m ""`), then run issue-relevant marker groups such as `slow`, integration, or backend-specific tests before posting the review, or explicitly state why they were not run.

For API migration or deprecation PRs, treat unexpected warnings in targeted tests as review signal. Promote relevant warnings to errors when practical, and prefer updating incidental legacy test call sites over documenting warning noise. Treat cache/write warnings caused by sandboxed paths outside the repository as environmental noise only when tests otherwise pass and the warning cannot affect the behavior under review; still report them in the review summary.

## Merge-Readiness Checks

Keep extra validation proportional to the PR. When relevant:

- For notebook/output-refresh PRs, verify the PR body matches the current branch behavior, committed outputs, required credentials, and validation actually performed; stale PR metadata is review feedback even when code is correct. If full notebook execution fails outside changed hunks, distinguish a pre-existing or out-of-scope notebook failure from the PR's changed behavior and require a targeted reproduction for the changed cells before accepting the limitation.
- For parity or porting PRs, compare the analogous source and target workflows end to end, including rendered notebook outputs, follow-on analysis cells, and visualization semantics. Do not stop at checking that replacement APIs are present if the PR claims behavioral or visual parity.
- For fixes to shared setup paths or repository-wide conventions in examples, notebooks, or config files, inspect sibling artifacts in the same family. Flag PRs that fix only the named files without a regression test or a clear reason the narrower scope is correct.
- Test a clean merge result in a temporary worktree if the head lags the base or generated output depends on full-repo state; remove the worktree after. Treat this as required, not optional, whenever the PR deletes or renames a path — follow the merge-result verification bullet in the shared conventions' [references/worktrees-and-checkouts.md](../gh-workflow-conventions/references/worktrees-and-checkouts.md), which covers probing conflicts with `git merge-tree --write-tree`, grepping the current base for consumers the diff cannot show, and why an import-time failure costs the whole test lane rather than one test.
- For PRs whose deliverable is *removing* tests — a test-suite cleanup, a de-duplication pass, a "replace snapshots with behavioral checks" refactor — the defect class is removed coverage, and it is invisible in the usual signals: the suite is green, CI is green, and the author's metrics (assertion ratios, line counts, test totals) are all reproducible. Reproducing those numbers is not the review. Diff the *test-name sets* between base and head (`git grep -h -o "def test_[a-z0-9_]*" <base> -- <tests>` versus the same at head, sorted, then `comm -23`) and read the removed names for the ones that guard a safety, cost, credential, or fail-closed policy rather than pedagogy or prose. For each, find what at head still catches it and mutation-test that claim; a removed guard whose replacement you cannot name is the finding. Two traps recur. A replacement that asserts a *committed output* ("QPU execution is disabled" in a stored notebook/snapshot) does not cover a source edit that was never re-executed, because the artifact stays byte-identical — so mutate the source only, leaving outputs untouched. And a replacement one layer away (the build target refuses without opt-in) does not cover the layer the users actually run, so check whether CI or any documented command exercises that layer at all before accepting it. Prove both directions: the defect mutation red, and the behavior-neutral edit the PR promises to tolerate still green.
- For dependency or lockfile PRs, verify the exact resolved versions in the lockfile, import updated packages when practical, and run documented tests/notebooks that exercise the changed dependencies. For compat-only PRs, compare the changed bounds against the current base files and flag any silent narrowing of already-allowed compatible lines when issue or PR examples are stale. Report expected warnings without treating them as failures. When a PR renames or first-sets a published distribution name, advertises an install command, or merely curates published distribution metadata (project URLs, maintainers, classifiers) without touching the name, confirm the name is actually available or owned on the target index (PyPI/npm/crates; for PyPI, `https://pypi.org/pypi/<name>/json` returns 404 when unregistered and 200 when taken). An advertised `pip install <name>` (or equivalent) can silently install an unrelated project that already holds the namespace — and a PR that publishes an unreserved name in README, rendered docs, and an install guide opens exactly that window between merge and first release, so flag reserving it (a placeholder upload) or tracking it in an issue. A rename also needs a migration step whenever the *import* name stays the same: package managers do not treat the new distribution as superseding the old one, so an environment holding the old name ends up with two records owning the same files, and uninstalling the new one can leave the stale record reporting an installed package whose import fails. Reproduce that upgrade path in a throwaway environment (install the merge-base, then the head, then uninstall) instead of reasoning about it, and require the install docs to carry an explicit uninstall-first step.
- When a rename or any manifest edit lands alongside a committed lockfile, confirm the lockfile was regenerated to match — a frozen/locked install (`pip install --locked`-style, `pixi install --locked`, `cargo build --locked`, `npm ci`) fails when lock and manifest diverge, so run it rather than trusting the committed lock. That check, and green CI, still answer only whether the lock *matches the manifest*, not whether its resolved content is sound. In a lockfile that mixes ecosystems (conda plus PyPI, system plus language packages), check whether any package resolves **twice** into one prefix from both sides: it happens when the entry on one side carries no cross-ecosystem mapping (for example `purls: []` on a freshly built conda package), so the other resolver satisfies the same requirement with a second artifact that then overwrites the first in place. Two builds of a compiled library stacked in one environment still import and still pass every test, so nothing but the lock content reveals it. Re-solve the same manifest with a current tool and diff against the committed lock; entries the re-solve drops, or mappings it fills in, are the evidence. Report the lock/manifest result and the resolved-content result separately, since the first can be green while the second is wrong.
- For security-alert remediation PRs, read the alert/advisory metadata and verify whether a patched version exists. If no patched version exists, verify that the vulnerable package path is removed or no longer locked/installed, that docs explain any intentionally unsupported optional path, and that a regression check prevents quiet reintroduction.
- For generated sites/docs, build the output and run a local-link/resource sanity check that respects generated base paths; include syntax checks for shipped JS/assets when applicable.
  If local build dependencies are unavailable but GitHub checks already ran the authoritative generated-site build for the same head, use targeted static checks plus the GitHub check result instead of spending time repairing the local system environment, unless a suspected issue specifically requires local reproduction.
  For GitHub Pages PRs, verify the intended deployment owner and canonical Pages URL. If the PR body advertises a fork or preview URL, make sure it is labeled as a preview or updated to the post-merge repository URL so reviewers do not confuse a fork Pages site with the upstream deployment.
- For LaTeX/manuscript PRs, compile the document (for example `pdflatex` + `bibtex` + reruns) as the merge-readiness check, and treat undefined references/citations and any mismatch between an `\includegraphics` filename and its caption or surrounding text (an embedded figure that plots a different case than the caption claims) as review findings, not cosmetic. Cross-check numeric claims against the figures/tables actually included rather than the prose alone. Build-environment package gaps (a missing document-class package) are handled in the shared conventions.
- For PRs that generate an input file consumed by an external solver or tool (a GAMS `.gms`, an LP/MPS or other model file, a generated CLI/config), a test that only asserts the expected lines appear in the written text does not prove the tool accepts the file: it can be emitted yet fail to compile or solve (for example priority `.prior` assignments written for variables the writer later eliminates, which pass a unit suite but break GAMS compilation). When a local instance of the target tool is available, run the generated artifact through it end to end. The tool may be installed outside `PATH`, so probe it through the project's own driver (for example Pyomo `SolverFactory("gams").available()`, which finds a GAMS install under a package directory) before concluding it is unavailable, and note when a subsolver path could only be validated from the author's own run because a local sublicense (for example GAMS/Gurobi) was missing.
- For PRs that add or swap an optimization/solver backend behind an adapter (or any thin wrapper that reads specific fields off a third-party result object — an SDK response, an HTTP client, a solver `Results` object), verify the adapter against the pinned dependency's *actual* result object rather than trusting the field names: a small probe against the locked version (one real solve/call) confirms the captured status/termination mapping, objective, timing, and version accessors exist and return sane values, because a mistyped attribute or an unmapped status surfaces only when that untested branch runs. Separately confirm the failure contract: the adapter must not expose a partial, stale, or non-optimal result as a success — it should load/return values only after a success/optimal termination and reject missing, non-finite, or materially out-of-range extracted values — and the public result type and report output must stay backend-independent (no solver object leaking through the general API). Reproduce any published reference result the PR claims to preserve, and when the underlying problem is degenerate (alternate optima), check the tie-break is a documented deterministic rule rather than incidental solver ordering.
- For PRs that vendor or derive code from another repository and cite a pinned revision as the implementation source, verify the pin by diffing the shipped file against that exact revision (fetch it raw by SHA) rather than checking that the link resolves. A pin chosen as "current upstream main" routinely postdates an upstream refactor of the same file — the citation then names a revision whose implementation differs from the shipped one, and a regression test asserting the pin string cements the error. When the diff is substantive, walk the file's upstream history (`gh api 'repos/OWNER/REPO/commits?path=<file>'`) to find the revision that actually matches, and prescribe repinning to it with deliberate local deviations noted beside the citation. Verify cited upstream PR/issue identities separately: query `repos/OWNER/REPO/issues/<N>` and inspect whether `.pull_request` exists, then use `repos/OWNER/REPO/commits/<sha>/pulls` to bind the pin to the PR that carried it. A commit subject such as `Fix ... (#63)` can name a tracking issue while the implementation merged through another PR, so a correct SHA does not make an incorrect PR attribution harmless. Cross-check values inherited from the upstream docs the same way: a "best known" objective or size table copied from the source repo must not contradict the PR's own committed artifacts — a best-known value better than every proven-optimal bound in the committed results is internally inconsistent, and the repo's own regenerated artifacts win.
- For PRs that add or edit a repository policy or planning document (`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING`, `PLANNING`/`RELEASING`, a style guide, agent instructions), check the three things the diff cannot show. First, every artifact the policy references must exist and match the repo: run the documented commands, and compare named test markers, environment names, file paths, and relative links against the tree (a marker list against `pytest.ini`, a `.github/`-relative link resolving to `../AGENTS.md`), including — for a Markdown policy — its own table-of-contents anchors against its headings, since GitHub's slug drops backticks and punctuation. Second, review it for *omissions* — a policy's defects are mostly what it leaves out — by checking it against the failure modes this repo has actually paid for: its recent fix PRs, open issues, and prior review threads. Propose each missing rule as drafted replacement text, not as "consider documenting X". Apply the redundant-interface lens to the entry points too: do not ask for another adapter file when a tool already reads the canonical one natively (Codex reads `AGENTS.md`), but do ask the document to say so, since an unexplained gap invites someone to add the redundant file later.
  Third, a policy binds the humans who must follow it, so check that they can actually read it — a document only an agent can parse fails at its stated purpose. The mechanical version of this check: for every term the document uses in a *normative* position (a gate, a promotion rule, an entry/exit criterion), confirm it is defined in the document or in a repo file it links. An undefined gating term is a finding at the severity the gate warrants, not a style nit, because a gate nobody can define cannot be walked; the usual tell is a term used several times in several spellings ("smoke/validation suite", "smoke/numerical suite", "smoke-install job") that `git grep` finds nowhere else in the repo. Judge the vocabulary against the audience the repo actually has: project-management and release-engineering idiom ("lazy consensus", "WIP limit", "burn down", "commitment unit", "DOI'd") is not common knowledge on a research or domain-science team. Ask for a one-line definition on first use or a short glossary rather than rewriting the author's model, and cite the document's own good examples when it has them — a term already defined parenthetically, or a terminology table it added for something else — so the ask is a pattern to extend rather than a matter of taste.
- For CI/workflow changes, cheaply verify referenced external action/tool versions exist and check `GITHUB_TOKEN` permissions/event triggers for unnecessary write scope or secret exposure. Flag by name the canonical injection pattern: a workflow on `pull_request_target` (or `workflow_run`) that checks out the PR head ref and then executes contributor-influenced code — build steps, tests, install scripts, or even linters reading config from the checkout — since those triggers run in the base repository's context with secrets and a write-capable token that a plain `pull_request` trigger never gets. Require the privileged trigger to keep the checkout inert (metadata-only, or explicitly pinned to the base ref), split the work into an unprivileged run-and-upload workflow plus a privileged consume-artifact workflow, or gate execution behind an explicit trust label before treating the workflow as safe. When a workflow change renames jobs, runner labels, or status contexts, compare branch-protection required checks against the PR's current check names and flag stale required contexts as merge-readiness feedback.
- For Dependabot-configuration changes, compare configured update directories against checked-in package/project manifest directories, verify grouped update names/cadences are coherent, and flag omitted active project directories or non-existent configured directories unless the PR explains the exception.
- For citation-metadata files (`CITATION.cff`), validate with `cffconvert --validate` rather than only eyeballing the YAML, since the acceptance bar is usually schema validity; the tool is not always in the project environment, so install it into a scratch venv when absent. Structurally-valid YAML is not proof of a valid CFF. Separately judge whether the `authors:` roster matches what the PR/issue claims (for example a full team versus only the verified contact), and flag an under-filled roster as review feedback.
- Before finalizing, list the repository's other open PRs (`gh pr list`) and check whether any touches the same files, identifiers, or config keys. A change that is correct in isolation can be obsoleted by a sibling PR — one that removes the very dependency a new test helper works around — or silently broken by one, as when a sibling renames a distribution or constant that this PR's lookup hardcodes and a `try`/fallback swallows the resulting error into a plausible-looking default. Neither shows up as a merge conflict when the two PRs touch different lines, and CI stays green on both. Report the coordination explicitly instead of reviewing the PR as if it were the only one in flight.
- In the posted review, distinguish PR-head checks from merge-result checks.

## Linked Issue Check

If the PR references or claims to close an issue, read the issue and comments with `gh`. Judge whether the PR solves the requested problem, not merely an adjacent one.

- Flag a clear miss of the issue's core ask as `Blocking`.
- Flag an arguable or partial gap as `Question`.
- Flag `Closes #...` when the PR only partially resolves the issue; the correct link is `Refs #...`.
- If no issue is referenced, note that and review on the merits.
- If the PR says it supersedes, replaces, or follows up another PR, read that PR's summary and state. Verify the new PR preserves the intended behavior without inheriting stale conflicts, generated output churn, or obsolete assumptions.
- An issue's acceptance criteria are a floor, not a ceiling. Meeting them — or the issue text appearing to sanction a particular approach ("a fast smoke test in the regular suite is fine") — does not make the change correct if it violates the repo's architecture or ecosystem idiom; an issue, often written by the same author, can under-specify or predate a convention. Judge the design against the codebase's boundaries even when the issue "allowed" the shortcut, and block on those grounds when warranted rather than citing the issue as a reason it is merge-ready.

## Findings

Report only actionable findings. Prefix each finding with exactly one severity:

- `Blocking`: correctness, regression, missing test for changed behavior, broken public API, security, or serious maintainability issue.
- `Nonblocking`: useful improvement that does not block merge.
- `Question`: clarification needed before deciding whether a change is required.

For each finding, state the issue, why it matters, a concrete fix, and the relevant file or docs link. Keep comments concise and anchored to changed lines when posting inline.

Keep reviewer-only machinery out of the prescribed fix. Prefer the simplest repository-consistent correction that addresses the demonstrated risk, even when the scratch reproduction or mutation probe used to discover it was elaborate. A short decisive counterexample is usually enough in an inline comment; include exhaustive tables or replacement harnesses only when the author needs them to reproduce or choose among materially different designs.

When a prescribed fix names a concrete identifier the reviewer did not construct — a result-dict key path, an attribute on a dependency's object, a config field — verify that identifier against the source that produces it (grep the producer, or read the constructed object) before posting. Sibling structures make this easy to get wrong from memory: a value can live under `problem.` on one result type and `metrics.` on another, and a fix sketched with the wrong path ships a KeyError that the addressing pass only catches by re-deriving what the review should have checked. The full-prototype bar above is for alternative designs; for a named path, one targeted read of the producing code is enough and is not optional.

When the reviewed head already carries a human approval at exactly that SHA, price the respin into the prescribed fix: any new commit leaves that approval referencing a superseded head. For a latent or `Nonblocking` item, weigh that cost against the defect's reach — a tracked deferral (a coordination note on the owning issue, cross-linked with the inline comment) is a legitimate prescribed remedy in that position. Say explicitly that deferral is the recommended resolution, so the addressing pass records the deferral instead of manufacturing a code change.

When the artifact already carries a *partial* version of what you are asking for — a refresh policy whose trigger list omits one case, a caveat covering one of two snapshots, validation that misses one branch — name the specific missing element instead of the general gap. A finding phrased as though the mechanism were absent invites an accurate reply that it already exists, costs a round trip, and reads as though you had not finished reading the file. Anchor such a comment where the fix belongs (the trigger list that needs a fourth entry) rather than where the symptom is visible, and name the other artifacts the same fix must cover.

When the concrete fix is an *alternative design* rather than a local correction, run it before recommending it. Write the prototype, exercise it against the same dependency and call pattern the PR uses, and check specifically whether it still satisfies the property the author was buying — a lazy loader that stops being lazy, a helper that changes an import-time contract, an API that breaks an existing call form. The failure mode is a finding that reads as strictly better and is not: PEP 562 module `__getattr__` returns real classes instead of factory functions, but `from mod import Name` invokes it at import time and defeats the laziness, so adopting it means rewriting every call site to attribute access. Post the trade-off with both sides and the cost you measured, and say plainly when the author's choice is defensible; an unprototyped "you should have done X" costs the author a round trip to discover what you would have found in five minutes. Where the author's design is sound but its constraint is non-obvious, the useful ask is often to record the rejected alternative and why, not to change the code.

When proposing replacement text via a GitHub ```suggestion block, never nest another code fence inside it (an inner ```math or ```julia block, for example): GitHub's "Apply suggestion" truncates at the inner fence and commits mangled content that then needs a follow-up fix. For replacements whose content contains fences, describe the edit in plain comment prose instead of a suggestion block.

For first-time or external contributors, keep GitHub review comments encouraging while preserving technical clarity: acknowledge useful work when true, frame required changes as concrete next steps, and do not soften `Blocking` severity when the issue genuinely blocks merge.

For top-level review-body findings that are not posted inline, include a short stable marker after the finding heading, for example `<!-- gh-review-pr:finding=integer-no-good-cut -->`. Keep markers unique within the review. Inline comments do not need extra markers because GitHub provides comment ids.

## Posting The Review

1. Before posting, re-list existing PR reviews with `gh api repos/{owner}/{repo}/pulls/{number}/reviews --paginate`.
2. If a review authored by you is `PENDING`, delete it with `gh api repos/{owner}/{repo}/pulls/{number}/reviews/{review_id} --method DELETE`.
3. Recompute the head SHA. If it differs from the SHA reviewed, stop and review the new head instead. Embed the sentinel `<!-- gh-review-pr:sha=<HEAD_SHA> -->` at the end of the review body. Recheck the reviews listed in step 1 for one authored by you (compare `user.login` to `gh api user --jq .login`) whose body already contains that exact sentinel; if one exists, do not post again — report that you already submitted a review for this head SHA (cite its state and id) and stop, unless the user explicitly asked to redo the review for this exact head and (per the Setup step 4 exception) confirmed they want a second post, or their original request already said to post/resubmit. In that case, post a new review anyway: open the body by stating it is a re-review of the same head by explicit request, and keep the same sentinel since the head is unchanged.
   - Before constructing the final body, confirm every top-level review-body finding has a unique `<!-- gh-review-pr:finding=... -->` marker. Do not leave body-only findings as unmarked prose or bullets; follow-up address and verification workflows depend on stable anchors.
4. Prefer one atomic review POST so a failed step does not leave a pending review: write a JSON body with `commit_id` set to the reviewed head SHA, `event`, `body`, and `comments` (`[]` for a body-only review), then call `gh api repos/{owner}/{repo}/pulls/{number}/reviews --method POST --input <json_file>`. Build that JSON by serializing an object with a real serializer (for example a short Python `json.dump` snippet), never by hand-authoring the JSON text: the `body` is Markdown full of double quotes, backticks, `<!-- ... -->` markers, and newlines, and a single unescaped `"` inside it makes the POST fail with `Problems parsing JSON` (HTTP 400). Have the serializer write the file, then `--input` it. Each inline comment must use a valid diff anchor (`path`, `body`, and either `line`/`side` or `position` as accepted by GitHub for that diff hunk).
5. Anchor inline comments on diff hunks. If the exact location is awkward, anchor on the nearest changed line and name the real location in the body. GitHub renders no diff hunk for very large, binary, or generated files (it shows "Large diffs are not rendered by default"), so an inline anchor on such a file 422s with `Line could not be resolved` — and because the review POST is atomic, that one bad anchor drops the entire review. Put findings on un-rendered files in the review body instead of anchoring them inline.
   - Weigh one more cost before anchoring inline: when the base branch enables `required_conversation_resolution` and the workflow posting this review is forbidden from resolving threads (the automated review/address/verify loop is), every inline comment becomes a merge gate that only a human can clear. In that combination prefer marker-bearing review-body findings, which carry the same content and the same stable anchors for the follow-up workflows without leaving the PR `BLOCKED` after the findings are addressed. Say in the body why the findings are not inline, so the choice reads as deliberate. Anchor inline as usual when protection does not require resolution, or when the user will resolve threads themselves.
6. Submit `REQUEST_CHANGES` if there are blocking issues, `COMMENT` if the PR is draft, `APPROVE` if there are no blocking issues and the PR is merge-ready, otherwise `COMMENT`.
7. If you are the PR author, GitHub rejects `APPROVE` and `REQUEST_CHANGES`; submit `COMMENT`, include the same findings, and state that this account cannot provide the formal approval. Say another maintainer is required only when live GitHub state reports an approval gate.
8. If `gh` fails to post, report the exact error and stop.
9. After posting, verify submitted review state through `gh api repos/{owner}/{repo}/pulls/{number}/reviews --paginate`; `gh pr view --json latestReviews` can omit COMMENTED reviews, especially author COMMENT reviews. For inline comments, query GraphQL `reviewThreads`, match the posted comment ids, and inspect `path`, `line`, `originalLine`, and `isOutdated`. Do not infer an invalid anchor solely because the REST review-comments response returns `line: null` or `side: null`; it can do so for a valid current comment, while `isOutdated: false` and a resolved current GraphQL line confirm the anchor. After posting an `APPROVE`, also re-read `reviewDecision`, `mergeStateStatus`, and branch protection if the PR still appears blocked. Do not claim the approval satisfied branch protection solely because the review API returned `APPROVED`; if GitHub still reports `REVIEW_REQUIRED`, state that another eligible maintainer/account may be needed, especially when the reviewer also authored or pushed the latest changes. When the posted review contains inline comments and branch protection enables `required_conversation_resolution`, expect `mergeStateStatus` to flip to `BLOCKED` because of the just-created unresolved threads (see shared conventions); report thread resolution as the remaining merge gate, not an approval requirement. For the same reason, do not assert a pre-post merge state such as `CLEAN` as current inside a review body that adds inline comments — posting the review itself invalidates it. Re-read the PR `state` (not only `mergeStateStatus`) immediately before posting: a maintainer can merge concurrently while you review, and a review can land seconds after the merge. `mergeStateStatus: UNKNOWN` on an otherwise-ready PR is a hint that a merge (or recompute) just happened — check `state` for `MERGED`. If it merged during your review, keep the review but frame it as retrospective, and drop any "before merge" recommendation since that gate is already gone.
10. If the user asks to revise a review's verdict at the same head SHA (for example converting previously `Nonblocking`/`Question` findings into blocking, or otherwise changing `APPROVE`/`REQUEST_CHANGES`/`COMMENT`) without new commits to react to, do not try to edit or delete the earlier submitted review — a submitted (non-`PENDING`) review is immutable and dismissal only marks it `DISMISSED` without changing its content. Submit a new review with the updated `event` and the same `<!-- gh-review-pr:sha=... -->` sentinel, and open the body by linking to and stating it supersedes the prior review. GitHub computes `reviewDecision` from each reviewer's most recently submitted review, so the new one takes effect without needing to dismiss the old one.

## Review Summary

End the posted review with blocking issues, nonblocking issues, questions, tests run and outcomes, and merge-readiness. Derive each finding count from the same structured inventory used to build the atomic review: count inline comments and marked review-body findings separately, and verify that their subtotals sum to the reported total before posting. Do not hand-enter a parenthetical breakdown that cannot be reproduced from that inventory. When reporting GitHub checks, summarize the latest/current run set for the reviewed head, and distinguish intentional `SKIPPED` checks from failures. If blocking issues exist, state: `I would not merge this until the blocking issues above are addressed.`

For author or draft COMMENT reviews with no findings, say plainly that there are no blocking findings, then state why the review is a COMMENT and any live remaining gate such as marking the PR ready or satisfying a reported review requirement. For author COMMENT reviews, do not claim that branch protection needs another maintainer approval unless GitHub reports that gate; otherwise say only that this account cannot provide a formal approval if one is needed. If the COMMENT is only because the PR is draft or behind its base, state that this review does not satisfy branch-protection approval and that an eligible APPROVE review will be needed if approval is required after those gates are cleared.
