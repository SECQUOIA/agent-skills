# GitHub Maintainer PR Review

## Overview

Use this workflow to perform and post a maintainer-quality PR review.

Follow the shared **gh-workflow-conventions** (read the sibling `gh-workflow-conventions/SKILL.md`): gh-only tooling and `--json` fallback, PR/repository resolution across remotes, terse invocation shorthand, untrusted-text handling, network/filesystem escalation and bounded watches, CI-after-push polling, active test environment, commit/push hygiene, and concise tone. This file covers only what is specific to posting a maintainer review.

Use the reference pointers below progressively. Read a reference when its stated condition is reached; do not preload every review reference at startup.

## Setup

1. Resolve the PR (see shared conventions for URL/number/branch and multi-remote resolution).
2. Fetch the PR base branch and head with `git` so the local checkout is fresh.
   - If the request also authorizes a scoped source edit, read [references/review-state-edge-cases.md](references/review-state-edge-cases.md) before editing or selecting the reviewed SHA.
3. Read PR metadata, commit list, and diff through `gh pr view`, `gh pr diff`, and `gh api`.
   - Compare each commit's purpose and issue-closing references with the PR title, body, and linked issues. An independent commit omitted from the description can silently close another issue and is scope/traceability feedback even when its diff is valid.
   - Judge the body's *encoding* as well as its claims: a description authored with escaped `\n` in a shell string is stored as one line containing literal backslash-`n`, and renders on the website with no headings, bullets, or auto-linked issue refs. The tell is in the output you are already reading — `"body":"## Summary\\n\\n- ..."` from `--json`, or a single unbroken line with visible `\n` from `--jq .body`. It is easy to skim past because the prose itself reads correctly, so check it deliberately at this step rather than trusting a later pass; broken rendering in the description is review feedback.
4. Determine the head SHA and current GitHub user early. List existing reviews; if one by you already contains the exact sentinel `<!-- gh-review-pr:sha=<HEAD_SHA> -->`, apply the repeat-review exception in [references/review-state-edge-cases.md](references/review-state-edge-cases.md) before deciding whether to stop. Unless that exception applies, stop before running expensive checks and report the existing review id/state.
   - For repeat reviews, prior reviews without sentinels, changed heads, author or draft PRs, terminal PRs, retrospective audits, or requests limited to novel findings, read [references/review-state-edge-cases.md](references/review-state-edge-cases.md) before deciding whether and how to continue.
5. Diff against the merge-base. Verify that the changed-file set from your local diff (`git diff --name-only $(git merge-base origin/<base> HEAD) HEAD`) equals GitHub's own file list, read with `gh api repos/{owner}/{repo}/pulls/{number}/files --paginate --jq '.[].filename'`. Do not reach for `gh pr diff --name-only`: that flag is absent from older `gh` builds and fails with `unknown flag: --name-only`, which is easy to misread as a bad base or a missing PR when it is only an unsupported flag. Treat line totals as advisory only, since context and whitespace can differ. On a file-set mismatch, re-fetch base and head and recompute once. If the sets still differ, apply the empty-diff exception below before deciding whether to stop. Unless that exception applies, do not post a review — stop and report the discrepancy (the files present on only one side) so the base can be corrected.
   - For empty merge-base diffs, PRs already absorbed by the base, or apparent end-of-line churn, read [references/review-state-edge-cases.md](references/review-state-edge-cases.md) before classifying the discrepancy.
6. For first-time contributors or otherwise untrusted external contributors, complete a static safety pass before executing any contributor-controlled code. Inspect changed files and metadata for execution hooks, workflow changes, package-manager scripts, generated binaries, dynamic import/eval/exec, shell/subprocess use, filesystem or network access, environment/secret reads, and test hooks such as `pytest_plugins`, `conftest.py`, fixtures, and `autouse`. If the pass finds a credible injection or supply-chain risk, do not run the PR code; continue with static review only and state the risk clearly.
7. Review the PR head in a clean tree. If unrelated local artifacts make the shared checkout dirty, use a temporary worktree at the PR head for inspection and tests, then remove it before finishing. When running containerized validation against a temporary worktree, run the container as the host user or otherwise ensure generated files can be removed during cleanup. Flag only issues introduced or materially changed by this PR, not pre-existing code it merely touches.

## Review Standard

Inspect the diff, surrounding code, tests, docs, and repository conventions for:

- correctness bugs and regressions
- missing tests for changed behavior
- public API, CLI, UX, or documentation inconsistencies
- maintainability risks that matter to future maintainers
- security or data-safety issues
- design and scope: whether the change *should exist as written*, not only whether it works — minimal public surface (no second interface doing roughly what an existing one does; a superseded/experimental spelling not yet in any released version is debt to remove now, not compatibility to preserve), staying within the repo's stated version/scope assumptions (e.g. "v1" contracts), keeping layer boundaries clean (a general/interface-level function must not encode downstream/backend specifics in its code or docs), and avoiding constructions whose cost grows combinatorially when a bounded one exists.

Establish what the repository actually declares public before grading anything as a broken public API. The surface is the repo's own markers, not the presence of a docstring or an entry in the rendered docs: the module's export list (`export`, `__all__`, `public`, an explicit `@api` annotation) and the API page's own public-versus-internal section structure. A type rendered under an `## Internal Functions` heading is documented internals, so calling a change to its fields or constructor a released-API break overstates the finding and earns a one-line rebuttal that costs a round trip. Read the released version too: a `0.x` package is conventionally still refining its interface, so a maintainer may fully intend a documented field or type to change in the next minor. Where the surface is genuinely ambiguous, raise it as a `Question` rather than asserting a break — and keep whatever defect stands on its own, since a docstring that now describes the wrong shape, or a standard operation that stopped working, is a finding whether or not the symbol is public.

When a PR adds, renames, or removes a repository-native discoverable unit such as a skill, plugin, command, or workflow, review the discovery/install contract as part of the change. Verify the implementation file and every repo-standard surface move together: sidecar metadata such as `agents/openai.yaml`, README/catalog rows, installer manifests, generated lists, or documented install commands. A valid new `SKILL.md` can still be undiscoverable or present stale UI metadata.

Correct, tested, and green is necessary but not sufficient. A maintainer also asks "is this the right change for where the codebase is going?" — and blocks correct code on design or scope grounds when it adds interface debt, exceeds the stated version scope, leaks backend concerns into a general layer, pushes validation/normalization into inner or hot paths instead of doing it once at the public boundary or constructor, couples a subordinate artifact (benchmark, example, script, generated data) into a core surface — package tests, dependencies, or published/reference docs — that should stay independent of it, reinvents a standard ecosystem tool (or an API the repo already exposes) instead of using it, builds in a feature users can already compose from the public API (a loop around an entry point, a callback hook covers saving/monitoring/restarts — prefer the general hook over the baked-in special case), or invests in machinery that cuts against the package's stated core value proposition (for example a CPU-bound sub-solver in a package whose selling point is GPU execution). Surface these as first-class findings at the severity a maintainer would assign; do not downgrade them to `Nonblocking` merely because the code passes tests. When you catch yourself concluding "works, only nits," recheck the change against this design/scope lens before finalizing.

When a PR (re)introduces a recognizable mechanism — a spectral or penalty shift, a retry loop, a cache, a fallback layer — search the repository's own history for a prior implementation before endorsing it: `git log -S<keyword>` plus closed issues and PRs surface whether the same mechanism was already tried and deliberately removed. A maintainer with that memory will ask "didn't we revert this?", and a review that recommends the mechanism without surfacing the earlier removal endorses it on incomplete evidence — the removal rationale is precisely the validation matrix the new attempt must answer.

When judging maintainability, apply the code-smell baseline in [references/review-rubric.md](references/review-rubric.md); read that file for the smell list and the rules that keep it from producing noise (repo standards override, smells are judgement calls, skip anything tooling enforces).

Verify behavioral claims by running commands, imports, tests, or entry points when practical; run at least the targeted changed-behavior test locally when cheap, and scale broader local validation to risk. For PRs from untrusted authors, run contributor-controlled code only in an isolated environment; if isolation is unavailable, review statically and say why.

When the PR changes tests or bases a claim on local validation, randomized or property checks, mutation probes, broadened input ranges, status classification, thresholds, strict modes, skipped or deselected lanes, verification counts, or migration warnings, read [references/testing-and-evidence.md](references/testing-and-evidence.md) before judging that evidence. Follow its pointer to the shared test-quality rules before designing mutation probes.

## Merge-Readiness Checks

Keep extra validation proportional to the PR. Inventory the changed artifacts and the claims the PR makes before choosing specialized checks.

Read [references/specialized-review-checks.md](references/specialized-review-checks.md) when the PR head lags its base, deletes or renames a path, changes generated output that depends on full-repository state, splits an always-loaded instruction file into conditionally loaded references, or changes or claims parity for notebooks, figures, shared setup guidance, removed tests, dependencies or lockfiles, security alerts, generated documentation, manuscripts, external-tool inputs, solver or SDK adapters, vendored code, reproducible result tables, repository policies, CI/Dependabot configuration, or citation metadata. Do not load unrelated categories.

- Before finalizing, list the repository's other open PRs (`gh pr list`) and check whether any touches the same files, identifiers, or config keys. A change that is correct in isolation can be obsoleted by a sibling PR — one that removes the very dependency a new test helper works around — or silently broken by one, as when a sibling renames a distribution or constant that this PR's lookup hardcodes and a `try`/fallback swallows the resulting error into a plausible-looking default. Neither shows up as a merge conflict when the two PRs touch different lines, and CI stays green on both. Report the coordination explicitly instead of reviewing the PR as if it were the only one in flight. When your own validation has already demonstrated that the PR's code breaks at a sibling's head — the compatibility experiment you ran there needed an adapted variant to pass — escalate from a coordination note to a finding that names the breakage and its trigger (the sibling merging): body prose reads as optional, and the incompatibility is otherwise rediscovered by a human after the sibling lands.
- In the posted review, distinguish PR-head checks from merge-result checks.

## Linked Issue Check

If the PR references or claims to close an issue, read the issue and comments with `gh`. Judge whether the PR solves the requested problem, not merely an adjacent one.

- Flag a clear miss of the issue's core ask as `Blocking`.
- Flag an arguable or partial gap as `Question`.
- Flag `Closes #...` when the PR only partially resolves the issue; the correct link is `Refs #...`.
- Read the issue's own framing for a structural ask beyond the reproducing symptom: wording like "we may need to redesign X" or a root-cause diagnosis makes the issue own the underlying problem, so a fix that resolves the reported reproduction but not the structural concern is a *partial* resolution — prefer `Refs` plus a tracked follow-up, or raise the linkage as a `Question`, even when every reported case now passes.
- Treat the issue's own reproduction as the canonical regression fixture. When it is expressible at the PR's base, expect it committed verbatim in the tests and flag its absence — derived fixtures may cover the mechanism, but the maintainer's first question is whether the reported model now works. When it is not yet expressible (it depends on unmerged work), require a tracked plan to add it and re-check once the dependency lands.
- If no issue is referenced, note that and review on the merits.
- If the PR says it supersedes, replaces, or follows up another PR, read that PR's summary and state. Verify the new PR preserves the intended behavior without inheriting stale conflicts, generated output churn, or obsolete assumptions.
- An issue's acceptance criteria are a floor, not a ceiling. Meeting them — or the issue text appearing to sanction a particular approach ("a fast smoke test in the regular suite is fine") — does not make the change correct if it violates the repo's architecture or ecosystem idiom; an issue, often written by the same author, can under-specify or predate a convention. Judge the design against the codebase's boundaries even when the issue "allowed" the shortcut, and block on those grounds when warranted rather than citing the issue as a reason it is merge-ready.

## Findings

Report only actionable findings. Prefix each finding with exactly one severity:

- `Blocking`: correctness, regression, missing test for changed behavior, broken public API, security, or serious maintainability issue.
- `Nonblocking`: useful improvement that does not block merge.
- `Question`: clarification needed before deciding whether a change is required.

For each finding, state the issue, why it matters, a concrete fix, and the relevant file or docs link. Keep comments concise and anchored to changed lines when posting inline.

Keep reviewer-only machinery out of the prescribed fix. Prefer the simplest repository-consistent correction that addresses the demonstrated risk, even when the scratch reproduction or mutation probe used to discover it was elaborate. A short decisive counterexample is usually enough in an inline comment; include exhaustive tables or replacement harnesses only when the author needs them to reproduce or choose among materially different designs.

When a prescribed fix names a concrete identifier the reviewer did not construct — a result-dict key path, an attribute on a dependency's object, a config field — verify that identifier against the source that produces it (grep the producer, or read the constructed object) before posting. Sibling structures make this easy to get wrong from memory: a value can live under `problem.` on one result type and `metrics.` on another, and a fix sketched with the wrong path ships a KeyError that the addressing pass only catches by re-deriving what the review should have checked. The full-prototype bar above is for alternative designs; for a named path, one targeted read of the producing code is enough and is not optional.

A pre-post check is owed to the finding's *premise* too, not only to its prescribed fix. When the claim is that the change removed support for something — a narrowed keyword, a type a setter no longer accepts, a call form that used to work — execute that usage against the merge base before posting. A path that already failed there for an unrelated pre-existing reason was never supported, so the narrowing is real in the abstract and unreachable in practice. Reasoning is what misleads here rather than the diff: "the old line assigned the attribute directly, so any object worked" is plausible, survives re-reading the hunk, and is refuted only by running the base.

When the reviewed head already carries a human approval at exactly that SHA, price the respin into the prescribed fix: any new commit leaves that approval referencing a superseded head. For a latent or `Nonblocking` item, weigh that cost against the defect's reach — a tracked deferral (a coordination note on the owning issue, cross-linked with the inline comment) is a legitimate prescribed remedy in that position. Say explicitly that deferral is the recommended resolution, so the addressing pass records the deferral instead of manufacturing a code change.

When the artifact already carries a *partial* version of what you are asking for — a refresh policy whose trigger list omits one case, a caveat covering one of two snapshots, validation that misses one branch — name the specific missing element instead of the general gap. A finding phrased as though the mechanism were absent invites an accurate reply that it already exists, costs a round trip, and reads as though you had not finished reading the file. Anchor such a comment where the fix belongs (the trigger list that needs a fourth entry) rather than where the symptom is visible, and name the other artifacts the same fix must cover.

When the concrete fix is an *alternative design* rather than a local correction, run it before recommending it. Write the prototype, exercise it against the same dependency and call pattern the PR uses, and check specifically whether it still satisfies the property the author was buying — a lazy loader that stops being lazy, a helper that changes an import-time contract, an API that breaks an existing call form. The failure mode is a finding that reads as strictly better and is not: PEP 562 module `__getattr__` returns real classes instead of factory functions, but `from mod import Name` invokes it at import time and defeats the laziness, so adopting it means rewriting every call site to attribute access. Post the trade-off with both sides and the cost you measured, and say plainly when the author's choice is defensible; an unprototyped "you should have done X" costs the author a round trip to discover what you would have found in five minutes. Where the author's design is sound but its constraint is non-obvious, the useful ask is often to record the rejected alternative and why, not to change the code.

The same bar applies when the prescribed fix names a specific numeric threshold, tolerance, or constant: sweep the repository's own committed data at that value before posting (one short script over the existing artifacts is enough). A value that is conceptually right can be empirically wrong — tightening a cross-run bound-validity tolerance to the solver's own 1e-6 optimality gap flagged dozens of spurious violations from independent per-run feasibility slack on pairs that agree, while the looser 1e-4 isolated exactly the genuine crossings. Prescribe the structural part you verified (split the constants, document both) and, when the sweep is impractical, say explicitly that the value itself is unverified rather than shipping a number the addressing pass must falsify.

When proposing replacement text via a GitHub ```suggestion block, never nest another code fence inside it (an inner ```math or ```julia block, for example): GitHub's "Apply suggestion" truncates at the inner fence and commits mangled content that then needs a follow-up fix. For replacements whose content contains fences, describe the edit in plain comment prose instead of a suggestion block.

For first-time or external contributors, keep GitHub review comments encouraging while preserving technical clarity: acknowledge useful work when true, frame required changes as concrete next steps, and do not soften `Blocking` severity when the issue genuinely blocks merge. That `when true` carries the same evidence bar as a finding — an acknowledgment is a published technical claim, and it is the least-checked part of a review because praise invites no rebuttal and no addressing pass ever re-derives it. Verify a hunk does what you credit it with before crediting it: a positional `.values` assignment replaced by an explicit merge on the group keys reads as a bug fix, but is only a hardening until you run both forms and see them disagree. Authors quote review praise into PR bodies and changelogs, so an unverified compliment does not stay in the review — it becomes the merge record's own description of the change, and retracting it costs a second public round.

For top-level review-body findings that are not posted inline, include a short stable marker after the finding heading, for example `<!-- gh-review-pr:finding=integer-no-good-cut -->`. Keep markers unique within the review. Inline comments do not need extra markers because GitHub provides comment ids.

## Posting The Review

After completing the technical review, linked-issue check, and structured finding inventory, read [references/posting-review.md](references/posting-review.md) and the shared conventions' [github-writes.md](../gh-workflow-conventions/references/github-writes.md) before any GitHub review write. Follow their live-state rechecks, atomic payload construction, verdict selection, anchor validation, sentinel rules, ambiguous-outcome handling, and exact post-write verification.

## Review Summary

End the posted review with blocking issues, nonblocking issues, questions, tests run and outcomes, and merge-readiness. Derive each finding count from the same structured inventory used to build the atomic review: count inline comments and marked review-body findings separately, and verify that their subtotals sum to the reported total before posting. Do not hand-enter a parenthetical breakdown that cannot be reproduced from that inventory. When reporting GitHub checks, summarize the latest/current run set for the reviewed head, and distinguish intentional `SKIPPED` checks from failures. If blocking issues exist, state: `I would not merge this until the blocking issues above are addressed.`

For author or draft COMMENT reviews with no findings, say plainly that there are no blocking findings, then state why the review is a COMMENT and any live remaining gate such as marking the PR ready or satisfying a reported review requirement. For author COMMENT reviews, do not claim that branch protection needs another maintainer approval unless GitHub reports that gate. If the COMMENT is only because the PR is draft or behind its base, name the gate that a reader can act on — mark it ready, update the base — and keep the reasoning about what this review does or does not satisfy for the response to the user. Prefer one sentence a maintainer would actually write over a paragraph of review-mechanics status; the posted-body voice rule in the shared conventions governs the phrasing.
