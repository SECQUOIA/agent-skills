# Worktrees, Checkouts, And Shared Local State

Part of **gh-workflow-conventions**. Read this before using temporary worktrees or scratch checkouts, probing merge results, or acting on a checkout other sessions may share.

- Prefer the primary checkout for edits and verification when it can be used safely. Unrelated untracked files do not automatically require a temporary worktree: identify them, confirm they neither overlap incoming or edited paths nor influence builds/tests, stage only explicit intended paths, and recheck status before committing. Use a temporary worktree when substantive tracked changes, overlapping or test-influencing artifacts, branch divergence or mismatch, concurrent activity, or filesystem permissions make in-place work unsafe. A preference for the primary checkout is not authorization to delete, hide, or relocate unrelated user work merely to satisfy a clean-tree gate; apply the cleanup rules in [change-hygiene.md](change-hygiene.md), and explain any temporary-worktree exception to an explicit user preference.
- If a test or import unexpectedly resolves files from another checkout (for example `module.__file__` paths under `/tmp` or a stale worktree), treat that as environment contamination. Re-run with the repository's documented wrapper, editable install, or source path override before counting the failure as a PR regression. Judge that by `module.__file__`, never by the paths printed in a traceback: a scratch tree copied with `shutil.copytree`/`cp -r` inherits the original's `__pycache__`, and Python reports the source path recorded in that bytecode, so a *correct* run against the copy prints frames pointing at the tree it was copied from. Exclude `__pycache__` when copying so provenance stays legible, and never conclude from traceback paths alone that a mutation failed to take effect — re-read the mutated line in the scratch file instead, since "the probe ran against the wrong tree" and "the guard is weak" are the two wrong turns this signature invites.
- When testing a throwaway worktree or checkout, verify that the imported module's `__file__` resolves to that tree. Editable installs, `site-packages` builds, and Python's first `sys.path` entry can select another copy: `python -c`/`-m` puts the current directory first, while `python <script>.py` puts the script's directory first, ahead of `PYTHONPATH`. Run from the intended worktree or use a script inside it, then verify the import. Check fresh child interpreters too: parent-only `sys.path`/`sys.modules` overrides do not reach tests that spawn Python. Propagate both source and scratch dependency paths through the child environment or an appropriate scratch install, and verify their origins inside a representative child before trusting subprocess results. A correct parent import does not validate the child.
- `PYTHONPATH=<worktree>` also does not reliably win against an editable install: `pip install -e` registers a `.pth` file or import finder that can resolve the package name ahead of the scratch source. To exercise a mutated copy of one file, load that file directly with `importlib.util.spec_from_file_location("<pkg>.<mod>_mut", "<scratch>/.../<mod>.py")` under a throwaway module name and assert the loaded module's `__file__` is the scratch path. A throwaway name only serves a check you write yourself; the repository's own tests still import the real dotted name. To run those tests against the mutant, register it under the real name (`sys.modules["<pkg>.<mod>"] = <mutant>`) from a scratch `conftest.py` or equivalent pre-import hook and assert the loaded `__file__` there. This stays within read-only checkout rules while proving red-on-base or red-on-mutation.
- A scratch `conftest.py` — or any helper the two bullets above have you materialize — written at the worktree or checkout root can silently overwrite a *tracked* file: many repos ship a root `conftest.py` carrying marker filters and collection hooks, so the clobber risks being committed and, worse, reruns the suite under altered collection rules while every test still passes, making the run's evidence quietly wrong. Before writing any shim into a worktree or scratch checkout, require the target path to be untracked (`git ls-files --error-unmatch <path>` succeeds only for tracked paths, so require it to fail), and re-check `git status` after writing. When the root already has a `conftest.py`, put the shim in a uniquely named module and load it with `pytest -p <module>` instead — that composes with the repo's own conftest rather than replacing it.
- When a scratch-copy check needs a dependency no available interpreter has, and `python -m venv` cannot bootstrap it (`ensurepip` missing, so the new venv has no `pip` and its `python` fails to import the package), do not fall back to the base environment. Install into a throwaway directory with `pip install --target <dir> <pkg>` using any interpreter that has `pip`, then run the check with `<dir>` prepended via `PYTHONPATH`. This provisions the dependency without polluting any project or base environment, and the directory is deleted with the rest of the scratch state.
- A fresh `git worktree`/checkout contains only committed files, so compiled build artifacts (PyO3/Rust `.so`, Cython/C extensions, generated bindings) are absent and imports fail with `ModuleNotFoundError` even when the code is fine. Before treating that as a real failure, reuse a prebuilt artifact or local executable from another checkout only when you can verify its build identity against the exact head or merge-result tree being tested. “The PR does not change native source” is insufficient: the copied binary can still predate base commits, generated bindings, or ABI/toolchain changes and produce plausible false failures or stale outputs. When the identity is not embedded or otherwise provable, run the repository's build step in the exact tree instead. Confirm both the imported module's `__file__` and the native artifact's build identity before trusting the result, and report the workaround and identity in the summary.
- Before removing a temporary worktree, `cd` back to the primary checkout first. If the shell's working directory is still inside the worktree when it is deleted, subsequent commands fail with `getcwd: cannot access parent directories` (a dead CWD) until you `cd` out. After removal, verify both that the path is gone and that `git worktree list --porcelain` has no stale entry. On a restricted filesystem, removal can delete the files but fail to update `.git/worktrees`; first retry `git worktree remove <exact-path> --force` with metadata-write permission so cleanup stays scoped to that worktree. Use the broader `git worktree prune` only if targeted removal cannot clear the stale entry, and audit the worktree list for unrelated prunable entries before pruning.
- When a write workflow uses a temporary worktree because the primary checkout is dirty, preserve the user's artifacts and re-read the primary `git status --short --branch` after cleanup. If the workflow advanced that checkout's upstream, do not treat reporting a behind count as a completed handoff: compare the dirty and untracked paths with the incoming path set and determine whether they actually block a fast-forward. The common trap is an untracked local file that the upstream now tracks; a later `git pull` aborts rather than replacing it. Preserve the exact local bytes in a clearly named stash restricted to the blocking path, fast-forward when the remaining tree permits it, and verify a second `git pull --ff-only` succeeds. Keep and report the stash when the local file differed, even if the difference was only whitespace. If substantive overlapping edits cannot be reconciled safely, leave them untouched and report the exact blocker; never overwrite user work merely to hide the behind count.
- A green check rollup at the PR head says nothing about the merge result once the base has advanced: those checks ran on a tree that does not contain the base's newer files. Probe the merge cheaply with `git merge-tree --write-tree <base> <head>`, which lists conflicted paths without touching a worktree (`mergeStateStatus: DIRTY` reports only *that* a conflict exists, never which files). Despite that read-like use, `--write-tree` writes a tree object under `.git/objects`; if it fails with a read-only or permission error before reporting merge content, retry the exact command with repository-metadata write permission before treating the probe as a conflict or unsupported. If it fails with `fatal: unknown rev --write-tree`, check `git --version` and fall back to the three-argument form `git merge-tree <merge-base> <ours> <theirs>`, which prints conflict-marked hunks and conflicted paths to stdout. Prefer that three-argument form outright in a read-only pass, whatever the git version: it resolves in memory and writes nothing, so a merge probe stays inside a no-write guarantee that `--write-tree` would quietly break by leaving objects in the repository under review. Then, whenever the PR deletes or renames a path — a shared test helper, a module, a fixture — grep the *current base* for remaining consumers (`git grep -n "<old-name>" origin/<base>`), because neither `gh pr diff` nor `git diff <merge-base>..<head>` can show a consumer that landed on the base after the branch point. If the grep finds any, build the actual merge and run the project's collect/build step: one stale import is not one red test, because an import-time failure is a collection/compile error that aborts the whole lane (`Interrupted: N error during collection` for pytest), so the suite reports far fewer passes rather than a single failure. Reporting that consequence, and the pass count after the obvious fix, is much stronger evidence than naming the conflict. Run the grep in the other direction too, and do not let "the PR deletes nothing" skip it: when the *base* removed or renamed an identifier while this PR was open, the PR's new code can still reference the old name, so grep the built merge result for the names the base retired (`git grep -n "<old-name>"` in the merge worktree, confirming against `origin/<base>` that it is really gone). That direction hides better than the first: git auto-merges the offending line with no conflict marker, so resolving every reported conflict still leaves a tree that will not load, and both the head's checks and the base's checks are green because neither tree ever contained the combination. Re-derive this every round rather than reusing another reviewer's result: on an active repo the base can move between review rounds and between reviewers, so cite the exact base tested and explain count differences as base differences when applicable.
- When reproducing a PR merge result via `refs/pull/<N>/merge`, that ref is GitHub-computed and can lag a recent base change (for example after the PR's base branch is switched): its base-side parent may still be the old base tip. Before trusting the reproduction, confirm the merge commit's base parent equals the current base tip (`git rev-parse origin/<base>`), or that their trees are identical (`git diff --stat origin/<base> <merge-parent>` is empty). If they differ, merge the head into the current base yourself instead of relying on the stale ref.
- Git's merge preferences such as `-X ours` and `-X theirs` operate on whole conflict hunks, not semantic changes, so they can silently discard distinct compatible additions that happen to sit beside an authoritative overlap. Remember that `ours` is the currently checked-out branch and `theirs` is the incoming branch; if an authority rule justifies using either option, treat it only as a starting resolution, compare the final tree and diff against both parents, and restore every compatible contribution. Ask before discarding distinct work when the requested authority does not settle the semantic choice.
- To inspect a PR head's files without checking it out, use `git show <ref>:<path>` for a single file or `git worktree add <path> <ref>` for broader browsing/testing. Give `git worktree add` an absolute path: under `git -C <repo> worktree add <relative-path>`, the relative path resolves against `-C`'s directory rather than the shell's working directory, so a scratch path such as `./wt-head` silently lands *inside* the very checkout the worktree was meant to leave undisturbed. Confirm placement with `git worktree list` after creating one; if it landed wrong, `git worktree remove <path> --force` and recreate it at an absolute path before running anything against it. Never run `git checkout <ref> -- .` (or any command that materializes another ref's whole tree) against the primary shared checkout — even when the intent is only to look, it stages that ref's entire file set into the working tree/index, silently producing a large dirty diff on a tree that was clean before. If it happens anyway, `git reset --hard HEAD` immediately restores the prior state, which is safe precisely because you checked `git status` was clean beforehand.
- When using a temporary worktree to avoid disturbing a user's dirty or unrelated primary checkout, prefer a detached worktree or clearly named temporary ref that cannot be mistaken for the PR branch. Record the user's original branch before starting, remove the temporary worktree after use, and delete any temporary local branch/ref once its commit has been pushed to the real PR branch. Before final response, recheck the primary checkout; if it ended up on a scratch branch, switch it back to the recorded original branch when clean, or clearly report why it was left there.
- Name a temporary worktree or scratch checkout with a valid Python identifier — the repository's own name is the safe default — whenever the repo root contains an `__init__.py` (legacy package layout). pytest's package detection walks upward past such a root, so the scratch directory's basename joins the import chain, and a hyphenated name like `pr130-wt` fails collection with `attempted relative import with no known parent package` raised from the root `__init__.py` — an error that reads like a broken PR, not a naming artifact, and that never reproduces in CI or the primary checkout. `git worktree move <old> <new>` repairs an already-created worktree in place.
- The primary checkout can be shared with another concurrently running session (a separate terminal, another agent invocation working the same PR) that switches branches or adds commits mid-task without this session doing so. If the local branch name or `HEAD` unexpectedly differs from what an earlier step in the same task established, treat that as evidence of external activity, not as damage to fix — re-derive conclusions from a fresh `git status`/`git branch`/`git log`/`git reflog` read rather than trusting the earlier, now-stale one, and only intervene if the user's actual request requires it.
