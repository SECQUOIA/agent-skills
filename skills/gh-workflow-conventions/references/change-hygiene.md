# Local Change, Commit, And Push Hygiene

Part of **gh-workflow-conventions**. Read this before modifying source, committing, pushing, handling generated or opaque artifacts, or allowing live credentials to influence repository output.

- When a workflow stops on a dirty tree and the user explicitly asks to clean it, clean only the identified blocking artifacts. Use tracked-file restoration only when the user's request clearly authorizes discarding those changes, remove only named untracked files/directories, and recheck `git status`. If an untracked local tool runtime path such as a bind-mounted `.codex`/`.claude` artifact cannot be removed, hide it with a local-only `.git/info/exclude` entry rather than changing repository `.gitignore`.

- When an unfamiliar untracked file blocks the clean-tree gate, classify it with read-only provenance checks before proposing deletion: inspect its header, type, and timestamps; search repository references, ignore/lint configuration, and Git history; and trace the likely generator when practical. Evidence that it is generated or regenerable informs the explanation but is not removal authorization. Obtain explicit user permission, remove only the named path, and keep unrelated repository ignore changes out of the task PR.

- Stage only intended files. Before pushing, inspect the staged diff (`git diff --cached --stat`) and stop and report instead of pushing if it includes credentials/tokens/secrets, large or binary/generated artifacts, or any file outside the planned set.

- `git diff` and `git diff --stat` omit untracked files. Before claiming the planned file set is complete, pair diff inspection with `git status --porcelain -uall`; then stage explicit paths and inspect the cached diff.

- When local verification needs live service credentials (API tokens, license keys, cloud credentials), pass them only through environment variables or the repository's documented secret mechanism; do not paste literal values into notebooks, config, review/comment bodies, or command output. After executing notebooks, report generators, or plotting scripts, recheck `git status` for untracked byproducts and search the changed artifacts for actual secret values when available, credential markers such as `Authorization`/`Bearer`/literal token assignments, local absolute paths, usernames, host-specific scratch paths, or stale source checkout paths before staging. Remove only the generated byproducts that the command created and sanitize committed outputs to repo-relative paths when the diagnostic is worth keeping.

- Once a credential is committed and pushed, neither deleting it in a new commit nor rewriting history removes it, and reporting the leak as remediated on local evidence is the failure to avoid. `git filter-repo` exits successfully while the blob stays reachable through refs it does not rewrite — an agent or editor plugin's own refs (`refs/codex/*` and similar), the stash, reflogs — so confirm removal with `git rev-list --objects --all | grep <path>` and `git cat-file -e <blob>` after expiring reflogs and `gc --prune=now`, never from the rewrite's exit status. The remote is worse: after a force-push GitHub still serves the old commit (`contents/<path>?ref=<old-sha>` returns the file), and `refs/pull/N/head` pins pre-rewrite commits for every PR ever opened and cannot be deleted. Rotating the credential is the only remedy wholly in the user's hands; when it cannot be rotated — an institutional licence file is the usual case — only GitHub Support can garbage-collect the unreachable objects, so draft that request citing the leaked path and introducing commit, and tell the user to keep the repository private until `contents/<path>?ref=<old-sha>` returns 404.

- Before editing a notebook in a repository that commits outputs, identify *which* file carries the published ones. A repo commonly tracks `<name>.ipynb` complete with its outputs while gitignoring the `<name>_output.ipynb` that its notebook lane executes into, so the copy you may freely regenerate is not the copy readers see, and the ignored one's name is what makes it look like the executed artifact. Editing only the cell sources then publishes a page whose rendered output contradicts them, and nothing reports it: the lane passes by re-executing into the ignored copy, and no check compares committed outputs against the sources that produced them, so a full local suite and every green check can sit on top of the stale page. Re-execute into the tracked file and commit that, reproducing the invocation the committed file's own metadata records (`metadata.papermill` stores the `parameters` and paths of the run that produced it) rather than copying the test's call, whose explicit parameters inject a cell the committed artifact does not carry. Confirm the result is outputs-only by diffing every cell's source against the previous commit, and propose a check that fails when committed outputs and their sources disagree, since none of the existing lanes can see that.

- When a repository commits executed notebook outputs and those outputs record the source revision that produced them, execute-then-commit records the *parent*: the run reads `HEAD` before your cells are committed, so the recorded SHA does not contain the code that just ran. Commit the cell sources first, re-execute at that commit, then commit the regenerated outputs as a separate output-only change. Verify the split by comparing cell sources across the second commit — they must be byte-identical — and by confirming the recorded SHA is the commit that introduced the executed cells. The same ordering keeps the reviewer's provenance check meaningful; without it the recorded revision points at a tree that lacks the section it claims to have produced.

- Preserve existing line-ending conventions in touched files unless the PR intentionally normalizes them. If a file has mixed or legacy CRLF endings, inspect the real diff with `git diff --ignore-cr-at-eol` and either keep edits line-ending-consistent or move normalization to an explicit separate change. The churn is often introduced by the editing step itself: a tool that rewrites the whole file normalizes every line to one ending, so a change to two lines shows as dozens of `-`/`+` pairs whose content is identical. After editing a mixed/CRLF file, diff with `--ignore-cr-at-eol` to confirm only the intended lines changed; if the tool churned endings, re-apply the change at the byte level (preserving each original line terminator) rather than committing the normalization. For CRLF-tracked files, check `git ls-files --eol <path>` before staging; if it shows `w/mixed`, normalize only the touched file back to its tracked line ending and rerun the CRLF-aware diff check. This also applies to throwaway mutation probes: a read-modify-write script can normalize the target file even when it later restores the original text. Prefer a read-only emulation of the mutation, or use a line-ending-preserving edit and re-check `git ls-files --eol` after each probe.

- Editing a committed `.ipynb` — or any pretty-printed JSON artifact — by parsing and re-serializing rewrites every line unless you reproduce that file's exact serialization. Writers disagree within a single repository: some notebooks are `json.dumps(..., indent=1)` and others `indent=2`, and `ensure_ascii` and the trailing newline vary too, so a guessed setting turns a two-line edit into a whole-file diff. Nothing catches it — the notebook still parses, the tests still pass, CI stays green, and only the review drowns. Detect the style per file rather than assuming: re-serialize the *unmodified* parsed object under each candidate setting, keep the one that reproduces the original bytes exactly, then apply the edit and write with that setting. Confirm with `git diff --stat` that the changed-line count matches the edit you intended.

- A tracked binary or opaque artifact (`.docx`, `.pptx`, `.xlsx`, and any file with no textual merge) is rewritten whole by the application that edits it, so an edit made while the branch is behind its base silently reverts everything that landed on that path meanwhile. Nothing local reveals it: `git status` says only "modified", the diff is unreadable, and the edit itself looks correct — the loss surfaces, if at all, as a merge conflict long after. This bites hardest when a human is handed the file to edit in Word/PowerPoint, since their edit lands on whatever stale copy the working tree held. Refresh the base and fast-forward or merge it into the branch *before* such a file is opened for external editing, and before committing one that was edited out of band. When it turns out to be stale, do not commit it and resolve later: rebuild the edit on the base's current version, then verify by extracting text from both (python-docx/python-pptx paragraph sets) and confirming the only differences are the intended ones. Choosing "ours" on a conflict in such a file is the same data loss wearing a resolution's clothes.

- A string replacement inside a hard-wrapped prose block — a Markdown paragraph, a docstring, a comment block — changes that block's line lengths, so rewrap the whole paragraph in the same edit instead of leaving one over-long or ragged line. Anchoring the replacement on a single line is what produces the ragged result: the new text lands mid-paragraph while every following line keeps its old break, and each leftover line then costs another edit. It is not only cosmetic — a code line that grows past the repository's formatter or linter limit fails the style check — so re-run the repo's formatter and lint on the touched files afterward and read the diff to confirm only the intended lines moved.

- When whitespace-checking an untracked file with `git diff --no-index --check /dev/null <file>`, exit 1 can mean only that the files differ even when no whitespace diagnostic was emitted. Prefer staging planned files and running `git diff --cached --check`; otherwise judge the no-index check by its diagnostic output, not that expected difference exit alone. `git diff --check` has a second false positive, and this one reads as damage you just introduced: in a CRLF-tracked file it flags *every* added line as `trailing whitespace`, because the CR before the newline is trailing space under the default `core.whitespace`. Confirm the file's tracked endings with `git ls-files --eol <path>` (`i/crlf` is the tell) and compare an untouched earlier commit (`git show --check <sha> -- <path>` flags the same lines at the same rate) before acting on it; then preserve the file's endings and rerun the check with `core.whitespace` including `cr-at-eol`. Never strip the CRs to silence it — that is a whole-file line-ending normalization wearing a whitespace fix's clothes.

- On a rerun of an existing branch with a clean tree and nothing to stage, treat it as an already-applied no-op: do not create an empty commit (no `--allow-empty`) and do not treat the non-zero `git commit` exit as a failure.

- For multi-paragraph `git commit` messages, use separate `-m` arguments for each paragraph or a message file; do not put escaped `\n` inside a quoted `-m` argument, because Git records the backslash and `n` literally. After committing, skim `git log -1 --format=%B` when the body contains issue-closing keywords or shell-sensitive text, so a malformed body is caught before push or PR creation.

- If a push returns a transport error after the request may have been dispatched (for example `unexpected EOF`, a timeout, or a connection reset), treat the outcome as ambiguous. Do not blindly retry or report failure: first re-read the affected remote ref. If the intended state already applied, continue with normal verification; if it did not, re-run any required live precondition and retry once under the applicable network-escalation rule. For a definite validation/permission rejection or a second failure, report the exact error and stop.
