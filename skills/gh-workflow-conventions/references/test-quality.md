# Test Quality And Coverage

Part of **gh-workflow-conventions**. Read this before verifying behavioral, scientific, or coverage claims, judging tests, or running mutation/parity checks.

- Verify behavioral claims at the layer users consume by running commands, imports, tests, or entry points when practical; green CI is supporting evidence, not a substitute for a cheap targeted check. When source passes through a renderer, compiler, or generator, inspect the built artifact's semantics rather than only source invariants or a successful build: a transform can synthesize or promote a node while retaining the source node, yielding duplicate output from one source occurrence with every source test green. Check every affected artifact in a repeated cohort, and when practical keep both source-structure and artifact-level regression guards.
- For README badge or link changes, validate the exact-head file through GitHub's renderer, not only the source: `gh api markdown/raw --method POST -H 'Content-Type: text/plain' --input README.md`. Inspect the rendered anchors and images, then fetch the badge SVG and confirm its `aria-label`, `title`, or visible text; HTTP 200 alone does not prove an encoded label rendered as intended. For external images rewritten through `camo.githubusercontent.com`, fetch both the canonical `data-canonical-src` and the exact rendered Camo `src`. If the canonical asset now works but Camo was stale, re-fetch the Camo URL and re-render before editing: a cache miss that returns the valid SVG is transient proxy/browser state, while a persistent Camo failure warrants a stable provider or cache-busting URL change.
- When adding or editing embedded BibTeX, compare every author name with an authoritative record such as Crossref or the publisher. Use unambiguous `Family, Given` forms for compound family names, then run a BibTeX parser/style and inspect the generated names or labels; source text that looks correct can still be parsed with only its final token as the family name.
- When a pushed fix changes parsing or validation of a credentialed or paid live-service response, an earlier provider run is historical interaction evidence, not current-head end-to-end validation. Rerun only when authorized and proportionate; otherwise record the old run's exact SHA separately and prove the new pure validation on the current head with credential-free fixtures. Never combine those two evidence sets into a current-head live-success claim.
- When an acceptance criterion requires execution in a hosted runtime or UI, source guards, bootstrap contract tests, and local emulation do not satisfy it. Run the hosted target when authorized and practical; otherwise leave the criterion explicitly partial or unverified, state the exact surrogate evidence, and obtain maintainer acceptance before claiming completion or merge readiness. Before asking a maintainer to run the hosted target manually, determine whether the defect can be enforced automatically with a faithful surrogate: execute the exact user-facing source through the same runtime or kernel protocol, reproduce the relevant environment markers and version mismatch, assert required milestones and forbidden output/error classes, and mutation-test each reported defect class. If the maintainer explicitly accepts that surrogate as the merge gate, document which hosted infrastructure remains unverified and do not reintroduce the manual run as a prerequisite.
- When an expensive operation has already returned a usable core result, treat a later diagnostic, status, or provenance sidecar as optional unless the public contract says otherwise. A missing or malformed sidecar must not convert the completed solve/build/call into a failure or discard its result: emit a diagnostic, preserve the core result, and fall back to the classification available from that object. Test absent and malformed sidecars separately, then exercise the serializer or report consumer with the metadata omitted; a unit test of the sidecar reader alone does not prove the completed-result path survives.
- When a change replaces a third-party dependency with a first-party reimplementation (vendoring a client subset, forking a helper, dropping a package to break a version conflict), the load-bearing claim is parity, and a passing suite cannot establish it because the tests were written against the replacement. Verify it directly: install the real dependency into a scratch environment, import it alongside the replacement, and diff their outputs for the *repo's actual call patterns* rather than a generic smoke test — every request body, converted payload, and assembled response the repo produces, including edge inputs (empty, single-element, all-default, and a size that crosses the chunking or pagination boundary). Read the upstream source for the surfaces a diff cannot reach (retry/backoff constants, exception message formats a caller parses with a regex, header construction, defaults such as compression) and confirm each matches. Separately test the premise that justified the replacement against the *newest* upstream release, not the version the issue names: an issue asserting "upstream pins X" can be stale, and if a newer release already relaxed the constraint, bumping the bound is the correct change and the reimplementation is avoidable debt. Report parity evidence as out-of-band and recommend an in-repo equivalent (a test lane, a pinned comparison), since nothing in the repository reproduces a scratch-environment diff once the session ends.
- When a PR or its body claims a changed file is comment-only, docstring-only, or formatting-only, verify that mechanically instead of skimming the hunks: parse both revisions and compare the code structure with docstrings stripped (for Python, compare `ast.dump` of each parsed tree; other ecosystems have equivalent AST or canonical-formatter tools). A claim that holds lets you review the file as documentation and report that scope with evidence; a claim that fails surfaces a behavior change hidden inside annotation churn, which is exactly the diff a reader is most likely to skim past.
- A lockfile diff is not readable evidence. Regenerating a lock can reorder shared package lists, so thousands of changed lines may hide a single environment change or a real removal. When a PR claims other environments stayed untouched, compare the lock structurally one environment block at a time and report evidence in that form, for example "`default` and `assimulo` byte-identical; one docs block added." Use the same extraction to verify what a new environment actually pins.
- Treat dependency-rationale prose as falsifiable, especially when a reviewer asked for it. Check claims like "X needs Y at build time" against the dependency's own metadata, the committed lock entry, and the source path that actually uses it; do the same for your own review findings before posting them.
- For scientific or numerical changes, trace units across every changed calculation and caller-to-callee boundary. Document input, intermediate, and output units at the smallest useful public or conversion boundary, using the repository's notation convention; add dimensional or unit-sensitive assertions when practical so a missing conversion cannot remain green. When a changed function lacks adequate argument/return documentation, add or update Numpy-format documentation for the changed function and its arguments, using real sections such as `Parameters`, `Returns`, and `Notes` where useful rather than prose-only units notes. When adding variables in code or tests, annotate each new namespace variable, fixture value, computed intermediate, and returned value assignment with units where not already obvious, including dimensionless quantities as `[-]`; do not leave units only in the PR body. Unit-bearing variable names are not a substitute for documentation: when a changed test file introduces scientific fixtures, local test-double classes, constructors/methods, helper callbacks, or expected values, add module/test/helper docstrings or adjacent comments that state the regression contract and units or `[-]` basis in the test file itself. Before finalizing, perform a named units/docs/comments audit over the full changed diff and adjacent call path: check public contracts, helper callbacks, residuals, normalized quantities, test fixtures, expected values, and derived intermediates, not just the specific variable that caused the bug.
- When a scientific PR ships a machine-readable parameter, training, or provenance table, treat the table as an API contract rather than prose. Parse it with the declared delimiter and schema; verify every row has the expected field count, range-only values are encoded consistently, units and target/type columns match the physical quantity, and any plan-required dimensions such as optimizer units, regions, zones, scenarios, or technologies have explicit rows or explicit unavailable/assumed rows. Hidden defaults in downstream text are findings even when the narrative explains them. The row-width check matters most when a header gains a field its rows never carry: name-based readers such as pandas do not error on the mismatch — they pad the *trailing* column with NaN and silently shift every interior column, so a downstream consumer reads a plausible wrong quantity under the right column name (a Hamming-distance panel fed objective values, say) while everything stays green. Assert header/row width at the producer that writes the table, not only in downstream review, and re-check any consumer that read the table while the schema was skewed.
- When you edit a delimited data file, a value or free-text field you touch must not contain the delimiter itself: subscript notation (`[u,z]`), thousands separators (`3,000`), and prose commas can silently add a column. Re-parse the whole file after each edit for row count and field width; use a delimiter-safe form, a semicolon, or a quoted field.
- When a literature-backed deliverable makes a quantitative or attributed claim — a figure, equation, screening limit, or "paper X reports Y" — trace it to the exact primary source and location before writing or keeping it: fetch and read the cited document, and follow the reference chain to the origin, because a paper that only *cites* a value (for example "see Table 5 of Ref. 16") is not its source, and a relation charted or applied by one author may be *defined* by another. Attribute each claim to the document that establishes it, with page/table when practical, and keep a dataset-specific range (e.g. a re-evaluation set's viscosity span) scoped to that dataset rather than restated as an original method's calibration bound. Never leave an unverifiable figure in the text behind a "not verified" hedge: either confirm it against the primary and cite it, or remove it — a flagged-but-unverified number is an artifact, not a citation.
- A deliverable that claims to *replicate* a published instance is not verified by reproducing that instance's inputs. Look up the source's own reported result and compare it against the run, even when the document never cites it — the replication framing is what makes the comparison owed, so its absence from the document is the defect rather than a reason to skip it. Inputs verified value-for-value plus a self-certified optimum only reproduce your own model: a network whose topology, capacities, costs, and demands all matched the source's figure and tables still certified 148.1 against the source's certified 183.5, exposing a formulation difference no input check could surface and which was headed for a manuscript as a replication claim. Before naming a cause, check whether the gap patterns across instances — agreeing on several and diverging on others localizes it far better than a single discrepancy. When the document further attributes a changed result to one input edit rather than to solver or hardware drift, test that attribution directly: rebuild the superseded input, re-run it in the current environment, and confirm it reproduces the old value.
- For analytical, reduced-order, or piecewise physical models, audit semantic normalization as well as units. Name each numerator, denominator, and inventory basis (for example total, contacted, mobile, recoverable, or remaining) at equation boundaries; verify a hand-computable conservation identity in every piece, especially the initial linear regime; and test continuity, interval ordering, bounds, endpoints, and singular or favorable parameter regimes across every range the public contract admits. A dimensionless equation can still double-count inventory or invert its piecewise regions.
- When equations, prose consistency gates, and committed parameter or schema tables describe the same contract, execute every gate against the committed rows and verify that field names, units, semantics, and granularity match downstream consumers. A stated validation rule is not evidence when the shipped example violates it.
- When review feedback asks for tests on a planning, schema, or design-document PR whose changed files are not implementation, read the owning issue and PR scope before classifying the fix. If the deliverable is the plan itself, a concrete test contract plus machine checks of shipped tables may address the comment, but report that executable regression tests remain downstream. If the PR claims implementation readiness, changes code, or the issue acceptance criteria require tests now, absence of committed tests remains a finding.
- Unit notation belongs in comments and docstrings, not in runtime *values*. A units audit that rewrites a string literal — a `units`/`label`/`symbol` entry in a metadata dict, a constant, a config field — is a behavior change wherever something downstream renders, parses, or compares that string, and it is precisely the kind of change no test covers. Before touching such a value, grep its consumers (a plotting or reporting layer that concatenates it into an axis or column label is the usual one) and compare the same field across the repo's other modules. A notation that ends up appearing in one file and nowhere else in the package is a regression, not a normalization — annotate the surrounding code instead and leave the value alone. Beware too that an empty or absent value is often the deliberate way a renderer is told to suppress a suffix, so "adding the missing `[-]`" can introduce output where there was none.
- When a scientific or numerical review fix also merges or rebases the base branch, repeat the units/docs/comments audit after conflict resolution on the final merged diff and call path. Treat upstream changes as part of the current contract: a newly landed helper may change a basis, denominator, or expected value, so comments and tests must be checked against merged behavior rather than the pre-merge PR head.
- For time-averaged rates on multiplicative quantities (production decline, growth, returns, conversion factors), do not use an arithmetic mean of percentage changes unless that is the explicit domain convention. Use log/geometric/compound averaging over the actual interval lengths so the summary rate maps the first value to the last, and add a non-uniform path test (for example decline then recovery) because uniform-step fixtures can make arithmetic and compound averages coincide.
- When a commented or conditional source edit is required to leave a generated document unchanged, preserve a pre-edit build, rebuild after the edit, and compare semantic and rendered output. For PDFs, compare page count, extracted text, and rasterized pages; binary inequality alone is not evidence of a rendering change because creation timestamps and other metadata can differ. For OOXML templates, also inspect section breaks and header/footer inheritance: appending content inside a cover section can repeat cover branding on every page even when the original package parts remain byte-identical. Render with the target office engine, inspect every page, and report body-page count separately from excluded cover and reference pages.
- For PDF layout or table-fit claims, neither a clean TeX log nor a source-level tabular width proves the built page fits: captions and notes can make a landscape stack too tall, while a rotated float can cross the physical `MediaBox` without an overfull warning. Reproduce any reported dimensions with the document's exact class, preamble, type size, and spacing; then measure the final PDF's per-page text/vector/raster ink bounds against the `MediaBox` and required margins, rasterizing borderline pages. Treat a direct portrait-to-landscape height overflow as evidence that the float needs reflow or splitting, not that genuine landscape is impossible. Where the layout is maintained, commit the page-boundary measurement as a regression guard.
- When a PR claims its committed tables, figures, or summaries regenerate from repository data, verify in a fresh `git archive` or detached worktree, not the author's checkout: run every generator there and require a zero diff against the committed artifacts. Generator scripts that silently read gitignored run directories pass in the author's tree and then *clobber* the committed artifacts with empty or placeholder output in a fresh clone — so the acceptance has two halves: the canonical inputs (including any solve caches, keyed by repo-relative paths so they hit outside the original checkout) must be tracked, and each generator must fail closed, refusing to overwrite a committed output when its inputs are absent, rather than writing whatever it found. When the repository test implements this check with `git archive HEAD`, its evidence is commit-dependent: put the candidate artifacts in `HEAD` (a real or temporary commit) and rerun after every artifact commit, because a pre-commit pass archives the parent tree and can stay green while the working-tree binaries are wrong. Byte identity for binary outputs may need the toolchain's determinism switch (for example `SOURCE_DATE_EPOCH` for PDF creation timestamps); turn the whole check into a repository test so it keeps guarding after handoff. When the output is an archive container such as OOXML, EPUB, or JAR and whole-file bytes differ solely because ZIP timestamps, entry order, or compression differ, compare the complete member inventory — including duplicate occurrences — and every member's uncompressed raw bytes without normalization, then run the format's structural validator and rendered or consumer check. Report that result as “package members byte-identical,” never “artifact byte-identical”; excluding or normalizing members proves only a scoped semantic comparison. A determinism switch covers only what the toolchain stamps, and recomputed values are the other half: anything reaching a committed artifact through a floating-point library — a least-squares or optimizer fit, a derived constant, a decomposition — depends on the BLAS/LAPACK build under NumPy/SciPy and differs in its last bits between CPUs, so an artifact that regenerates byte-identically on your machine can differ on a CI runner with identical library versions. Matching versions on both sides is the tell that the data moved rather than the renderer, and a sibling artifact built from committed coefficients staying stable while the one that refits does not confirms it. Round at the artifact boundary — the values written or plotted, to a precision far below anything the artifact conveys — and never in the shared computation that models or published results depend on. Narrowing the comparison instead, or excluding the offending file, trades a real guard for a green one. One trap defeats this check before it starts: `git archive` stamps every extracted file with the same mtime, so a timestamp-driven build tool (latexmk, make, and any generator with an up-to-date test) concludes its targets are current and performs no work, printing something like `All targets are up-to-date` and leaving the committed artifact in place — which then trivially matches itself and reads as a reproduction. Force the rebuild (`latexmk -gg`, `make -B`, or delete the target first), and confirm the tool actually reported writing the artifact before comparing hashes.
- For an explicitly requested expensive or licensed benchmark sweep, define a bounded matrix and comparison baseline before running. Pin the evidence to the exact head, environment and solver versions, time/resource limits, and effective settings observed in solver logs rather than only the requested CLI flags; cross-check summaries or manifests against the raw run artifacts. For JIT-compiled workloads, warm every compared path symmetrically and separate first-use compilation or setup from warmed repeated timings. When reporting an aggregate such as median wall time, bind result and solver metadata to the same selected repetition or aggregate each field under a stated rule; never pair the aggregate duration with the last repetition's objective, status, iteration count, or internal elapsed time. Report mixed or absent improvements and comparison confounders honestly—especially different thread counts, stopping criteria, or iteration counts—and do not make cross-configuration runtime claims when those controls differ. Keep transient solver outputs untracked unless the task requires a durable fixture.
- Fixing a bug in artifact-writing code mid-sweep does not heal the sweep: processes launched before the fix keep executing the old module for hours and keep emitting the broken artifacts (truncated sidecars, mis-serialized values) alongside good ones from later launches. When such a fix lands while runs are in flight, record the fix time, classify every artifact by whether its producing process started before or after it, and re-capture or explicitly exclude the pre-fix artifacts — a downstream consumer cannot tell the generations apart, and a parse-and-skip fallback quietly hides how much of the sweep is degraded.
- For staged performance claims, report the baseline, each intermediate stage, and final timing in a table with each stage's speedup, absolute time removed, and share of the total staged time savings. Compute that share from absolute deltas (`stage input - stage output` divided by `baseline - final`), not by comparing or multiplying speedup factors. Put optimizations measured against different baselines or execution conditions in a separately labeled non-additive table, and distinguish isolated computation gains from end-to-end wall-time gains.
- For regression tests, make the expected value independent of the implementation under test when practical: use hand-computed literals, fixtures, or an alternate calculation instead of duplicating the same expression that production code uses.
- Do not assert a numeric tolerance tighter than the slack the toolchain is entitled to take. A bound that was tuned until one local build passed is pinned to that build and fails on another for reasons unrelated to the code — a solver permitted to sit `bound_relax_factor` outside a constraint reports a violation proportional to the bound's magnitude (1e-8 against a 243 K limit is 2.4e-6 K), so a hand-picked 2.0e-6 K assertion is not a stricter test, only a more fragile one. Derive the tolerance from the setting that produces it and name that setting in a comment, so the number moves with the configuration instead of being re-tuned on each failure. When such an assertion does fail, check the governing setting before loosening: the fix is a bound with a stated basis, not a larger constant. Check the assertion's *direction* first, though, because deriving a tolerance is the wrong repair for a bound that points the wrong way, and it hides the defect behind disciplined-looking work. A one-sided bound near an equilibrium (`outlet <= utility_temperature`) is decided by the model, not the solver: an exothermic reaction against a cooling utility crosses that temperature and relaxes back toward it *from above*, so the residual's sign is a property of the fixture and a passing run on the author's machine by 4e-12 was luck. Probe which side the model actually approaches from — print the profile, count the points on each side, find the crossing — before touching the constant. When the direction is wrong, delete the bound and record the measured behavior; when it is right, then derive the tolerance. A companion equality assertion (`approx(target, abs=tol)`) usually already carries the real claim and makes a slackened one-sided bound redundant anyway.
- When a cadence, period, stride, or frequency option controls modulo or repeated scheduling, validate its type and positivity at the public boundary before using it. Test zero and negative values separately: zero otherwise leaks a low-level division error, while a negative value can silently produce a schedule that never triggers.
- Before adding a regression guard, name the defect class it prevents and ask whether that class can recur. Correcting a one-off fact — a misspelled author name, a wrong citation title or venue, a fixed typo — does not create a recurring class, so pinning the corrected string guards nothing while converting future legitimate edits into failures. Prefer guards over relationships that must keep holding (two artifacts that have to agree, an invariant a plausible future change could break) rather than over values that were merely wrong once. A test asserting that documentation contains particular words, that a source file still contains a particular line, or that a build file still names a target the build itself would reveal as missing, is in this category. When a reviewer or author calls such a guard overkill, that is usually right: keep the correction and drop the test.
- Keep regression suites lean without weakening their contract. Remove assertions guaranteed by constructors, types, or earlier checks; preserve assertions that distinguish behavior, ordering, state carryover, and boundary handoffs. Consolidate duplicate expensive setup or solver calls into a mixed scenario that exercises both the trigger and no-trigger paths when practical, and compare the expensive-call count before and after so reduced runtime is evidence-backed rather than assumed. Attributing a runtime *increase* needs the same evidence and is easier to get wrong, because the intuitive reading is that consolidation caused it: under a parallel runner (pytest-xdist `-n auto` and equivalents), deleting short tests can raise wall-clock time by leaving the scheduler less filler to pack around the long poles. Compare per-test durations (`--durations`) before blaming the diff — unchanged per-test times under a worse total is a scheduling artifact, not a regression, and reporting it as one is a finding the author can refute from the same log.
- When replacing a hand-written expected-value table with a fixture or snapshot, inventory every enforcement direction before deleting the table. A record-to-fixture loop proves that present records are correct, but not that every actual source-to-current divergence still has a record. Delete one record while leaving its changed data in place and require the suite to fail; prefer deriving the complete changed-key set and comparing it bidirectionally with the documented keys, counting both old and new keys for moves or renames.
- When a PR removes or consolidates tests, measure line coverage before calling the suite contract-preserving when the coverage pipeline is available. Use exact base and head refs with matched runtimes and dependencies, and compare covered and uncovered source-line identities as well as totals; equal percentages can hide different lines. Report lower assertion or execution counts separately from binary line-coverage changes, and do not treat a successful coverage-upload step as a coverage verdict. Line identity is still not the whole contract, and this is where an author's "line-for-line identical coverage" claim quietly overstates itself: a deleted test can have been the only one taking the *false* side of a condition, and every line stays covered because the line still executes. Read the repo's coverage config first — branch coverage is off by default and many projects never enable it (`branch = True` / `--cov-branch` absent), so the pipeline the author ran could not have detected the loss. Re-run both refs with the branch flag yourself and compare branch-arc identity too; nothing in the totals reveals the gap.
- For executable benchmark or report fixtures, derive residuals, objectives, and comparison metrics from the constructed model or raw fixture instead of restating them as coupled constants. Expose those raw values and assert independent hand-computed literals so a fixture edit cannot silently desynchronize the reported conclusion.
- When a change introduces or moves initialization, seeding, conversion, normalization, routing, or validation state that a downstream function or executable artifact consumes, audit alternate paths before testing only the nominal handoff. If a per-item guard sits inside a dispatch loop, grep for fast paths, pre-passes, caches, and writers of the "already handled" registry or skip key the loop honors; those paths bypass the guard and must enforce the same contract at their own site or be excluded. Add a caller-to-callee or producer-to-consumer test, including a fixture routed through each relevant bypass, and when practical mutate the transfer, early return, or fast-path guard so the test fails. A guard *outside* the loop fails the same way with no bypass involved: its condition can simply under-cover the entries, which is hardest to see when the matrix draws per-entry defaults from a table (a `_defaults(case)` helper returning a different algorithm, backend, or dependency per case). Derive what you run from that table — enumerate its distinct combinations and exercise one entry per combination — rather than generalizing from whichever entry you or the author already ran, since the guard was written against that one. A preflight keyed on `global_search_method == "solver"` skipped solver resolution for the one case whose default *algorithm* required that solver regardless, so it died mid-run instead of failing fast while the suite, CI, and a one-entry smoke run all stayed green.
- When a fix generalizes a hardcoded assumption into a parameter — a residual or correlation that silently assumed one operating case, a constant that becomes an argument — the single new fixture proves the new case works but says nothing about the other two risks. Confirm the new form reduces *exactly* to the old behavior at the previously-assumed value: that is the no-regression proof for every existing caller, and an existing test pinned at that value demonstrates it cheaply. Then sweep the parameter across its physical range and check both that the solve stays well-conditioned (converged flag, residual magnitude) and that the result moves in the physically expected direction; one fixture point cannot show the generalized form is stable or correctly signed. Settle the convention against the repository's own consumers rather than the textbook — whether a quantity is a liquid or vapor fraction, or which component a ratio is taken relative to, flips the sign of the fix, and the repo's existing uses of that symbol are the authority even when a standard convention exists.
- When a refactor PR adds structural/count assertions only to prove extraction parity with an existing implementation, document that scope in the test or nearby docs/PR body. Do not present component counts, generated equation counts, or similar scaffolding checks as permanent scientific/modeling invariants; say when future intentional formulation changes should update or replace them with behavior tests.
- For shape or broadcasting regressions, avoid fixtures where distinct semantic axes have the same length (for example nodes and components, rows and columns, or sources and targets). If review feedback flags this ambiguity, first try making the axis lengths unequal and adding a short clarifying comment while preserving the PR's scope; defer only when the unequal-shape fixture would require an out-of-scope behavior change. When applying that fix, re-check every axis pair rather than only the flagged one — raising a node count from 2 to 3 can clear a nodes-vs-volatiles collision while creating a nodes-vs-components one, trading the ambiguity rather than removing it. Where a collision is unavoidable in the asserted output, confirm the expected values are asymmetric enough that a transpose is still caught by value rather than by shape, and mutate (drop a `.T`) to prove it; report that as the reason the remaining collision is benign. For numeric fixtures whose intended behavior requires nonintegral values, also inspect the constructed dtype and values after copy/`zeros_like`/assignment paths: integer-derived arrays can silently truncate fractions and turn an apparently asymmetric case structurally degenerate. Assert the resulting coefficients or nonzero pattern, not only the input literals.
- When a fix changes a magic-string/enum value or its casing convention (a `oper_mode`, status, or type sentinel), grep the whole repo for every producer and consumer of that value — assignments and `==`/`!=`/`in` comparisons alike — before trusting it. The real evidence the fix works is that the new value matches what distant consumers expect (routing in a flowsheet/connection or exec layer, not just the changed class), and that no stale-convention occurrence remains in scope; a repo that mixes conventions elsewhere (for example a lowercase sentinel in an unrelated module) is a latent bug to note, not to silently adopt.
- When a change turns a previously-accepted input into a hard error — new validation, a raised `ValueError`, a tightened type or enum check — on a public constructor or entry point, enumerate the existing call sites before judging it safe. Grep the repo for every construction or call passing that argument, including examples, notebooks, and tests. The change is only additive if no in-repo caller passes a now-rejected value; if one does, the fix trades a silent wrong answer for a crash in working code, and the tests written for the new validation will not catch that, since they only assert the rejection. Report the enumeration as the evidence, not the fact that the suite is green.
- A constant that encodes call-chain depth — `warnings.warn(..., stacklevel=N)`, `sys._getframe(N)`, `inspect.stack()[N]`, or a fixed skip count in a logger or traceback trimmer — is only correct for entry points whose chain is exactly that deep. Enumerate every public entry point that reaches the line and exercise each one; an inheritance chain with both direct and indirect callers may need `N` and `N+1` at the same site, and a one-entry-point test pins only the case that already worked.
- When a PR adds, renames, or widens public API such as methods, constructor keywords, or user-visible defaults, make the compatibility policy explicit before calling the item procedural or complete. Prefer one canonical name or keyword, preserve old entry points as deprecated aliases when existing callers should continue working, emit and test the deprecation warning plus returned behavior, and update docs with a compact public-API/compatibility map. Put that map in the initial PR body when creating the PR or in a new PR comment when the PR already exists; do not rewrite existing PR text unless the user explicitly requests it. For numeric defaults, state units or `[-]` and whether the value is an equation term, an empirical constant, or only a configurable design/default choice. When an optional value or sentinel selects a mode, exercise one reusable instance through default → set → documented off/default sentinel and both resulting modes, while asserting unrelated settings survive the clear; a getter default that its setter rejects is a broken lifecycle even when fresh-instance tests cover each mode.
- When a core result or sample changes element type, inventory strict boundary adapters (typed third-party constructors, serializers, solver interfaces) and exact-output documentation. Keep any compatibility conversion at the narrow adapter that requires it, then run examples to refresh pinned output text instead of predicting how the new type prints.
- Do not accept a test because it is green and well named. For a regression test, prove it fails without the fix: in a scratch copy, delete the fix (or feed the test the pre-fix input the issue describes) and re-run — if it still passes, the test does not guard the regression, and that is a missing test for changed behavior no matter what the test is called. For a test-only PR stacked on the branch that carries the production fix, the fix is not in the PR's own diff: mutate the base production code the test depends on (using the throwaway-module loader under Worktrees, Checkouts, And Shared Local State when an editable install would otherwise win), since there is nothing in the diff to delete. When a review finding asked for coverage of a specific branch or behavior, also confirm the test actually enters that path: check the fixture/stub/mock state satisfies the branch's guard (for example a stub whose `outputs` is a dict so an `isinstance(instance.outputs, dict)` branch is entered) and that the pre-fix code shape would have failed the new assertion. The usual causes of vacuously green tests are an expected value that recomputes the production expression, a fixture passed straight to the function under test so the real call path never runs, and a stub that never enters the target branch. Report the mutation and its before/after result as evidence instead of merely asserting the gap. When that evidence goes into a comment posted to the PR — not just your own reasoning — spell it out in plain language: name the mutation performed, and state that the test *failing* is the intended, reassuring outcome. A compressed line such as "Mutation: re-add `/(1-satur)` → Caught (3/9 mismatched)" reads as jargon to anyone outside the loop, who cannot tell that "Caught" is the good result or what the mutation was; write "I put the bug back (re-added the extra divisor); the test then failed, which confirms it still guards the fix" instead.
- For coverage or inventory guards, require the test's discovery cohort to mirror the production enumerator across every accepted artifact representation. Assert each intended cohort is non-empty, then remove one record backed only by each representation and require the guard to fail. If production falls back from a sidecar to a CSV or result file, a test that globs only sidecars is vacuous for CSV-backed records even when a broader regeneration test happens to catch the omission.
- When one PR bundles several independent changes, run that mutation proof once per change, not once for the PR. A suite that is green at head and red on the merge base for two of three changes says nothing about the third, and the PR body's "each behavioral change has a regression test" reads as if it covered all of them. Revert each changed hunk in turn at head: any hunk whose reversion leaves the suite green has no guard at all, and that is the finding — cite the specific hunk you reverted and the still-passing count as the evidence.
- When a mutation probe runs in place in a working tree that also holds uncommitted work — the normal case when probing a guard you just wrote, or verifying a fix before committing it — commit or stash that work before the first mutation. Do this even when you intend to revert by explicit path: `git checkout HEAD -- <file>` is not a safeguard here, because the file you mutate is usually the same file holding your uncommitted change, so the revert restores HEAD and silently deletes the work along with the mutation. A blanket `git checkout -- .` is worse only in blast radius, not in kind. After any such revert, every later probe runs against unmodified source and *passes*, which reads as "the guard is weak" rather than "the tree is no longer what I think it is". Treat a probe that unexpectedly passes as a signal to re-read `git status` and `git diff` before drawing any conclusion about the check, and re-run the whole battery once the tree is restored. If you copied the file before mutating, restore from that copy rather than from git, and verify the restore by re-reading the mutated line rather than assuming it — reporting "restored" after reverting to HEAD is how the loss goes unnoticed.
- Red-on-base proves a test catches the *old* bug, not that it pins the *new* contract. An assertion on an aggregate — a size, count, length, or shape of an assembled structure — leaves element identity and order unpinned, so also mutate to a variant that keeps the aggregate but gets the content wrong: swap two adjacent columns of an assembled state vector, or reorder two fields of a record. A width-only check such as `assert states.size == num_nodes * expected_width` is red against a branch that *omits* a column and still green against one that emits the same columns in the wrong order, which silently mis-slices every downstream consumer. For sparse serializers, include a declared trailing entity absent from every nonzero term: metadata extent and per-entity companion arrays must retain the declared model size while the payload remains sparse. A fixture where every entity appears cannot distinguish declared size from size inferred from support. When a mutation passes, the coverage gap is real no matter how red the test is on base; the fix is usually to assert the distinguishing values (which a well-built fixture already gives distinct), not to add another count. The same blindness sits one level down, in the *assertion* rather than the fixture: a check that tests a predicate over a value — `x in cell`, `x not in cell`, a regex or membership test — partitions that value's domain in two and cannot see a regression within one partition. Paired directional assertions are the trap, because covering both directions of the predicate reads as covering the contract: over evidence labels drawn from `L1+L2`/`L2`/`L1`/`not screened`, asserting `"L1" in cell` for proven rows and `"L1" not in cell` for the rest lets a corrected `L2` regress to `not screened` while both the reintroduce-the-defect and the swap-two-rows mutations stay red — so a two-mutation battery certifies the gap and the guard ships described as strictness-preserving. Enumerate the value's domain and mutate to each *other* member on the same side of the predicate; better, drop the predicate and assert the complete expected value, recomposed from the same inputs production composes it from.
- A fixture with a *single* element on the axis a fix operates over cannot support the ordering mutation at all, so no number of red-on-revert tests proves that axis is pinned. This is the usual shape when a fix applies a per-element vector elementwise — a per-reaction normalization factor, a per-column scale, a per-row offset, a per-species mask — because at `n == 1` a correct alignment and a reversed or transposed one are numerically identical. Treat a length-1 axis as an automatic coverage gap rather than a simplification: build the fixture with at least two unequal elements and prove it by mutating the vector to `[::-1]` and confirming the test reddens.
- The same blindness follows from an argument *value*, not only a fixture dimension, and it is harder to spot because the choice looks deliberate. Any input that annihilates a term — a zero matrix or vector, an empty collection, a `None`, an identity or unit scale — deletes that term from the assertion while reading as a tidy way to isolate the other one. A test calling `get_jacobians(..., sens=zeros(n, p))` against a function returning `jac_states @ sens + jac_params` verifies `jac_params` and nothing else: replacing the product with zero *and* transposing `jac_states` both stay green, and a square `jac_states` makes the transpose shape-valid, so only values could ever catch it. So when the function under test returns a composition of independently computed pieces, mutate the composition — drop a term, transpose a factor, swap the operands — rather than only the pieces, and require at least one case whose arguments are all non-degenerate and mutually unequal. Verifying each piece against an independent reference does not cover the expression that combines them.
- A whole-document substring check proves presence, not that a value is bound to its intended structured field. For guards over BibTeX, YAML, JSON, or similar metadata, corrupt the target field while retaining the correct token in another field such as `url`, `note`, or prose, and require the guard to fail; repeat for each independently maintained entry the policy claims to protect. Prefer parsing or an entry/field-scoped extractor when duplicates are valid elsewhere in the document.
- A source guard that strips comments and then searches for a marker is still a substring guard, not proof that the marker is an executable statement: the same token can survive in a string literal, logging call, dead declaration, or larger expression. Disable the real statement while retaining the marker in each plausible non-executing context and require the test to fail. Prefer a parser/tokenizer or statement-scoped exact or structural match; when behavior-neutral local-name changes must stay green, make only the invariant statement exact or use an identifier-tolerant structural matcher instead of falling back to whole-source substring search.
- When a fix narrows a classifier from a broad token match to a structural contract and a repository-wide test also discovers examples to feed it, verify that the discovery predicate narrowed with the classifier. Insert a legitimate negative that still contains the old token into the real corpus: the classifier must reject it and the inventory scan must ignore it. A focused negative unit test is insufficient when a later "every discovered candidate is valid" assertion still selects with the obsolete heuristic and turns correct future content red.
- One mutation per test is not a mutation check; aim one per *distinct defect class* the guarded behavior admits. A loop that assembles paginated or chunked data admits at least three independent failures — wrong order, a dropped element (off-by-one bound), and overwrite-instead-of-append — and a test can catch the first while missing the other two. A function with several fallback branches needs one mutation per branch, since disabling branch A leaves a test that only ever exercised branch B green. Report which classes you probed and which test each reddened; a battery where every mutation reddens exactly its target while siblings stay green is what distinguishes real coverage from one lucky assertion. This applies with full force when an author's address summary already reports a mutation check of their own: a single self-reported mutation is evidence for that one defect class, not for the others, so run the battery independently rather than accepting the reported result.
- Derive any mutation failure count from an unfiltered run of the full relevant module or test set. If isolation requires `-k` or another selector, label the result as a filtered cohort and report the deselected count, then run the unfiltered cohort before publishing a total: a name filter can silently omit a guard whose test name lacks the selected words. Distinguish pytest cases from test functions when parametrization or repeated failure nodes makes their counts differ (for example, `4 cases across 3 functions`).
- A mutation check that goes red is not automatically a well-aimed test: read the *error* it produces, not just the pass/fail. When reverting the fix makes the test fail somewhere downstream of the defect — a `KeyError` on a captured value rather than the `AttributeError` the issue actually reports — a broad `pytest.raises(...)` or equivalent catch-all wrapped around the exercised path is absorbing the real symptom before any assertion sees it. Such a test still guards today, but it reports a misleading cause and silently stops guarding as soon as the stub or fixture shifts. Flag it, and suggest a sentinel exception raised by the stub at a known point so the genuine error escapes to the assertion. Red can also mean the test never ran at all, which is the same misread one level lower and reassuring in exactly the wrong direction: a probe harness that builds its own subprocess environment can break collection outright — passing a hand-built `env` without `HOME`, `PATH`, or the interpreter's own variables makes pytest exit non-zero on a `KeyError` before any test executes — and every probe then reports identically red, reading as a fully verified battery. Run the *unmutated* baseline through the exact same harness first and require it green before any mutation counts, distinguish a collection `error` from a `failed` assertion in the summary line, and treat a battery where every probe reddens uniformly (including ones aimed at different defect classes) as a harness fault until the baseline proves otherwise. The mirror case reads in the reassuring direction and needs the same suspicion: a battery that stays uniformly *green* is more often an edit that never reached the file than a weak guard. A read-modify-write probe silently applies nothing when its anchor string's line endings differ from the file's — an LF anchor against a CRLF-tracked source is the usual case — and when the probe and the test run as separate commands, the test then executes against pristine source and reports a plausible pass. Make the probe assert that its anchor matched, and confirm the mutation is in the file (re-read the mutated line, or `git diff` it) before any green counts as evidence.
- When the finding was "this test passes for the wrong reason", the fix is only proven by rebuilding the wrong reason. Re-create the original conditions while keeping the new assertion and confirm the silently wrong cases now fail; re-running the test green proves nothing, because it was green before.
- When the PR's deliverable is a regression guard — a canary test, tripwire import, lint check, or CI check whose job is to catch a future regression — mutation-prove it in both directions. First confirm it fires for each protected target. Then rerun the same battery with the guard excluded from collection to size what it uniquely adds; targets still caught by pre-existing tests are not what the new guard buys. Report the uniquely protected subset by name.
- When a check's verdict comes from grepping tool output, anchor the pattern to the marker the tool actually emits for that verdict. A bare substring such as `grep -q error` over pytest output also matches warning text, so every mutation can report as caught and invert a coverage gap into a claim of full coverage. Match result markers (`^ERROR `, `^FAILED `) or parse the summary line, and surface matched filenames next to each verdict.
- A mutation that leaves the suite green is evidence only when that mutation *could* have reddened it. Constants gating an assertion have a direction: loosening a tolerance, raising an iteration cap, or widening an accepted-value set makes every assertion easier, so consumers and non-consumers alike stay green and the probe carries no information. Probing whether a shared `KNOWN_RP_ENDPOINT_TOLERANCE_PP = 1.5` was genuinely single-sourced by widening it to 20 passes cleanly and proves nothing; tightening it below the observed margin is what separates them, and it must redden *every* claimed consumer — the test and the notebook cell or script that imports it, not just the one you ran first. Before reporting "nothing consumes this" or "this is uncovered" on the strength of a green mutation, confirm the mutated value moves the guard toward failure.
- An artifact-level gate — a build, a linter, a whole-suite run — returns one exit status for many diagnostics, so attributing that status to the change you just probed requires isolating which diagnostic actually caused it. Read the failing diagnostic, not just the exit code: an unrelated co-occurring error (a flaky external fetch, a pre-existing warning) can hold the gate red while the setting you were testing had no effect at all, and the natural reading — "my change kept this fatal" — is then exactly backwards. Re-probe with the other diagnostic removed, or exercise the two independently, before concluding anything. This one misreads in the reassuring direction, and a conclusion drawn from it can reach a posted review as a prescribed fix that does not work.
- A probe that substitutes a different execution strategy than production uses answers a question about the substitute, not about the code. Reconstructing a solve by fixing the discrete choices and calling the underlying solver directly (a Big-M reformulation plus a cold NLP start in place of the decomposition the code actually runs), issuing one bare request in place of a client's retry/backoff, or calling a function directly in place of the framework dispatch that initializes it, all change the path under test, so a failure belongs to the harness. The tell is a negative result on an input the code demonstrably handles: when an enumeration reports the *published, reproduced* answer infeasible, suspect the probe before the model. Re-run the case through the code's own entry point; when that is impractical, discard the probe instead of reporting it, and say in the review that you did and why, so the same misleading negative is not rediscovered later and mistaken for a defect.
- When running or mutation-testing a grep-based guard over single-line JSON artifacts such as committed notebooks, a single hit prints the entire file as the matched line: suppress match output (`grep -q`, `git grep -l`, or redirect stdout) and assert on the exit status instead of capturing megabytes of output. The same failure mode inside the guard itself is review feedback — a CI check that prints matched lines from such files floods the log on every violation, so suggest filename-only output such as `git grep -l`. The assertion-level form of the same trap: for documentation or source guards over large strings, avoid assertions whose failure renderer expands the complete searched text (for example a direct `occursin(needle, document)` assertion) — wrap the search in a small named Boolean predicate or otherwise assert only its Boolean result, so an expected red reproduction stays concise and its actual failure summary is not truncated.
- Committed output values — notebook cell `outputs`, golden/snapshot files, fixtures asserted as expected — can be hand-edited to look correct, so a PR claiming output parity or refreshed outputs is not proven by reading the committed text. Extract each cell's/producer's source, execute it, and diff the produced output against the committed output. When notebook policy deliberately clears setup or bootstrap outputs, require identical cell sources and no execution errors, coalesce split stream chunks before comparing every non-setup output semantically, and inspect each excluded setup output to confirm differences are limited to transient activation, timing, or host-path logs; never exclude result-bearing cells or normalize away scientific values. For a cross-language or cross-artifact parity claim, run each side in its own runtime pinned to the CI version (for example Julia 1.10 when CI pins 1.10) and confirm the pair is byte-identical. For comparison tutorials, name canonical source notebooks separately from generated or executed artifacts and inventory each plot family as a user-visible parity surface. When implementations or solvers are compared, either report matched-scope timings under the benchmark rules above or explain explicitly why the timings are not comparable. When the PR adds a parity/equality guard test, also confirm it is non-vacuous by checking the merge-base actually failed it (the pre-fix artifacts diverged), not merely that it passes at head.
- When only a non-result-bearing helper or setup cell changed and a credentialed rerun produces different stochastic scientific samples, separate current-head execution evidence from output promotion. Verify that the changed cell ran and that the notebook had no execution errors or secret leakage, then compare and report the scientific differences. Retain the previously published result set unless refreshing stochastic outputs is explicitly in scope, and never describe retained samples as reproduced by the current run.
- For Python notebook tests that need one function from a cell that also defines later functions or classes, parse the cell with `ast.parse`, select the exact `FunctionDef` or `AsyncFunctionDef`, and compile that node or its source span. Do not split at the next `def` — a later `class` then leaks into the extracted text — or execute the whole cell, which can pull unrelated imports or live-service calls into the regression harness.
- When authoring examples with pinned expected output (Documenter `jldoctest` blocks, pytest doctests, golden files), produce the expected text by running the example and pasting the observed output — never by predicting it. For stochastic solvers, design the instance with a unique optimum, run at least twice to confirm the output is stable, and keep warning- or log-emitting paths (for example an infeasible-solve demo) in non-doctested code blocks, since logger output is not captured deterministically by doctest runners.
- Before committing an assertion about stochastic-solver output (for example "both degenerate optima appear in the returned distribution"), probe it across many seeds and compare the worst observed margin against the assertion threshold. If the margin is heavy-tailed, seed the RNG inside the testset and use the repository's established determinism mechanism (a minimum bond/rank dimension, a fixed schedule) instead of shipping a statistical test; state the probed margin in the PR or commit so reviewers can judge the residual risk.
- A symmetric assertion that two derived collections are equal (`assertEqual(extract(a), extract(b))`) passes vacuously when both extractions are empty or equal-length-but-trivial, so it does not by itself guard that the compared content exists. This is a real regression path when a repo also ships an output-clearing step (for example a `clear-notebook-outputs` Make target running `nbconvert --ClearOutputPreprocessor`): clearing both sides leaves both extractions empty and the test still green. Flag it, and require the test to also assert the extracted collection is non-empty and of the expected length before comparing.
- A test that stubs or monkeypatches the collaborator it is named for pins only the boundary contract — which arguments that collaborator received — never the collaborator's own behavior. Assertions on values returned by a fully stubbed call are vacuous, holding because of the stub. When judging coverage, state which of the two a test actually establishes.
- When review feedback challenges monkeypatch-heavy coverage, first look for a stable slice of the fixed behavior that can be tested through the real public API without monkeypatches, and add that test when it is meaningful. Keep a monkeypatched boundary test only when the broader path would exercise unresolved or out-of-scope dependencies; then document the exact boundary it pins and name the unresolved dependency or follow-up issue rather than presenting it as end-to-end coverage.
- When a test imports a module whose own import requires an optional backend or licensed solver, match the repo marker/skip convention before the import (for example `pytest.importorskip` plus the relevant marker) and verify collection in the minimal CI environment as well as the backend-enabled environment. When test execution requires the backend but collection intentionally proves that production modules remain importable without it, use the opposite structure: keep the production imports unconditional in the normal import block, before `HAS_*` assignments and module-level marker or skip setup, and use `skipif` or solver markers only to suppress execution. Do not merely move those unconditional imports out of a guard while leaving them below runtime setup; that creates late-import lint violations and obscures the collection contract. Document this dual collection/execution role in the test module so a later cleanup does not reintroduce the guard. If a boundary test stubs imports to stay in the minimal lane, inventory every import executed while loading that module—not only the headline backend—and stub or skip each undeclared optional package; run against CI's exact base/development dependency profile because a richer local environment can mask collection failures.
- When adding or refactoring fallback code for a missing optional dependency, verify that fallback path specifically. If the active local environment has the dependency installed, use a targeted import-block/stub smoke test, run the same suite under another local interpreter that genuinely lacks it, or rely on a CI lane that truly lacks the dependency; a green full suite in a dependency-enabled environment does not exercise the fallback. Enumerate the available environments before concluding no dependency-free interpreter exists — a base conda install or an unrelated project env often has the core dependencies and not the optional one, which reproduces the default-installation claim far more faithfully than a stub. Do not assume a repo-local `.venv` is dependency-free; probe it, because it is often where the optional backend is installed.
- A test that simulates a missing dependency needs its blocker checked, because the blocker can silently miss the import path. Patching `builtins.__import__` does not stop `importlib.import_module`; a `sys.meta_path` finder that raises `ModuleNotFoundError` can block statement imports and `import_module`. If production or skip logic also calls `importlib.util.find_spec`, simulate native absence there too by returning `None`; a raising finder can make `find_spec` explode during collection instead of evaluating a `HAS_X = False` flag. Assert both probes behave as intended, and identify which lane exercises the dependency-enabled case before trusting the guard.
- When extracting reusable pytest helpers, avoid making tests import `conftest` directly by default. Put pure helpers in a real test helper module, or expose `monkeypatch`-dependent setup as a fixture from `conftest.py`; if a direct `conftest` import is retained, state the repository assumptions that make it safe.
- When a CI workflow invokes an explicit list of pytest node IDs, adding a test to the named file does not place it in that lane. Inspect and update the exact list, add a configuration-contract guard for membership when the repository uses such guards, prove that guard is red before the workflow edit, then run the exact expanded command and report its increased collected/pass count as evidence that the test entered CI.
- For pytest marker or lane-expression changes, verify collection boundaries with `--collect-only` for both the changed lane and any sibling lane that could still select the same tests. Do not assume a custom marker such as `serial` changes xdist scheduling unless the repo has a plugin or wrapper that enforces it.
