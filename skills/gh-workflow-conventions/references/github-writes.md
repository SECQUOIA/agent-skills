# GitHub Writes And Verification

Part of **gh-workflow-conventions**. Read immediately before any GitHub mutation. First read [github-operations.md](github-operations.md) so the repository, target, and live state are already resolved. These rules cover safe payload construction, live preconditions, ambiguous outcomes, mutation fallbacks, and exact post-write readback.

- For a bulk GraphQL mutation over many objects — resolving every addressed review thread before a merge is the common case — write one mutation document with one aliased field per target (`t01: resolveReviewThread(input:{threadId:"..."}){thread{id isResolved}} t02: ...`) and send it once with `-F query=@<file>`. One aliased document is fewer round trips than a shell loop of single mutations, and a loop of write commands can be blocked wholesale by command-approval tooling that accepts the single reviewable document. Check each alias's result instead of assuming all-or-nothing. A `RESOURCE_LIMITS_EXCEEDED` response can still mean that earlier aliases committed while later fields are `null`; immediately re-read every target or idempotency marker, then split the remaining document and retry only aliases proven unapplied. Never resend the original document wholesale.

- When reading the same GraphQL object before and after a mutation, reuse the previously successful query text and change only its variables instead of hand-simplifying the readback. If the mutation succeeds but the readback query has a parse or schema error, do not repeat the mutation; correct the query and verify the result before any later write.

- If an explicitly authorized `gh pr`/`gh issue` write fails because the CLI queries a deprecated or unavailable GraphQL side field such as classic Projects `projectCards`, retry the same state change through the narrow REST `gh api` endpoint (for example, when the user explicitly requested an existing PR-body edit, use `gh api repos/OWNER/REPO/pulls/N --method PATCH -F body=@<file>`), then re-read the object to verify the write — confirm the intended field content actually changed, not merely that `updatedAt` advanced, since an unrelated push bumps that timestamp and can make a silently-failed edit look applied. This failure is often silent: the command can print only a Projects-classic deprecation notice and still exit 0 without applying the change (seen with `gh pr edit --add-reviewer`, which left `reviewRequests` empty), so treat that notice as a signal to verify the object and retry via REST, never as success.

- For PR and issue bodies, do not put escaped `\n` inside an inline shell string such as `gh pr create --body "...\n..."` or `-f body=...`: GitHub stores the backslash and `n` literally, so the description renders as one unbroken paragraph with visible `\n` and loses headings, bullets, and auto-linked issue references. Use a body file, then read the stored body back with `gh pr view <N> --json body --jq .body` or the equivalent `gh issue view` command; a body returned as one line containing `\n` sequences is broken however correct its wording, and this is easy to skim past because the content reads correctly in JSON.

- If a state-changing `gh` command returns a transport error after the request may have been dispatched (for example `unexpected EOF`, a timeout, or a connection reset), treat the outcome as ambiguous. Do not blindly retry or report failure: first re-read the affected GitHub object. If the intended state already applied, continue with normal verification; if it did not, re-run the live precondition and retry once under the applicable network-escalation rule. For a definite validation/permission rejection or a second failure, report the exact error and stop.

- For non-trivial GitHub comment, review, or issue-close bodies, especially bodies containing Markdown code spans, quotes, or shell-sensitive characters, write the text to a temporary body file and use `--body-file` or `-F body=@<file>` instead of an inline shell string. Reserve `-f body=...` for literal strings. (GraphQL queries follow the same rule — see the `-F query=@<file>` bullet in [github-operations.md](github-operations.md).) On a REST `--method PATCH` that sets an explicitly authorized body edit, `-F body=@<file>` can still fail with `unexpected EOF` while leaving the object untouched; after the ambiguous-transport re-read above confirms nothing applied, retry the same edit as `--input <json-file>` with the field as a JSON string, which is unaffected. Re-read the object and assert the new content is present rather than assuming the retry took. Create each such comment/review body or JSON `--input` payload with your file-write tool rather than a `cat > file <<'EOF'` heredoc, which needlessly routes through shell-command approval.

- For ordinary explicit GitHub writes, do not add a confirmation pause beyond the workflow's live-state checks. When the user names the write surface (`PR body`, top-level PR comment, inline review reply, review verdict, issue comment, review request, or merge), write to that surface after verification. Ask one clarifying question only when the latest instruction or an explicit earlier constraint such as "draft", "do not post", "preview first", or "commit and push only" leaves the authorized publish surface ambiguous. Treat "commit and push" as Git writes only unless the user also asks to publish GitHub text. Authorization to provide or attach a local artifact on one named PR or issue does not authorize publishing it on a second public surface such as a gist, release asset, or new repository. When the named surface cannot carry the file and a second public host is required, describe the destination and exact files, inspect them for secrets or private data, and obtain explicit approval for that publication before uploading.

- Treat an existing PR title/body, submitted review, top-level PR comment, and inline review comment or reply as immutable history by default. General authorization to submit, address, review, or merge a PR authorizes adding the new comments, replies, or reviews that workflow requires; it does not authorize rewriting earlier PR text. Edit one of those existing surfaces only when the user explicitly requests that exact edit. Otherwise post a new top-level PR comment or inline reply containing the corrected/current information, link the earlier text when context matters, state that the new comment supersedes it when appropriate, and skip the write when an exact idempotency marker already exists. Creating the PR's initial title/body is unaffected.

- Do not hard-wrap a hyphenated compound immediately after the hyphen in a Markdown body: the rendered newline becomes a space and breaks the word. Wrap before the compound or keep it on one line, then inspect the posted readback.

- When replying to a nested PR review comment, use the latest actionable comment's database ID when constructing the reply and marker. GitHub may still display or return the created reply as attached to the thread root (`in_reply_to_id` can differ); if that happens, report the exact permalink and note that the marker targets the nested comment so the user can trace the response.

- When asked to request PR review, mark the PR ready if requested, then use `gh pr edit --add-reviewer`, with the deprecated-field REST fallback above. If REST returns 403/404 for missing upstream write permission or a cross-repository request, post an explicit PR comment requesting review. Re-read `isDraft` and `reviewRequests` and report whether the formal request exists. A previous approval does not replace an explicitly requested re-request: verify the login in `reviewRequests`, not `reviewDecision`.

- A collaborator-only review-request rejection does not authorize changing repository access. When access is separately authorized, bind the intended person to an exact login before inviting them, and apply the same binding before an @-mention, assignment, or review request. An unavailable supplied handle plus a similar name, affiliation, or profile is insufficient to substitute another account; ask for the corrected handle unless an existing verified mapping resolves it. A supplied handle that does resolve proves no more: a short handle recalled for a collaborator can belong to a stranger, so compare its profile name with the intended person and treat a mismatch like an unavailable handle. Reuse confirmed identities and authorization without asking again. Verify the invitation's recipient and permission level, and distinguish pending acceptance from active access. Once eligibility is confirmed, complete any already-authorized review request and verify `reviewRequests`; an invitation alone does not complete that assignment.

- When the guidance is to verify a live precondition (PR/issue `state`, merge status, draft flag, branch protection) immediately before a hard-to-reverse or outward-facing write (posting a review, merging, closing, commenting), run that verification as its own command and inspect its result before issuing the write. "Its own command" means one `gh` read with literal repository scope (`--repo OWNER/REPO`, or a `repos/OWNER/REPO/...` path) and nothing else on the line: no `;`, `&&`, `||`, or `|`, no second `gh` call, and no unrelated local check. Only that shape makes the exit status report whether the read itself succeeded, since a trailing `; git status` or `| head` masks a failed read. A `--jq` projection is fine. The same shape applies to the post-write readback below, and it is the shape the optional encounter guard requires before it credits either step. Do not bundle the check and the write into one compound command (for example `echo $(gh pr view … --json state); gh api … --method POST …`): a single shell line cannot branch on the state it just printed, so a PR that was closed or merged seconds earlier still gets written to. Read the state, confirm it still permits the action, then write in a separate step. Keep the *post-write* readback separate too, and for the opposite reason: a compound line reports one exit status for all of its parts, so a malformed verification chained after a successful write (an unsupported `--json` field, a typo'd endpoint) returns non-zero and makes the write look failed. That misreads in the dangerous direction — the natural response is to retry a merge, comment, or review that already landed. Treat any non-zero exit from a line that contained a write as ambiguous, and re-read the object before concluding anything.

- Likewise, do not compose a live GitHub read, payload transformation, and mutation as one shell pipeline (for example `gh api … | python … | gh api … --method PATCH --input -`). A failed read can still start downstream stages with empty or invalid input. Complete the read first, materialize and validate the payload in a temporary file, then issue the mutation separately; if such a pipeline was already attempted and any stage errored, re-read the target before deciding whether to retry.

- After any state-changing GitHub write (`pr merge`, issue comment/close/edit, PR review/edit, or review-thread resolution), immediately re-read the affected PR, issue, or thread with narrow `--json` fields or GraphQL projections before doing slower follow-up work or sending the final response. For PR metadata edits, verify the intended field together with workflow-critical state such as `isDraft` and `reviewRequests`; if the write caused unintended state drift, restore the policy-required state before any later write. For a single issue/PR discussion comment created through `repos/{owner}/{repo}/issues/{number}/comments`, re-read it through `repos/{owner}/{repo}/issues/comments/{comment_id}`; the issue-number path does not accept a trailing comment ID.

- Before citing a specific external URL in a review, comment, or PR/issue body (a CI job/run link, a specific commit/line-anchored file link, a comment permalink) that you did not copy verbatim from a prior tool result, fetch and confirm that exact URL right before writing it into the body — for example `gh api repos/{owner}/{repo}/actions/runs/{run_id}/jobs --jq '.jobs[].html_url'` for a job link. Job IDs in particular are not derivable from the parent run ID or from timing, so a constructed or remembered ID produces a broken or wrong link once posted, and a posted review is hard to quietly correct. Full commit SHAs are equally non-derivable from short ones: never pad a short SHA into a 40-character ref by guessing the tail — expand it through the commits API or `git rev-parse` before fetching or citing it. Apply the same discipline to *values and their provenance*, which is easier to skip because no link is involved: before writing that a number came from a particular file, row, or run — or that a value is stale, superseded, or absent from an artifact — read it there. Recovering a source value by inverting one you already rounded for display yields a plausible, self-consistent, wrong number, and naming which artifact a value belongs to without opening it fails the same way. Both are hard to catch afterwards because the surrounding claim is usually right and only the citation is invented, so the correction lands as a reply admitting the posted evidence was fabricated. Reading the file in the wrong *tree* fails identically and hides better, because a read did happen and returned real content. The trap is the supporting file **outside** the PR's changed set — a helper's signature, a base class, a constant the changed code calls — since nothing about it prompts you to fetch it by ref, while the primary checkout routinely sits on an unrelated branch that modified exactly that file. A working-tree `grep`/`sed` of such a file can therefore contradict the head under review and manufacture a blocking finding about code the PR never touches; the existing worktree rules do not catch it, because they govern where commands *run*, and the tests may well have run in a correct head worktree. Read every file that will back a posted claim at the reviewed ref — `git show <head>:<path>`, or `gh api repos/{owner}/{repo}/contents/<path>?ref=<head>` — rather than by bare path, and prefer confirming a signature or constant by importing/executing it inside the head tree over grepping for it.

- For academic DOI or publisher links, do not classify a link as broken solely because the publisher HTML returns `403`, `429`, or another access/anti-bot response to an automated request. Inspect each redirect hop rather than relying on the final `curl` exit status or response code: a successful `doi.org` redirect to the expected publisher followed by a publisher anti-bot or Cloudflare 403 confirms the DOI mapping but not publisher accessibility. Resolve the DOI, check the final landing URL and title when available, and use DOI content negotiation or Crossref-style metadata to verify the citation. Report the distinction explicitly: "DOI resolves to the intended publication, but publisher HTML blocks automated access." Only treat it as broken when DOI resolution or metadata fails, or the resolved title/publication mismatches the cited source; verify any badge asset separately.

- When creating a PR/issue body — or updating an issue body or an existing PR body under the explicit authorization required above — inspect the repository's template first (for example `.github/pull_request_template.md`) and keep the relevant section names and checklists rather than replacing them with an unrelated free-form body. Remove template sections and checklist items that do not apply instead of leaving empty boilerplate, but do not overcorrect by deleting useful checklist structure wholesale. If the linked issue, triage comment, or maintainer comment lists acceptance/success criteria, carry them into the body as a checked/unchecked list with a brief note on how each criterion was handled, deferred, or left out of scope; mark satisfied criteria checked, and do not leave irrelevant unchecked template items in the PR body. Use that same scope map to choose `Refs` versus `Closes`, and apply the choice to every channel that can close an issue. GitHub honours a closing keyword in any **commit message** reaching the default branch, independently of the PR body. It equally honours one anywhere in the **body's prose**, which is the channel you write by accident: any keyword immediately followed by an issue reference counts, so a descriptive clause such as "preserve the closed #78/#83 contracts" or "fixed #12 earlier" adds that issue to the PR's `closingIssuesReferences`, and the Development panel and permanent merge record then claim this PR closed work another PR actually did. Only the number directly after the keyword is captured, which is why the mistake survives review — the sentence reads as history, not as a link. Rephrase so no keyword precedes a number, and confirm the result with GraphQL `pullRequest { closingIssuesReferences { nodes { number state } } }` (older `gh` builds reject `gh pr view --json closingIssuesReferences`), requiring exactly the issues the PR intends to close. Only a body edit clears such a link — a correcting comment cannot — so when a review raises one, ask for that body-edit authorization rather than only recording it as remaining. Editing a body from `Closes #N` to `Refs #N` therefore does not disarm a `Closes #N` already written into an earlier commit — the merge succeeds and the issue closes seconds later, with nothing at merge time to flag it. Before stating that merging will leave an issue open, scan the branch's messages (`git log <base>..<head> --format=%B | grep -niE '(clos|fix|resolv)e[sd]? *#<N>'`). Rewriting a pushed message is usually not permitted, so when a keyword is already there, either say plainly in the new PR or a later corrective comment that the issue will auto-close, or reopen it immediately after the merge with a comment naming what remains.

- When a policy or planning document calls itself a living record or generates operational artifacts, require a maintenance contract: identify the authoritative system for assignments and status, the update owner, the refresh triggers or cadence and its rationale, and how snapshots or derived artifacts stay synchronized. Keep live state in the operational system rather than duplicating it as a static checklist unless the document is explicitly authoritative.

- When an authorized partial redressal or out-of-scope cleanup is deferred to a follow-up issue/PR, cross-link the chain before reporting done: the follow-up should cite the source PR/issue/comment and any related owning issues; the current PR or issue should name the follow-up; and the original owning issue should receive a concise coordination note when the deferral would otherwise be invisible. Re-read each written object and report the verified links.

- When a completed child issue appears in an umbrella issue body or an authored checklist comment, update that existing checkbox and annotate any accepted exception in addition to posting a coordination comment. A new status comment does not make the older unchecked item non-stale; re-read both the child state and the exact tracker body after the edits.
