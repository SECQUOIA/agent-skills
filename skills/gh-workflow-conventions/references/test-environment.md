# Test And Verification Environment: Selection And Sandbox Workarounds

Part of **gh-workflow-conventions**. Read this before choosing an environment for tests/builds or working around sandbox, cache, and command-approval limits.

### Environment Selection

- Discover the repository's documented commands rather than guessing them: install, test, lint, type-check, and format commands live in README, CI workflows, `Makefile`, `pyproject.toml`, `tox`/`nox` config, `package.json`, or their equivalents. Record the exact command you ran, including the interpreter or environment it ran in, so a later skill in the pipeline can rerun it verbatim instead of rediscovering it.
- When refreshing a PR body's recorded test command or exact pass/skip counts, rerun that command under the same interpreter and environment. Optional solvers and backends can change both which tests execute and the totals; if the environment must change, record the new exact command and identify the change instead of combining evidence across environments.
- The shell's working directory does not reliably persist between separate command invocations, and a relative project flag silently retargets the run: a `--project=.`-style suite command (Julia `Pkg.test()`, `npm --prefix .`, `tox`) executed after the cwd drifted can test a *different* package in the workspace — and exit green — which reads as evidence for the package you meant to test. Pin suite invocations to the absolute project path, and before trusting any result, confirm the run's own banner (the `Testing <Package>` line, suite title, or reported project path) names the intended target. The same drift also produces false *negatives* that read as findings rather than errors: a relative-path check run from the wrong directory reports the file, binary, or lock entry as absent, which is easily written up as "the dependency did not install" instead of "I looked in the wrong place". Treat any surprising not-found result as a cwd check first — re-run it with an absolute path before recording it as evidence.
- When any long run is captured to a log or background task for later inspection — a test suite, but equally a docs/site build, a lint sweep, or a solver run — capture it unfiltered and filter at read time, preferring a redirect to a file (`cmd > run.log 2>&1`) over piping into a filter. A filter in the capture position is a single point of failure for the whole evidence: an unsupported pattern (for example a PCRE lookahead that the installed `grep` rejects) makes the filter exit immediately, discarding every line the command produced, and the pipeline can still look like it ran. When full output is genuinely impractical, filter only through an alternation that provably retains every failure signature *and* the summary/count line for that framework (for a Julia suite: `Test Failed|Error During Test|did not pass|tests passed`). Never `tail`-truncate the capture, and never use a filter that can drop the failure detail or totals: either loss forces a full rerun just to see what failed. Report pass/fail totals only when they appear verbatim in captured output — if the summary line was lost, rerun or state the outcome without a number rather than approximating one into a PR body or comment.
- Before installing or downloading a missing dependency, inspect repository manifests and already-installed environments, depots, and caches; probe the required imports and versions there first. If isolation is needed, build the scratch environment from local paths or cached packages before requesting network installation, and request a download only after the local candidates are absent or incompatible.
- When a check genuinely requires installing a tool that is absent, scope the install to scratch space (`PIXI_HOME`, `CARGO_HOME`, `npm --prefix`, `pip install --target <dir>`) and then verify what the installer touched *outside* that directory. One-line vendor install scripts (pixi, rustup, uv, nvm, conda) routinely append a `PATH` export to `~/.bashrc`, `~/.zshrc`, or a profile snippet even when the binary itself lands in the scoped directory. Read the shell rc file after installing, revert any line the task did not intend to leave behind, and confirm the revert. Mutating the user's shell configuration is a side effect of your verification, not part of the work they asked for.
- Prefer the repository's active environment over the shell's default interpreter — which may not exist at all, since a bare `python` on `PATH` is not guaranteed. Choose in this order: a repository-local environment first (`.venv`, `uv`, `pixi`), then a named project `conda`/`mamba` environment, and never install into or run against the root/base Python installation. Enumerate the candidates (for example `conda env list`, or the env directories under a conda install) and pick the one where the project's own optional dependencies actually import, especially before judging optional backends or licensed solvers as unavailable. Treat an availability helper that spawns a subprocess or trial solve as an executable check, not static discovery: a generic `false`, `NameError`, or "unavailable" result under a restricted sandbox can be a false negative even when the binary resolves on `PATH`. Retry the exact probe or smallest representative solve with the required process/filesystem/network access while preserving the same active environment and `PATH`; distinguish binary discovery, sandbox access, and license failure before declaring the backend unavailable.
- When a project has a local `.venv` and a project command must run outside the sandbox, preserve that environment for the whole command by using the repository's wrapper or putting `.venv/bin` first on `PATH`. Do not install into or rely on the base Python environment merely because an escalated command can see it. If adding a `PATH=...` prefix would bypass an already-approved command prefix, request a narrow approval for the wrapper command rather than silently dropping the local environment.
- Two `PATH` pitfalls flank conda-style activation, and both corrupt the evidence rather than erroring. First, `conda run -n <env>` rebuilds `PATH` from the env's own directories and drops entries the calling shell had, so a solver binary that `which` finds in the plain shell (an `ipopt`/`glpsol` living in another prefix's `bin`) vanishes inside `conda run`, and an executable availability probe reports the backend missing — activate instead (`source <conda>/bin/activate <env>`), which prepends the env while preserving the caller's `PATH`. Second, when adding a solver directory to an activated env's `PATH`, append it (`PATH="$PATH:<dir>"`) or prepend only directories that carry no interpreter or test runner: prepending a directory that ships its own `python`/`pytest` (a conda base `bin` is the classic case) silently shadows the activated env, and the whole suite runs — and can even pass — in the wrong environment. The tell is tracebacks or `__file__` paths resolving site-packages under the unexpected prefix; before trusting counts from any augmented-`PATH` run, confirm `which python pytest <solver>` all resolve where intended.
- When reproducing a CI/workflow PR, match the runtime version the workflow pins (for example `uv venv --python 3.11`) rather than the shell default. Pinned dependencies (`numpy<2`, `scipy<1.14`, etc.) often have no wheels on a newer local interpreter, so an install failure there is environmental noise, not a PR defect; re-run in the pinned version before drawing conclusions, and note the version mismatch in the summary. The same applies to pinned *tools*, not just interpreters: an older build can reject manifest syntax the pinned version supports (for example Pixi reporting `expected a string, found table` for a newer nested mapping), while a newer build can report a spurious mismatch such as a lockfile flagged "not up-to-date" only because it upgrades the lock format. Re-run the same check with the pinned version before reporting a mismatch as a finding, and when recommending a regeneration, say whether the output stays readable by the pinned version or the pin must move with it.
- The previous bullet discounts a local *failure* under a newer tool; the converse is more dangerous and has no such tell. A newer local build can silently accept input that the version CI installs rejects, so the local run is green and the CI run is red on identical code. Strict input validation is the usual mechanism: many solvers and CLIs treat an unrecognized option as fatal rather than ignoring it, so one stale option name aborts the process before it does any work (an IPOPT 3.14 build accepting an option that the 3.13 build from `idaes get-extensions` rejects with `Unknown keyword`, failing every solver-backed test, is the shape of it). Before concluding that a local pass clears a solver-, compiler-, or CLI-backed change, check which build the workflow installs; if it differs, re-run the same command against that build — installing it locally is usually cheap, and putting it first on `PATH` for one command is enough. When CI fails on code that passed locally, compare tool versions before debugging the code.
- A locked environment can still drift from its lockfile, and the resulting failure reads as a defect in the change under test. Before attributing any local failure to your edits, reproduce it at the unmodified base or head — stash the edits, or run the same command in a clean checkout — since a failure that reproduces there is not yours. When it does reproduce while CI is green on the same commit, suspect the installed prefix rather than the lock. In a prefix that mixes ecosystems (conda plus PyPI, system plus language packages), a wheel installed later can overwrite an earlier package of the same name in place, leaving the prefix's two record sets disagreeing — one reporting the locked version, the other the one that overwrote it — and a compiled extension built against the first then fails at import with an ABI or symbol error. Compare the records directly (for a conda prefix, `conda-meta/<pkg>-*.json` against `site-packages/<pkg>-*.dist-info`) and rebuild from the lock before reporting anything; a locked reinstall over a contaminated prefix does not reliably repair it, so remove the environment directory and reinstall. Report that as environment repair, and never adjust the lock or the code to accommodate a prefix that had drifted. Re-running the locked install afterwards also tells you whether a newly added environment is what contaminated the others, which is worth confirming before blaming a pre-existing one.
- A Julia package's root environment and its `test/Project.toml` environment are disjoint, so neither `--project` alone runs a single test file that imports the package *and* uses test-only deps: under `--project=.` the test deps (e.g. `Test`, `JuMP`) are missing, and under `--project=test` the package under test itself is missing (`Package <X> not found in current path`). `Pkg.test()` passes because it builds a combined sandbox, but it runs the *whole* suite, not one file. To run a single targeted file with both on the path, put the root package and the test env on the load path explicitly: `JULIA_LOAD_PATH="@:test:@stdlib" julia --project=. -e 'using Test; include("test/<file>.jl"); <fn>()'` (`@` supplies the root package, `test` the test deps) — this is usually the exact command the PR body's verification section documents, so read that first rather than guessing a `--project`. Treat either missing-package error as an environment artifact, not a test failure.
- Before testing a Julia package under a different Julia release line, inspect whether root or test `Manifest.toml` files are tracked or ignored and read their `julia_version` when present. An ignored local manifest still influences `Pkg.test()` and can fail during instantiation before any test runs when another Julia version generated it. Do not resolve, rewrite, or remove the user's ignored manifest to make the check pass; use its matching Julia runtime, or run the CI-version check from a clean temporary worktree without that local manifest. Report an environment-blocked attempt separately from actual test results.
- In a temporary Julia worktree, do not copy or symlink an ignored root, test, or docs `Manifest.toml` from another checkout: path dependencies can retain that checkout's absolute source path and silently load the wrong branch. Create the worktree-local environment with the repository's documented setup (for example, run `Pkg.develop(Pkg.PackageSpec(path=pwd())); Pkg.instantiate()` from the worktree root for its docs project), then require `Base.pathof(PackageModule)` to resolve inside that worktree before trusting tests or doctests. If it resolves elsewhere, recreate only the disposable worktree manifest with the documented setup; do not change committed dependency metadata.
- When a docs or generated-site build fails at CLI/config parsing, check whether the installed docs builder major version matches the repository's config format before chasing missing system tools. For example, a project with classic Jupyter Book `_config.yml`/`_toc.yml` may need the classic `jupyter-book` line rather than a newer incompatible CLI; pin or use the documented compatible toolchain when the repository lacks a lock.
- A local link/resource check over a Sphinx build must strip Sphinx's cache-busting query strings (`_static/theme.css?v=9edc463e`) and fragments before testing each path on disk. Otherwise every asset on every page reports missing and buries whatever the check was meant to find; the useful evidence is a corrected run reporting zero missing local resources.
- In a local Documenter.jl link/resource check, deployment-owned root assets such as `siteinfo.js` and `versions.js` may be absent from the per-version build. Verify those references against the exact-head preview/deploy status instead of reporting local missing-file false positives; still report missing project-owned assets.
- When a check extracts text from a built PDF (Ghostscript `txtwrite`, `pdftotext`) and returns empty or garbled results — bracket labels missing their digits, ligature words dropping letters ("Geoffrion" reading as "Georion") — run `pdffonts` before treating the check as failed: Type 3 bitmap fonts defeat text extraction while the PDF still renders (for TeX, this means the scalable-font package such as `cm-super` is missing). Font metrics are identical either way, so page counts and line breaks from such a build remain trustworthy evidence; install the scalable-font package and re-run the extraction-based check instead of weakening it.
- When a check requires *building* a LaTeX document, a minimal TeX install may lack packages that the document *class* requires at load time (for example the SIAM `siamart` class does `\RequirePackage{algorithm}` and loads `algorithmic`; both live in the `texlive-science` bundle), so compilation dies before any content is processed — this is an environment gap, not a defect in the PR. Probe with `kpsewhich <pkg>.sty`; install the missing bundle (retrying with network escalation), or, when install is unavailable, drop a minimal stub `.sty` into a scratch directory referenced via `TEXINPUTS=<dir>:` (never committed) so a document that uses none of the missing package's features still builds. Do not report a LaTeX PR as unbuildable on a missing-class-package error alone; after building, treat undefined references/citations from the log as real findings.

### Sandbox, Cache, And Approval Workarounds

- If Pixi fails before environment creation with `failed to acquire global cache lock` or `no writable layers to cache package to`, leave the project and worktree unchanged and rerun with `PIXI_CACHE_DIR` set to a task-scoped writable directory. A fresh scoped cache may then need package downloads; if the next failure is a DNS or network restriction, retry that same scoped-cache command with network access before judging the lockfile or environment broken. Remove the temporary cache after verification.
- If `pre-commit` fails before running hooks because its cache under `~/.cache/pre-commit` is read-only, rerun with `PRE_COMMIT_HOME` in a writable temporary or repository-local directory. Before creating or downloading hook environments, compare each hook's `files`, `exclude`, and type selectors with the changed files. If every hook is inapplicable, do not install dependencies or grant broader permissions solely to obtain a `SKIPPED` result; record the selector evidence and same-head CI instead. For an untrusted PR, never grant host or network access to contributor-controlled hooks merely to reproduce CI. If an applicable hook's environment installation then fails on registry/DNS access under the workflow's required isolation, retry the same validation with network access before treating the hook as broken.
- When using `uv` directly or through a `PYTHON="uv run ..."` Make override in a restricted filesystem, keep its cache in the repository if the project already defines a local cache such as `UV_CACHE_DIR` or `.uv-cache`. Use the documented Make target that exports that variable, or pass a scoped option such as `uv run --cache-dir .uv-cache ...`; a one-off `uv run` can fail with `EROFS` under the home cache even when the same environment is otherwise valid.
- If `uv lock --offline` or another offline uv resolution reports a dependency conflict because only older cached versions are available, treat that as an incomplete local cache until you rerun the same resolution with the same scoped cache and network access. Do not report a real incompatibility or change bounds based only on an offline-cache miss.
- If Black fails before reporting any formatting difference because its worker pool cannot create a local manager socket (`PermissionError: Operation not permitted`), rerun the exact `black --check --diff` command with the required process permissions. Do not substitute `--fast` or otherwise weaken Black's equivalence check to work around the sandbox.
- If Plotly/Kaleido image export fails before rendering because its bundled Chromium cannot initialize the process sandbox (`SandboxHostLinux::Init`, `shutdown: Operation not permitted`), rerun the exact report or image command with the required process permissions. Preserve the same environment and pinned Plotly/Kaleido versions; do not skip PNG generation or replace it with a weaker static figure check.
- If Jupyter or `nbconvert` fails before starting a notebook kernel because restricted networking prevents creation of a local socket or port (`PermissionError: Operation not permitted` from `socket.socket` or `find_available_port`), rerun the exact notebook verification command with local socket permissions before treating it as a notebook failure. Preserve the same environment and command; do not replace the fresh-kernel check with a weaker static check.
- If Jupyter or `nbconvert` cannot launch a kernel because the configured interpreter path does not exist, inspect `jupyter kernelspec list` and the selected kernel's `kernel.json` `argv`. A kernelspec that points into a deleted temporary environment is local environment drift, not a PR regression. Select or temporarily register the repository's active environment as the kernel and rerun the exact notebook check; do not rewrite committed notebook kernelspec metadata unless the PR requires that change. `jupyter kernelspec list` can look correct — the active environment's own `python3` spec listed — while execution still resolves the notebook's `python3` name to a stale spec elsewhere; do not spend time debugging that name precedence. Register a uniquely named throwaway spec instead (`python -m ipykernel install --user --name <unique>`), run with an explicit kernel override (for nbconvert, `--ExecutePreprocessor.kernel_name=<unique>`), and remove the spec (`jupyter kernelspec remove <unique> -y`) after the check. That route needs a place to pass the override, so it does not apply when the check is a repository *test* that calls papermill or nbclient itself: there the kernel name comes from the notebook, and a uniquely named spec is never consulted. Shadow the notebook's own name instead — install a spec under that exact name into a scratch directory and point `JUPYTER_PATH` at it, since that variable prepends a search root. `JUPYTER_DATA_DIR` is not a substitute: it relocates the user data directory without reliably outranking an existing user-level spec of the same name, so the stale spec still wins and the failure looks unchanged. A broken shared spec breaks *every* notebook test, including ones the PR never touched, so confirm an untouched notebook test fails the same way before attributing it to the PR.
- Command approval matches on the leading command token, so invoke one tool per command to stay within a per-tool approval for that tool. A leading env-var assignment (`PYTHONPATH=… python -m pytest …`), a `;`-chained multi-tool line, or an absolute-path/`-m` wrapper (`/abs/.venv/bin/python -m pytest …`) no longer starts with the bare tool name (`pytest`), so it falls outside that approval and re-prompts even when the underlying tool is already approved. Prefer the console script as the leading token (`pytest …`, `ruff …`), set env inside the active venv/wrapper, and split chained steps into separate calls to avoid repeated approval prompts. When a scratch virtualenv's `bin` genuinely must be on `PATH` — a build that shells out to a console script or a bundled binary — `source <venv>/bin/activate && <tool> …` achieves it without an env-var prefix.
- When a build needs a system binary that cannot be installed system-wide (for example `pandoc`, which `nbsphinx` invokes for notebook pages), check for a PyPI wheel that bundles it before declaring the build unreproducible locally: `pip install pypandoc_binary` ships a `pandoc` executable, and symlinking it into the scratch venv's `bin` puts it on `PATH` for the build without touching the host. Confirm the tool resolves (`which <tool>`) inside the same activated shell that runs the build.
- Heredocs break silently under environment wrappers: `conda run`, `uv run`, and similar do not forward stdin, so `conda run -n <env> python - <<'PY'` executes an empty script and prints nothing, which reads as a check that ran and found nothing. Write the script to a file with your file-write tool (see the temporary-body-file bullet under Commit And Push Hygiene in the core conventions) and pass its path. When a JSON `--input` payload must embed dynamic content (a review body or inline comment read from a file), assemble it with a small Python `json.dump` script rather than a standalone `jq -n` command: `gh`'s built-in `--jq` flag ships an embedded jq for reading output and is always available, but a standalone `jq` binary often is not on `PATH` (for example a minimal WSL/conda environment), so a payload build that shells out to `jq` fails with `jq: command not found` mid-workflow.
- When that written script must import a module from a scratch or archived source tree (for example a one-off verification/soundness check against a `git archive <head>` copy), place the script *file inside that tree*, not in a separate scratchpad. Running a script by path puts the script's own directory on `sys.path[0]`, not the current working directory, so a script that only `cd`s into the tree still fails with `ModuleNotFoundError`. Putting the file in the tree resolves the import with no env prefix; a `PYTHONPATH=<tree> python …` workaround would instead re-trigger command approval (see the leading-token rule above). Assert the imported module's `__file__` is the intended tree before trusting the result.
