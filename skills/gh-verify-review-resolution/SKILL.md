# GitHub Verify Review Resolution

## Overview

Use this workflow to check whether PR updates addressed existing review comments or a user-referenced source report/checklist. It is read-only by default; only the explicit bounded close-out exception below permits GitHub state changes.

Follow the shared **gh-workflow-conventions** (read the sibling `gh-workflow-conventions/SKILL.md`): gh-only tooling and `--json` fallback, PR/repository resolution across remotes, terse invocation shorthand, untrusted-text handling, bounded watches, and concise tone. The Read-Only Rules below override any convention that would write, push, or change checkout state. This file covers only what is specific to verifying review resolution.

## Read-Only Rules

Do not modify files, stage, commit, push, mark comments resolved, submit reviews, or reply to comments. Do not run `gh pr checkout`, switch or create branches, or otherwise change the local checkout state. Do not start, re-run, or cancel CI runs — no `gh run rerun`, `gh workflow run`, or `gh run cancel` (watching existing runs with `--watch` is fine; it only polls). Produce an assessment and stop unless the user explicitly requests the bounded close-out actions below. Do not perform a new review yourself. If one is warranted, recommend it and hand off to gh-review-pr. A new review means new findings, or reviewer judgment beyond the existing items. Posting the verdict this verification already reached is a close-out action below, not a new review.

The no-file rule also covers temporary GraphQL query files. Preserve `gh`'s typed-field parsing without a persistent file by feeding the query through standard input, for example `printf %s '<query>' | gh api graphql -F query=@- ...`. Do not fall back to lowercase `-f query=...` or an inline multi-line query string.

Read-only forbids changing the checkout, not running checks. To execute tests or mutation checks against the PR head, copy the working tree to a scratch directory excluding `.git`, then overwrite the PR's changed files with head content read via `gh api repos/{owner}/{repo}/contents/<path>?ref=<headRefOid>`. Do not use `git worktree add` for this: it writes to `.git`. Run everything inside the scratch copy, delete it afterward, and confirm the real checkout is still clean and on its original commit. Note that a `cd` into a `.git`-less scratch copy makes later `git` commands in the same shell fail — that error is the copy, not the repository. This recipe assumes the working tree's *unchanged* files already match the PR base; overwriting only the PR's changed files is enough only when the rest of the tree equals that base. When the local checkout is on a different or divergent branch (`git rev-parse HEAD` is not the PR head, and the base-side files the changed file imports have diverged), a changed-files-only overwrite builds a wrong-source tree — the test would exercise a different implementation than the head's expected values were computed against, producing a false pass/fail. Divergence includes files the local branch *adds*, not only ones it modifies: `git show <base-ref>:<path>` fails for those, and leaving them in the scratch copy silently joins extra tests to the run, so the suite total disagrees with the PR head's for reasons unrelated to the review. Delete them from the copy. Either also refresh the base-side dependencies from the base ref, or skip the local run and rely on CI plus a semantically-inert diff (for example a docstring/comment/format-only delta from a head you already timed) as the evidence. A cleaner alternative that sidesteps the base-match assumption entirely: fetch `pull/<N>/head` and materialize the exact head tree in one step with `git archive <headRefOid> | tar -x -C <scratch>`. It writes nothing to `.git`, needs no per-file overwrite, and produces the pristine head regardless of what the local checkout is on — a divergent branch, an ancestor commit, or a dirty tree — so the wrong-source failure mode above cannot arise; verify the archived tree matches head with a diff of the changed file against `git show <headRefOid>:<path>` before trusting it. Pristine *files on disk* is not pristine *imports*, though: `git archive` fixes what grep, `git show`, and diff read, but it does not redirect Python's import resolution. If the package under test is editable-installed (a `.pth`/import finder pointing at the primary checkout), running the archived tree's own test suite still imports the installed package — the branch the primary checkout happens to be on — not the archived source, so the archived head tests can silently exercise the wrong branch and fail (or pass) for reasons unrelated to the PR. A quick tell is a baseline that should pass failing on a renamed/added symbol (`AttributeError: ... has no attribute <new_name>`), meaning the installed older source was imported. To actually exercise the archived head source, combine the archive with the `sys.modules` real-name injection in `gh-workflow-conventions`' [references/worktrees-and-checkouts.md](../gh-workflow-conventions/references/worktrees-and-checkouts.md), and assert the imported module's `__file__` is the archived path before trusting any pass or fail. The archived copy has no `.git`, so tests that enumerate tracked files or otherwise require a git checkout can skip or fail outright — for example, a helper that runs `git ls-files` with `check=True` raises on “not a git repository.” Treat either outcome as an artifact of the copy, not a PR result, account for it when the scratch suite total differs from CI, and use explicit non-git-dependent sibling node IDs when a mutation check needs proof that neighboring tests stay green.

When `git archive` is unavailable, do not reason about which paths differ and overwrite only the obvious ones. Enumerate the complete delta against the head with `git diff --name-status <local-HEAD> <headRefOid>`, apply exactly that set from `git show <headRefOid>:<path>` (adding, overwriting, or deleting per the status letter), then prove the reconstructed tree before running anything: compare every path from `git ls-tree -r --name-only <headRefOid>` with `git show <headRefOid>:<path>` and require zero mismatches. Command-approval tooling commonly denies `git archive` and `git worktree add` alike; the byte-for-byte proof makes this fallback equally trustworthy from any local commit.

Run the same recipe in reverse when the tree already sits at the PR head and the *base* behavior is what you need — most often to re-confirm that tests an address commit strengthened are still red without the fix. Build the scratch copy from the head tree, overwrite only the PR's changed production files with base content, and keep the head tests; `git show <base-sha>:<path>` reads ref content without touching the checkout, so it stays within the read-only rules. Confirm the module resolves inside the scratch copy before trusting the run. Re-check red-on-base after any commit that edits the tests themselves: strengthening assertions can quietly cost the original regression guarantee, and the address summary's own green test log cannot show that, since it only ever ran against the fixed head. When the address commit also renamed or restructured the production API the head tests call (a review comment asking for a clearer function name is a common trigger), the whole-file base swap breaks — base production predates the rename, so the head tests calling the new symbol will not import against it. Reintroduce only the specific defect into the head production instead (mutate the one fixed line, keep everything else at head), keep the head tests, and confirm they still go red; that isolates the regression guarantee from the rename. Also confirm the head tests were actually updated to target the renamed symbol — a rename that missed a test leaves it calling an alias or a stale name, which can pass vacuously.

Some claims cannot be settled by reading files at all, because what is under review is how *git itself* evaluates repository configuration — an added `.gitignore` negation, an `.gitattributes` rule, an ignore precedence that only bites once a sibling branch merges. Do not resolve these from documentation: the exception that a re-include cannot rescue a file whose parent directory is excluded is precisely the kind of rule that decides such a finding, and getting it wrong flips the verdict. Read-only forbids editing the repository's own configuration to test it, so reconstruct the configuration in a throwaway repository instead — `git init` an empty scratch directory, write the exact file content the claim concerns (including any lines a sibling PR would reintroduce), create the paths in question, and let `git check-ignore -v` decide. That yields the same decisive evidence a maintainer review would get from `git merge-tree --write-tree`, while writing nothing — not even loose objects — into the repository under review. Delete the scratch repo afterward.

Classify the address commit's production delta before deciding how much to re-verify, rather than re-running everything or trusting the summary. Parse the changed production file at the reviewed head and at the new head, strip docstrings from every module/class/function node, and compare `ast.dump` of the two trees (other ecosystems have equivalent AST or canonical-formatter tools). An identical result proves the delta is documentation-only, so prior red-on-base evidence for untouched tests carries forward unchanged and does not need re-running; a differing result means real behavior moved and the mutation checks must be repeated. This is the same mechanical comment-only check the shared conventions require for comment-only *PR* claims, applied across two heads of one PR — and it is what lets a verification pass be both cheap and honest about which earlier evidence it is reusing.

An inert production delta shifts where the mutation must be aimed. When the address commit only *adds a test* — the common answer to a missing-coverage comment — there is no fix inside that commit to revert, so the usual "delete the fix and confirm red" move has no target and the commit's own green log proves nothing about whether the new test is vacuous. Mutate the *pre-existing* production branch the new test claims to cover instead: force the gate the other way, neutralize the condition, or otherwise disable exactly the behavior the comment said was untested, then confirm the new test fails while its siblings still pass. Report that scoped failure as the evidence, and check the sibling tests stayed green — if the mutation reddens tests that were already covering that path, the "missing" coverage was not actually missing and the comment may be `Not applicable`.

That delta classification governs tests; *committed generated artifacts* — executed notebooks, golden files, rendered tables — need their own reachability and carry-forward decision, and the AST comparison above will never raise it. A behavior-preserving refactor still moves an artifact's recorded bytes whenever the new path applies defaults the old one did not: routing a direct `SolverFactory("ipopt").solve(model)` call through a package wrapper that sets solver tolerances shifted a committed notebook's fitted parameters in the eighth decimal, while the guarding parity test's `2e-5` tolerance was orders of magnitude too wide to see it. Before rerunning, trace the changed behavior against each artifact's committed inputs, configuration, or status metadata. When a machine-readable inventory or ref-pinned search proves no committed artifact can enter the changed branch, carry those artifacts forward without invoking expensive solvers or services and cite that negative evidence. Otherwise re-execute every reachable committed artifact and diff against the committed bytes — not only artifacts whose own source changed, since an address pass that refreshes one notebook routinely misses its sibling. Report a stale artifact as a new finding rather than an unaddressed comment, and say explicitly when the suite has no output-comparison guard: that staleness ships to the rendered docs and no CI lane will ever report it.

The read-only default is the skill's own initiative, not a veto on an explicit bounded close-out request. Complete the full read-only assessment first, then perform only the requested actions: post one assessment summary, submit one outcome review, resolve threads just classified `Addressed` at the unchanged head, and/or mark an open draft PR ready for review. Re-read the exact targets immediately before and after every write; use the shared bulk-thread mutation convention, never resolve a `Partially addressed` or `Not addressed` thread, and after marking ready inspect whether `ready_for_review` triggered fresh checks. Resolving threads settles only the thread-shaped half of the inventory, so map the open findings onto the thread list before resolving anything. Findings in binary artifacts or PR metadata can never carry an inline comment and are body-only by construction: when every thread classifies `Addressed` while such a finding is still `Partially addressed` or `Not addressed`, resolving them all leaves the PR reporting zero unresolved conversations with blocking work outstanding. Give every finding that has no thread its own named section in the summary you post, and never promise to hold a thread open for one — it does not have a thread to hold. Do not infer these actions from the recommendation, merge the PR, or make any other write. An automated or orchestrated invocation never counts as the request.

For an explicitly requested close-out comment, use a top-level discussion comment even when it includes remaining findings or conditional merge readiness. State the conditions and distinguish the assessment from GitHub's recorded review verdict. Follow the shared [write-surface and immutable-history rules](../gh-workflow-conventions/references/github-writes.md): the comment request does not authorize a formal review or deletion of earlier comments. Requests for a new review round still route to gh-review-pr; when the user authorizes another review only if needed, apply the Review-Round Decision below first.

An outcome review records the verdict this pass reached on the existing items, so it does not need a fresh review round. Use it when the user asks to approve, accept, or record the verification as a review. The requester is often the reviewer whose `CHANGES_REQUESTED` holds `reviewDecision`. Post it under gh-review-pr's [references/posting-review.md](../gh-review-pr/references/posting-review.md) rules:
- Recheck the PR state and head, and delete your own `PENDING` review.
- Honor the `gh-review-pr:sha` sentinel.
- Build the JSON with a serializer and POST it once.
- Re-read `reviewDecision` afterward.

Choose the event as follows:
- `APPROVE` only when every item is `Addressed` at the unchanged head, no new finding surfaced, and the account is not the PR author.
- `COMMENT` otherwise. GitHub rejects an author's approval, and a partial outcome is not an approval.

The review body is the short outcome summary. Do not also post a discussion comment with the same content. A new finding surfaced during verification is new review work: hand it to gh-review-pr rather than posting it in an outcome review.

## Inspect

1. Resolve the PR (see shared conventions for multi-remote resolution) and read the current PR diff with `gh pr diff` and `gh api` — do not check out the head locally.
2. Identify commits added since the relevant review comments were made. When commits — especially refactors or base merges — landed after a thread was resolved, a resolved flag or an "Addressed in `<sha>`" claim is not proof the fix still holds: verify the claimed change is still present at the current head, since a later refactor can silently reintroduce a previously addressed issue. When the address commit is itself a merge of the base, do not settle for confirming the fix line still reads identically: a merge can move a computation the fixed function depends on (for example an upstream unit conversion) so the function now receives a different contract while its own line text is unchanged, which can quietly defang the guarding test. Re-run the mutation against the merged head — reintroduce the original bug and confirm the regression test still fails — rather than treating a textually-unchanged line as proof.
   A fix that *restates a measurement* of the PR itself — test counts, a results table, files changed, coverage, timings — behaves differently from a code fix: every later commit can re-invalidate it without anyone touching the corrected text, so the presence check above returns the wrong verdict, since the corrected numbers are still sitting there while the quantity moved. Re-measure at the current head and classify on that value rather than on the fix being present — re-collect in the scratch head tree and cross-check the CI job log's own collected/passed line — and never carry this class forward on a previous round's `Addressed`. The author-side refresh is `gh-address-review-comments`' job; re-measuring here is the independent check, not a duplicate of it. These numbers ship to the default branch in the merge record and no CI lane reports their drift.
   When the full PR diff is too broad or truncates, inspect the address commit directly with `gh api repos/OWNER/REPO/commits/<sha>` and its `files[].patch`, then verify the result against exact current-head contents; commit patches can truncate too, so an absent hunk is not proof.
3. Read all review threads with `gh api graphql`, recording each thread's `reviewThreads.isResolved` value (it is a returned field, not a query filter), and paginate the `reviewThreads` connection until `pageInfo.hasNextPage` is false so PRs with more than 100 threads are not silently truncated. Also read review bodies and open discussion comments; actionable findings may have no inline thread. Do not treat an empty `reviewThreads` list as no feedback until top-level review bodies are checked. Evaluate resolved and unresolved threads alike: `isResolved` is workflow state, not the content classification. A still-open thread can be `Addressed` when current-head evidence proves the fix, while a resolved thread can remain `Partially addressed` or `Not addressed` when the defect persists. If branch protection requires conversation resolution, report a content-addressed but open thread as an administrative merge gate under Remaining issues and recommend that the reviewer resolve it; do not downgrade the finding or recommend another automated review solely to clear the flag. Treat prior address-summary comments with `<!-- gh-arc:...:target=summary -->` markers as evidence of claimed fixes and tests, not as separate actionable feedback unless they contain a new explicit request. When such a comment defers part of a finding to another issue or PR (a coordination note, often cross-linked with a `gh-coord:` marker), treat the deferral as a claim too: confirm the cross-links resolve in both directions and that the deferral is technically valid at the current head — for example that a "works only incidentally today, will break after issue X lands" rationale actually holds against current source — rather than accepting the split because the note exists.
   GitHub may create an empty-body `COMMENTED` review solely as the container for an inline reply. Correlate it with pull-review comments and timestamps; treat that empty wrapper as transport metadata rather than a separate finding or new review round, while still evaluating the underlying inline reply.
   For comments about stale PR metadata, generated sites, or GitHub Pages deployment URLs, verify the current PR title/body and any linked site URL. Distinguish a fork preview URL from the canonical post-merge repository Pages URL, and report any remaining ambiguity only when it falls within the reviewed feedback's scope.
   For comments about stale required status checks or branch protection, read the base branch protection required status checks and the PR's current `statusCheckRollup`; compare required context/check names with the emitted PR checks and re-read `mergeStateStatus`. Treat settings-only summary comments as evidence of a claimed fix, not proof, until live protection and PR state match.
   Only report a missing-approval gate (for example "the only review is a COMMENT by the PR author, so a formal APPROVE is still needed") when branch protection actually enforces approving reviews. Verify first: an empty `reviewDecision` together with `mergeStateStatus: CLEAN` and no `REVIEW_REQUIRED` means no approval is enforced — do not surface the gate speculatively. Confirm via the base branch protection (`required_pull_request_reviews.required_approving_review_count`) before reporting it. When it genuinely is required and the only review is a COMMENT by the PR author, state the concrete resolution rather than an open-ended note: the author account cannot approve its own PR, so a second eligible maintainer (or bot) account must post the APPROVE.
   Conversely, a standing `reviewDecision: CHANGES_REQUESTED` is not cleared by addressing the comments: GitHub keeps that gate until the original reviewer submits a new review or dismisses the old one, independent of whether the inline threads read `isResolved: false` (threads and the formal review verdict track separately). When every comment is content-addressed at head but the formal review still requests changes, report that the gate clears through the reviewer re-reviewing or dismissing — a human action by that reviewer, not the author, and not grounds for another automated round. With multiple reviewers this aggregates conservatively: a later `CHANGES_REQUESTED` from one reviewer holds `reviewDecision` at `CHANGES_REQUESTED` even when a different reviewer has separately `APPROVED`, and it is that specific requesting reviewer who must re-review or dismiss — another maintainer's approval does not override it. Name which reviewer's verdict is the blocker rather than pointing at the approval.
   On a merged PR, a lingering `reviewDecision: CHANGES_REQUESTED` can be a post-merge artifact rather than an unmet gate: a reviewer whose final round was inline-suggestions-only (empty review body) may have applied their own suggestions ("Apply suggestions from code review" commits on the head), resolved those threads themselves, and merged without submitting a fresh APPROVE. Check the review timeline against the head commits and thread resolution before reporting it; classify such reviewer-self-applied rounds as addressed, citing the reviewer's own commits.
4. Inspect relevant tests, documentation, and surrounding code using ref-specific read-only data from the PR head, not the local checkout. Prefer `gh pr diff`, `gh pr view --json headRefOid,headRefName,files`, and `gh api repos/{owner}/{repo}/contents/<path>?ref=<headRefOid-or-headRefName>` for file contents. The default JSON+base64 contents response silently returns `encoding: "none"` with empty content for files over ~1MB (a notebook with embedded outputs easily crosses this) rather than an error — if content comes back empty, re-fetch the same endpoint with `-H "Accept: application/vnd.github.raw"` to stream the raw bytes regardless of size before concluding the file can't be read. When a file is large or a raw-content read truncates, rerun a focused search against the PR-head content (for example symbol names, exact assertions, hidden markers, or reviewed strings) and capture only the matching context needed to verify the claim. When that focused search verifies a claimed rename or symbol removal, scope each hit to the PR's changed hunks (`gh pr diff`, or `git show <head> -- <file>` at a verified head) before judging it: a whole-file or repo-wide grep for the old symbol commonly lands on a same-named identifier in another method or class the PR never touched, which is pre-existing out-of-scope code (an optional consistency note at most), not evidence the rename was left incomplete — so do not downgrade the finding to `Partially addressed` on the strength of an out-of-diff match.
   If the working tree already sits at the PR's exact head — for example left over from an earlier step in the same session — confirm `git rev-parse HEAD` equals `gh pr view --json headRefOid` and that `git status` is clean before relying on it. Once that exact match holds, that pre-existing tree may also be used for `git diff`/`git log`/`git show` and for running the project's own local test suite as stronger supplementary evidence beyond the ref-specific `gh api` reads above. Never fetch, switch, or check out a branch to manufacture this match — a name-only branch match is not enough, and doing so remains prohibited by the Read-Only Rules. This local-test allowance is separate from, and does not relax, step 6's restriction on triggering new GitHub Actions runs. `HEAD` plus a clean status is one sufficient proof of the match, not the only one: an externally driven pipeline can leave the branch pointer behind the pushed head with the head *content* already in the tree as uncommitted modifications, so `rev-parse HEAD` names an older commit and `git status` is dirty while every file is byte-identical to the PR head. Settle it by content — `git diff <headRefOid> --stat` empty together with `git status --porcelain -uall` reporting no untracked files proves the tree equals the head tree, which is what a local run actually depends on. Fetching the ref to `FETCH_HEAD` only to name it moves no branch and stays within the rules. Report the lagging pointer as a workspace observation; repairing it is a checkout change the Read-Only Rules forbid.
5. For notebooks or other large generated files, avoid dumping full patches with embedded images/output. Use `gh pr diff --name-only`, targeted searches, and raw PR-head file reads or JSON parsing to inspect only the cells, metadata, and tests relevant to the comments.
   - For visual or notebook parity comments, verify rendered cell outputs, output MIME types, or committed notebook JSON outputs when available. Source-level API checks alone are insufficient when the comment was about the displayed plot, analysis, or user-visible parity.
6. Read existing CI/test results only — `gh run view`, `gh run watch`, or `gh pr checks`. Prefer non-watch reads. If watching is necessary, bound it with `timeout <duration>` because watch commands can wait indefinitely. Never start, re-run, or cancel a run, and never push, commit, or modify tracked files based on what you find.

## Comment Status

For each review comment, review-body finding, and discussion comment, classify it as:

- `Addressed`: the issue was fixed adequately.
- `Partially addressed`: some but not all of the issue was fixed.
- `Not addressed`: the issue remains.
- `Not applicable`: the code changed or the premise was incorrect.

When the pass was invoked against a source report, checklist, or requirements artifact, that document's own items belong in this inventory too — the shared conventions require reporting source-artifact coverage separately from GitHub-comment resolution, and this section is where that obligation is discharged. The list above names only comment-shaped items, which is exactly why the artifact gets dropped: verifying every posted thread feels complete, and "all N threads addressed" then ships as though it answered the report. Inventory the artifact's actionable items first, map each to the thread, finding marker, or address commit that covers it, and give source coverage its own line in section 1 — an item satisfied in the code but never mentioned in the author's response is a documentary gap worth naming, not a pass. Derive that inventory from the artifact itself rather than from a previous round's findings list: a finding list built from a partial sweep propagates its own gap into the fix, and the next round then verifies the narrower set again.

For each item, provide a brief explanation, supporting commit/file/test when applicable, and any needed follow-up. If a Blocking comment was declined rather than fixed, flag it separately as a declined Blocking comment requiring a human decision; do not fold it into `Not addressed`.

When a finding's own prescribed remedy was to open a follow-up issue or otherwise defer (typically a `Nonblocking` finding that explicitly says "recommend a follow-up" and does not ask for a code change in this PR), classify it `Addressed` — noting it was handled as a deferral — once the deferral is valid per the Inspect step: the follow-up issue exists, cross-links resolve in both directions, and the finding's premise still holds at the current head. Do not classify such an item `Not addressed` merely because the PR code is unchanged; unchanged code is the requested outcome, not an unmet request. This is distinct from a declined Blocking comment, where the requested fix was skipped rather than intentionally routed to a tracked follow-up.

A comment is `Blocking` when it carries the `Blocking` severity prefix posted by the maintainer review; if it has no explicit severity, treat correctness, regression, missing test for changed behavior, broken public API, security, or serious maintainability issues as Blocking. Treat the posted prefix as authoritative. For review-body findings, use `<!-- gh-review-pr:finding=... -->` markers when present and otherwise use the severity-prefixed title as the item identity.

## Review-Round Decision

Classify the next review decision as exactly one of:

- `No`: the existing findings are adequately classified and another review would only repeat the verification.
- `Targeted`: reviewer judgment is useful, but the reason can be bounded to specific address commits, findings, files, behavior, tests, APIs, build logic, or CI logic. Prefer this for a revised approach or for behavior that moved beyond the commented lines while remaining locally scoped.
- `Full`: the address work is broad, cross-cutting, or cannot be bounded reliably — for example, it introduced new public API behavior or materially changed CI, build, or test architecture across the PR.

For `Targeted`, provide a compact re-review brief containing the prior reviewed SHA, current head SHA, address commits between them, finding markers or thread IDs, affected surfaces, and the precise question the reviewer should answer. Targeting sets the review's priority, not its safety boundary: `gh-review-pr` must still re-verify the full changed-file set, relevant tests, PR metadata, regressions, and live merge gates under its own rules.

A partial address or a fix spanning several files is a follow-up note, not automatically grounds for either kind of new review. Recommend another address pass when the remaining work is already defined; recommend targeted review when the revised solution needs bounded reviewer judgment.

Cap the loop. If the review-resolution-verification cycle has already run the agreed maximum number of rounds, default three, or if the same comment or class of issue keeps recurring, do not recommend another automated round. Escalate to a human and state that the loop is not converging.

Distinguish a non-converging loop from a converging one when the reviewer and author are the same account (self-review). Successive rounds that only surface progressively smaller `Nonblocking` refinements, each promptly addressed, are converging, not stuck — recommend merge rather than another round even if a criterion above (for example "CI/build/test logic changed materially") would otherwise trigger one. Each round of automated review-then-fix has a cost; once no blocking finding is outstanding and the head passes, prefer close-out over another self-review pass.

## Final Response

Use exactly these sections:

1. Overall assessment
2. Comment-by-comment status
3. Tests or CI evidence inspected
4. Remaining issues
5. Whether another review round is justified
6. Recommended next action

Begin section 5 with `No`, `Targeted`, or `Full`. For `Targeted`, include the compact re-review brief required above; for `Full`, state why a reliable narrower scope is not possible.

Do not carry out the recommended action unless the user explicitly requests it under the bounded close-out rules above; assess first, then act and report the verified result. Keep the tone concise and professional; no emoji or praise padding.

When every item is `Addressed` and the fixes verify at head, include in "Recommended next action" an offer to post the outcome. Check the invoking account with `gh api user --jq .login` and compare it with the PR author. For an eligible non-author account, offer an `APPROVE` outcome review with a short summary as its body. For the PR-author account, offer an affirming summary comment instead: a short "verification pass confirms each comment is addressed and the fixes are correct" note attributed to the assessment. That comment cannot serve as a formal approval, but it records the per-item resolution and gives the final human reviewer a ready starting point, which the reviewer must otherwise reconstruct. Recommend it; do not post it unprompted. Post it only when the user directs the write, through the bounded close-out path in Read-Only Rules — never as a default side effect of verification. When every item is `Addressed` but a specific reviewer's standing `CHANGES_REQUESTED` still holds `reviewDecision` (see the multi-reviewer rule in Inspect), the affirming comment is not just a record — it is the prompt that unblocks the PR. Address it to that reviewer by `@login` and state the one concrete action that lifts the gate (re-review or dismiss), since neither the author nor another maintainer's approval can clear that particular reviewer's request; name that reviewer as the blocker rather than pointing at CI or the author's replies. When that reviewer is the invoking account, the `APPROVE` outcome review is itself the action that lifts the gate, so offer it directly.
